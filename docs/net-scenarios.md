# Сценарии работы сети

Что происходит в сети по шагам: кто что шлёт, какие функции и компоненты в этом участвуют и что бывает при сбое. Документ нужен, чтобы не изучать для этого код. Модель и инварианты (`S_T = F(S_{T−1}, I_T)`, И1–И8), а также найденные расхождения (Н1–Н11) описаны в [net-core.md](net-core.md). История решений — в [client-server-plan.md](client-server-plan.md). Код лежит в `src/lib_z13/modules/net_module/src/`, если не сказано иное. Сверено с кодом 2026-10-17.

Значения настроек по умолчанию: `CoreSettings` (`lib_core/fbs/core_settings.fbs`), `NetTuning` (`schemas/fbs/net_tuning.fbs`), таймауты (`schemas/fbs/settings.fbs`). Сеть живёт в `NetSessionSystem::Service` (`net_session_system.cpp`). Пока идёт переигрывание (`IsCatchingUp`), транспорт не обслуживается: он относится к настоящему, а не к тикам, которые считаются заново.

| Настройка | По умолчанию | Где решает |
|---|---|---|
| `fps` | 60 | тик = 1/60 с; сервер шлёт своё значение в `Welcome` |
| `snapshot_interval_seconds` / `rollback_snapshots_per_interval` | 1 с / 4 | снимок для отката каждые 15 тиков |
| `snapshot_retention_seconds` | 5 | глубина отката и истории событий сессии |
| `max_tick_backlog` | 15 | отставание стенных часов больше этого — заминка, тики выбрасываются |
| `max_catch_up_ticks_per_frame` | 1024 | сколько тиков без рендера за кадр; предел правдоподобного катч-апа |
| `send_interval_ticks` | 3 | батч команд, дайджест, `FinalizeLateInput` |
| `max_late_ticks` / `max_schedule_ahead_ticks` | 96 / 30 | окно сервера для команд: `[now − 96, now + 30]` |
| `session_event_delay_ticks` | 12 | через сколько тиков применяется вход/выход игрока |
| `clock_catch_up_threshold_ticks` / `clock_catch_up_every_ticks` | 2 / 4 | догон по тику |
| `clock_jump_threshold_ticks` | 15 | прыжок часов |
| `clock_offset_smoothing` | 0.25 | сглаживание оценки отставания |
| `SessionTimeout` | 32 попытки, 20–60 с | ENet рвёт соединение с замолчавшей стороной |
| `ConnectTimeout` | 32 попытки, 1–3 с | сколько ждать соединения при входе |

## 1. Старт сервера

1. Меню (или `--server` у выделенного сервера) создаёт `StartServerRequest`, который обрабатывает `OnStartServerRequest`.
2. Открывается транспорт на порту (ENet, `SessionTimeout`). Если порт занят: статус `kFailed`, а выделенный сервер завершается с `EXIT_FAILURE` (меню, куда вернуться, у него нет).
3. `ResetSessionScopedComponents` сбрасывает всё, что принадлежит сессии: очереди, журналы, часы, дайджесты.
4. Ставятся `NetSession`, `ServerRole`, статус `kConnected` и `Gameplay`. Хост сразу играет как обычный игрок.
5. Сервер отвечает на поиск по LAN (`LanDiscoverySystem`, [server-plan.md](server-plan.md), «Поиск сервера»).

Хост — тоже участник: свои команды он пишет в журнал сразу. `NetActionSender` не шлёт их себе батчем, а рассылает клиентам как `SequencedCommands`. Часы хоста — эталон, у него `offset = 0`.

## 2. Вход клиента

**Клиент.**

1. `JoinRequest` → `OnJoinRequest`: сброс сессионных компонентов, `ClientRole`, статус `kConnecting`, ENet-соединение (`ConnectTimeout`).
2. Соединение открыто → `SendClientHello`: версия протокола, хэш палитры блоков, список действий ввода (`DescribeActions`).

**Сервер** (`HandleClientHello`, `server_session.cpp`).

1. Версия или палитра не совпали → `Rejected{reason}`. Клиент: `FailSession`, статус `kFailed` с причиной.
2. `NegotiateActions` сопоставляет действия клиента со своими. Если не вышло — тоже `Rejected`, причём id игрока на отказ не тратится.
3. Выдаётся id игрока (`PlayerIdAllocator`). Id не переиспользуются, повторный вход получает новый. Повторный `Hello` на том же соединении игнорируется.
4. `SendWelcome`:
   - **катч-ап** (`MakeCatchUp`, `catch_up.cpp`):
     - снимок базы (`CatchUpBase`) — самый свежий снимок истории, который старше `max_late_ticks`, не новее отложенного отката и не новее общей границы подтверждения: его входы уже не изменятся (И4);
     - журнал команд после базы (`ActionsSince`);
     - удерживаемые значения на тик базы (`HeldValues`);
     - очередь будущих команд (`ScheduledCommands`);
     - границы подтверждения (`ConfirmedInputTicks`);
   - `fps`, `NetTuning`, `PhysicsTuning`, `BuildingTuning` — настройки сессии;
   - `action_ids` — согласованные id действий.
5. Сразу за `Welcome` идут события сессии новее базы: история плюс ещё не применённые. До `Welcome` клиент события игнорирует.
6. `SchedulePlayerJoined`:
   - сервер создаёт сущность игрока (точка спавна по `PositionLess`: сначала заполняется нижняя палуба), снимает её состояние и уничтожает;
   - рассылает всем `PlayerJoined{apply_tick = now + 12, entity_state}`;
   - игрок появляется у всех на одном и том же тике.

**Клиент получает `Welcome`** (`JoinFromWelcome`, `client_session.cpp`).

1. `AdoptSessionSettings`: настройки сервера заменяют свои до конца сессии, `RestoreOwnSettings` вернёт свои.
2. `IsPlausibleCatchUp`: `server_tick − snapshot_tick ≤ 1024`, иначе `Welcome` непригоден → `kFailed`.
3. `AdoptActionIds`, `LocalPlayer{id}`, затем `Gameplay` (сцена начинает строиться) и новый `ClockSync`.
4. `AdoptCatchUp`:
   - журнал заменяется серверным, в него вливается свой ещё не отправленный ввод (И7);
   - заменяются очередь, границы и история снимков (в ней остаётся одна база);
   - `RequestRollback(snapshot_tick → server_tick)`.
5. `TickWorld` между кадрами восстанавливает базу и переигрывает до `server_tick`. `WorldRestores` заставляет производные системы (индекс блоков, тела Bullet, комнаты, свет, меши) перестроиться полностью.
6. Статус остаётся `kConnecting`, пока не применится свой `PlayerJoined`: `FinishPendingJoin` видит сущность своего игрока → `EnsureLocalPlayerReady`, `kConnected`. С этого момента идут пинги и сравниваются дайджесты.

**Пока клиент грузился, время шло.**

1. Постройка сцены после `Gameplay` — один длинный кадр: на `spire` 3–20 с в зависимости от машины и сборки.
2. Пейсер (`TickPacer`, `lib_core/time/tick_pacer.h`) видит отставание больше `max_tick_backlog` и выбрасывает его как заминку, а число выброшенных тиков копит в `DroppedTicks`.
3. Клиент с `Gameplay` (`MakeUpDroppedTicks`) сразу просит прыжок часов на это число (`RequestClockAdjust`).
4. `TickWorld` прогоняет прыжок без рендера, до 1024 тиков за кадр. Остаток переходит на следующий кадр (`ClockAdjustRequest.ticks`).
5. Пинг при этом не нужен: клиент догоняет сервер сразу, пока станция не успела измениться ещё раз.
6. Что осталось после прыжка (время на сам прыжок, неточность) добирает пинг (сценарий 4).

## 3. Обычная игра

**Свой ввод (любая роль).**

1. `RecordChangedActions` пишет изменившиеся действия в `OutgoingCommands`. Раз в интервал снимков туда же переутверждаются удерживаемые (Н7: возможно, лишнее).
2. `ApplyOwnCommands` сразу кладёт их в свой журнал на тик записи: своя команда действует без задержки.
3. `NetActionSender` раз в 3 тика шлёт `CommandBatch{base_tick, commands, through_tick = свой тик}`. Пока удерживается отпускаемое действие, пустой батч уходит как пульс: он двигает границу подтверждения.

**Сервер принимает батч** (`HandleCommandBatch`).

1. Неизвестные действия отбрасываются. Сверх лимита частоты (`CommandRateLimits`) отбрасывается остаток батча — для честного клиента лимит недостижим.
2. Тик каждой команды зажимается в окно `[now − 96, now + 30]` и ставится не раньше предыдущей команды того же действия (`ScheduleTick`, `LastCommandTicks`).
3. Если тик сдвинулся, отправитель получает `CommandsRetimed`. Клиент переносит свою запись (`MoveOwnCommands`) и, если нужно, откатывается: команда не теряется, а только сдвигается.
4. Команды попадают в `ScheduledCommands`. Остальным уходит пачка в `SequencedCommands{runs, commands}`: `NetSession::QueueRun` держит пачки каждого получателя до конца кадра сервера (`FlushRelays`) или до следующего надёжного сообщения ему, так что клиент получает одно сообщение с пачками всех игроков вокруг. `through_tick` зажат `now + 30`.
5. `ConfirmInputThrough` двигает границу подтверждения игрока.

**Клиент получает чужие команды.**

1. `QueueSequencedCommands` ставит их в очередь и двигает границу. `CommitDueCommands` переносит их в журнал на их тике.
2. Если тик уже прошёл, команда вливается в журнал и ставится отложенный откат (`DeferRollback(tick − 1)`). Откаты одного кадра объединяются: `max_deferred_rollbacks` 16, `max_rollback_delay_ticks` 6.
3. Предсказание чужих: за границей подтверждения игрока его неабсолютные действия считаются отпущенными, абсолютные (углы обзора) — последним значением. Когда граница сдвигается и окажется, что он что-то держал или нажал, — откат с тика старой границы.

**Замолчавший игрок** (`FinalizeLateInput`, сервер, раз в 3 тика).

1. Тики раньше начала окна уже никто не изменит.
2. Если граница игрока отстала от `now − 97`, сервер сам отпускает его удерживаемые действия на этих тиках (`ReleasesAfter`) и поднимает границу.
3. Рассылает это как `SequencedCommands`, в том числе самому игроку. Клавиша, которую он всё ещё держит, будет записана снова как нажатие.

**Снимки и откат** (`lib_core/state/rollback.h`).

1. Снимок мира пишется в `PostFrame` каждые 15 тиков и хранится 5 с (`WorldSnapshotHistory`).
2. Откат восстанавливает самый свежий снимок не новее нужного тика и переигрывает обычными кадрами под `ReplayInProgress` до текущего тика.
3. Глубже самого старого снимка откатиться нельзя (`RollbackFailed`):
   - сервер пишет ошибку;
   - клиент до входа проваливает вход;
   - клиент после входа просит ресинк (сценарий 5).

## 4. Часы

Цель — тик клиента равен тику сервера. Клиент не опережает сервер на задержку (Н5: это цена в откатах, не ошибка).

1. Раз в секунду (`tick % 60 == 0`) клиент шлёт `Ping{client_tick}` (`SendPingIfDue`) и запоминает `ClockAdjustRequest.applied` на этот момент.
2. Сервер сразу отвечает `Pong{client_tick, server_tick}` по ненадёжному каналу.
3. `ApplyPong` (`clock_sync.cpp`):
   - считает оценку отставания: `rtt = received − sent − (прыжки за время пинга)`, `offset = server + rtt/2 − (received + ещё не прогнанная часть прыжка)`;
   - ответ не на тот пинг, что в полёте, игнорируется;
   - промах больше `max(15, rtt)` заменяет оценку целиком (часы сдвинулись), меньший — сглаживается (0.25).
4. `SteerClock` → `TakeClockAdjustment`:

   | `|offset|` | Действие |
   |---|---|
   | < 2 | ничего |
   | 2–14 | раз в 4 тика лишний тик (догоняем) или пропуск кадра (ждём) |
   | ≥ 15 | прыжок на весь `offset` |

5. `TickWorld` исполняет `ClockAdjustRequest`. Положительный — лишние тики подряд без рендера, до 1024 за кадр, остаток на следующий кадр. Отрицательный — пропущенные кадры.
6. Каждый прогнанный тик сразу вычитается из `ticks` и прибавляется к `applied`. Поэтому `Pong`, обработанный посреди прыжка, не просит оставшееся ещё раз и не считает прыжок задержкой сети.
7. Во время переигрывания отката `SteerClock` молчит: измерение тогда не о настоящем. Прыжок за заминку (`MakeUpDroppedTicks`) не ждёт, так как его величина — это стенные часы, а не измерение.

Открытое: в поле (Windows, Debug) прыжок на 1024 тика прошёл за ~40 мс и не сдвинул часы — Н11, ветка `f/net-clock-jump`, нужен лог клиента.

## 5. Дайджесты и ресинк

1. Сервер и клиент записывают `StateDigest{tick, хэш снимка, число сущностей, хэш имён, позиции игроков}` на тиках, кратных интервалу снимков (`RecordStateDigest`). Сравнивается только хэш снимка этого тика (`HashSnapshot`): он ловит любое расхождение состояния; остальное — для лога, чтобы было видно, что разошлось.
2. Сервер рассылает дайджест (`SendSettledStateDigests`), когда тик окончателен:
   - `tick + 96 < now`;
   - не новее отложенного отката;
   - не новее общей границы подтверждения.

   Вместе с ним уходят `input_through` (границы) и `received_through`.
3. Клиент сначала применяет границы из дайджеста (`ConfirmInputThrough`), а сравнивает (`CheckReceivedStateDigests`) только когда выполнены все условия:
   - сам дошёл до тика;
   - нет отложенного отката;
   - сервер уже знает все его команды до этого тика (`OwnCommandsSettled`).
4. Если не совпало: `ResyncIfDiverged` пишет дамп расходящегося тика (`DumpDivergedTick`, файлы `client_<id>`/`server_for_<id>`), шлёт `ResyncRequest{diverged_tick}` и ждёт (`awaiting_resync`). Новые дайджесты до ресинка не сравниваются. `RollbackFailed` после входа тоже ведёт к ресинку.
5. Сервер (`HandleResyncRequest`) пишет свой дамп и шлёт `Resync{катч-ап}` — тот же, что в `Welcome`.
6. Клиент (`HandleResync`): катч-ап как при входе, но часы назад не двигаются (цель — `max(server_tick, свой тик)`). Свой ввод, отправленный после запроса, вливается обратно (И7). Счётчик `StateDigests.resyncs` растёт. Непригодный `Resync` сбрасывает ожидание: следующее расхождение попросит снова.

Для игрока ресинк — откат на ~100+ тиков и переигрывание до настоящего: заметный рывок чужих сущностей, свой ввод сохраняется.

## 6. Заминки

- **Клиент**:
  1. долгий кадр (загрузка, GC драйвера, свёрнутое окно) — пейсер выбрасывает отставание больше 15 тиков, а `MakeUpDroppedTicks` тут же прыгает на выброшенное (сценарий 2);
  2. меньшее отставание пейсер прогоняет подряд сам;
  3. пока клиент стоит, сервер держит его клавиши (до границы) и затем отпускает их сам (`FinalizeLateInput`);
  4. команды клиента после заминки приходят поздно, сервер переносит их в окно (`CommandsRetimed`).
- **Сервер**: выбрасывает свою заминку так же, но не прыгает — он эталон. Клиенты по пингу видят, что опередили его, и ждут (пропускают кадры).
- Если заминка длиннее `SessionTimeout` (20–60 с), ENet рвёт соединение (сценарий 8).

## 7. Потери и задержки пакетов

- Команды, `SequencedCommands`, `CommandsRetimed`, события сессии, дайджесты, `Welcome`, `Resync`, `Hello`, `Rejected` идут по надёжному каналу ENet: потеря — это задержка, а не пропуск.
- `Ping`/`Pong` идут по ненадёжному каналу: потерянный пинг просто ждёт следующей секунды.
- Задержка своих команд больше окна: сервер переносит команду на начало окна, а не выбрасывает её.
- Задержка чужих команд оборачивается откатом у получателя.
- Глубина отката ограничена историей снимков (5 с); дальше — ресинк.
- Неразборчивый пакет: клиент его пропускает; сервер пропускает и разрывает соединение с отправителем.

## 8. Выход, разрыв, таймауты

1. **Игрок выходит в меню.**
   - Клиент: «Exit to Main Menu» снимает `Gameplay`, `ServiceNetSession` видит это и вызывает `EndSession`:
     - закрывается транспорт;
     - снимаются роли;
     - возвращаются свои настройки (`RestoreOwnSettings`);
     - сбрасываются сессионные компоненты.
   - Сервер получает `kDisconnected` → `HandleServerDisconnect`:
     - забывает соединение и `LastCommandTicks` игрока;
     - рассылает `PlayerLeft{apply_tick}`, где `apply_tick` — не раньше `now + 12` и после последней запланированной команды игрока (`LeaveApplyTick`), чтобы его последние команды отыграли.
2. **Сервер пропал** (хост вышел, сеть, таймаут). Клиент: `HandleClientDisconnect`:
   - если игра шла: `Gameplay` снимается, ставится `Pause`, статус `kDisconnected` («server closed the connection»);
   - если до входа: `kFailed` («disconnected before joining»).
3. **Хост выходит в меню.** `EndSession` закрывает сервер, все клиенты получают разрыв (п. 2).
4. **Таймаут.** ENet сам рвёт соединение, если другая сторона не подтверждает пакеты 20–60 с (32 попытки). Пределы выше ENet'овских, потому что первая постройка станции в Debug длится больше 11 с. Дальше — как при выходе: игрок пропадает у всех через `PlayerLeft`.
5. Граница подтверждения ушедшего забывается вместе с его событием в истории (`PruneSessionHistory`, через 5 с): откат через тик выхода её ещё видит.

## 9. Повторный вход

- Вход после выхода — обычный вход (сценарий 2) с новым id игрока. Старый игрок к этому времени удалён своим `PlayerLeft`.
- Клиент начинает с чистого состояния сессии (`ResetSessionScopedComponents` в `OnJoinRequest`).
- Сцена строится заново из снимка базы.

## 10. Поздний вход после долгой игры

Что растёт с длительностью игры: только сама станция (блоки, комнаты, свет) и число игроков. Журнал, история снимков и событий ограничены окном в 5 с.

1. **Размер снимка.**
   - `Welcome` везёт полный снимок базы одним надёжным сообщением: на двух копиях `spire` (14 678 блоков) ~1.4 МБ.
   - ENet режет его на фрагменты. На медленном канале передача — секунды, их съедает прыжок после загрузки.
2. **Постройка сцены.**
   - Это производное из блоков: индекс, тела, комнаты, свет, меши.
   - Время растёт с числом блоков, а не с длительностью игры. Это один долгий кадр, который потом догоняет `MakeUpDroppedTicks`.
3. **Прыжок после загрузки** — тоже симуляция: тики без рендера. Чем больше станция (больше тел, больше изменений), тем дольше каждый тик. Прыжок больше 1024 тиков растягивается на несколько кадров, сервер за это время уходит дальше, и следующий прыжок меньше.
4. **Риски.**
   - Если загрузка длиннее `SessionTimeout`, сервер считает клиента пропавшим. ENet обслуживается только между кадрами, а постройка сцены идёт в одном кадре.
   - Если база в `Welcome` старше 1024 тиков от `server_tick` (сервер долго не мог снять окончательный снимок), `Welcome` непригоден.

Замер: `StationLoadBench.DISABLED_LateJoin` (`src/lib_z13/modules/z13_module/tests/bench/station_load_bench_test.cpp`, перечислен в [benchmarks.md](../.claude/skills/perf-measure/references/benchmarks.md)).

- **Сценарий:**
  - сервер играет `Z13_LATE_JOIN_SECONDS` секунд (по умолчанию 60) и всё это время достраивает вторую копию `spire`;
  - затем входит клиент;
  - кадры клиента идут в реальном времени, как в `Core::Run`: сервер прогоняет тики, которые занял кадр клиента, а отставание клиента больше `max_tick_backlog` уходит в `DroppedTicks`.
- **Ожидается:** клиент догоняет сервер (|отставание| ≤ 2 тика 60 кадров подряд) без ресинка.
- **Печатает:**
  - размер снимка;
  - время входа;
  - самый длинный кадр;
  - выброшенные тики;
  - наибольшее отставание;
  - когда догнал.
- Блоки сервер ставит напрямую, а не командами игрока, поэтому перед входом стройка затихает (`2 × max_late_ticks`): до новичка доходят только блоки, попавшие в базу.

Замер 2026-10-17 (PRoot, Debug, 60 с игры, две копии `spire`):

| Что | Значение |
|---|---|
| снимок | ~1.4 МБ |
| вход (до `kConnected`) | через 5.3 с |
| самый длинный кадр клиента (постройка сцены) | 2.7 с |
| выброшено и сразу прыгнуто | 241 тик |
| наибольшее отставание после входа | 59 тиков |
| догнал | через 6.8 с от начала, без ресинка |

При 10 с игры — те же цифры: время входа зависит от размера станции, а не от длительности игры.

Запуск: `Z13_LATE_JOIN_SECONDS=60 bin/tests/z13_test_runner --gtest_also_run_disabled_tests --gtest_filter='StationLoadBench.DISABLED_LateJoin'`.
