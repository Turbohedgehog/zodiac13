# Дизайн: неполный мир клиента (интерес)

Предложение к этапу 4б `network-scaling-plan.md` (`f/interest-filter`); решения подтверждены пользователем 2026-10-26 (четыре вопроса внизу решены так, как предложено). Этап 4 (`f/interest-set`) уже считает интерес каждого клиента (`InterestMap`) и ничего не фильтрует.

## Почему этап 4б нельзя сделать одной веткой

Сегодня каждый клиент держит и симулирует весь мир: `Welcome`/`Resync` несут снимок всего мира, `PlayerJoined` — сущность игрока, `SequencedCommands` идут всем, `StateDigest.state_hash` считается по снимку всего мира, откат восстанавливает снимки всего мира. Если рассылать команды только в интерес, не меняя остального, мир клиента расходится с серверным уже у игроков, которых он не видит, а хеш — у всех. Поэтому фильтр команд идёт последним, после трёх подготовительных шагов.

## Модель

- **Клиент знает** игроков и блоки в секторах своей подписки (`InterestMap`: кольцо `radius` + запас `margin`, с гистерезисом). Остальных у него как сущностей нет. Свой игрок всегда в подписке. Предлагаю не «замораживать» чужое: устаревшая позиция врёт отрисовке и физике, а удалённое просто отсутствует.
- **Вход и выход — события сессии**, как `PlayerJoined`/`PlayerLeft` (`ScheduledSessionDeltas`, `apply_tick`, `session_event_delay_ticks`): `EntityEntered`/`EntityLeft` для игрока, `SectorEntered`/`SectorLeft` для блоков сектора. Откат раньше события возвращает мир без входа, повтор тиков применяет его снова: механизм уже работает для игроков, обобщается список вариантов `SessionDelta`.
- **Откуда состояние при входе.** Сервер состояние в `apply_tick` ещё не знает. Событие несёт отфильтрованный `CatchUp`: снимок из `WorldSnapshotHistory` на `snapshot_tick` (уже есть и у `Welcome`), `actions` за `(snapshot_tick, now]` тех, кто влияет на вошедшее, `held_values`, `pending`. `apply_tick` = `snapshot_tick`; клиент получает событие «из прошлого», просит откат на `apply_tick − 1` (`ApplyDueSessionDeltas` это уже делает) и повторяет тики. Цена — один откат на вход в сектор (около 0,1–0,15 мс на игрока в Debug, замер `f/rollback-cost-bench`) раз в несколько секунд ходьбы.
- **Кто за что отвечает.** Подписка сектора определяет, что есть у клиента: игрок присутствует, если его сектор в подписке. Вход игрока в подписку из чужого сектора даёт `EntityEntered` с тем же `CatchUp`, отфильтрованным по этому игроку. Сервер хранит для каждого клиента «что он знает» и каждый тик сверяет с `SectorIndex` и `InterestMap` (порядок событий внутри канала сохраняется: тот же надёжный канал, что у команд).
- **Команда** уходит надмножеству получателей: клиентам, чья подписка касается досягаемости команды (`CountRelay` уже считает это). Досягаемость берётся по виду команды: движение и взгляд действуют только на отправителя (0), стройка и снос — `max(destroy_reach_distance / kCellSize, wall_pick_reach_cells)`. Получателю достаточно подписки на сектор отправителя или досягаемости.
- **Правило настроек.** Внутреннее кольцо должно накрывать досягаемость стройки: `interest_radius_sectors * sector_size_cells >= wall_pick_reach_cells` (иначе игрок у края сектора не видит, что строит) — в `ValidateSettings`.
- **Откуда берётся хеш.** Сегодня `HashSnapshot` — по всему миру. Предлагаю хеш **по секторам**: блоки уже лежат в снимке группами по чанкам индекса (`SnapshotGrouping`, сектор кратен чанку), игроки — по сектору позиции. Сервер считает хеш каждого сектора один раз и шлёт клиенту хеши его внутреннего кольца; клиент сравнивает свои. Хеш одного клиента на сервере (`N` хешей вместо одного) дороже и не масштабируется. Сектор игрока на границе в тик дайджеста определяется по позициям снимка этого тика, поэтому обе стороны относят его одинаково.
- **Производные данные.** Помещения (`RoomCache`), физика (Bullet) и свет строятся из блоков, которые есть, поэтому внутри подписки совпадают с сервером; кольцо запаса нужно, чтобы граница среза лежала вне того, что игрок видит. Помещение, уходящее за запас, на границе среза режется: срез считается стеной для помещений (предлагаю, проверить в `f/interest-snapshots`). Газа и жидкостей пока нет; их этапы должны учесть интерес.
- **Ростер** («кто на сервере») откладывается отдельной веткой: игроков вне подписки у клиента нет. Чат (`chat-plan.md`) от подписки не зависит.

## Порядок работ

1. **`f/interest-snapshots`** (~600): снимок и хеш по набору секторов (предикат на захвате/хеше/восстановлении), хеши по секторам в `StateDigest` (рядом со старым `state_hash`, оба для всех секторов), правило настроек про досягаемость. Тест: хеш всех секторов совпадает с хешем всего мира в сумме (одно число из хешей секторов); фильтр по секторам оставляет только их; восстановление отфильтрованного снимка не трогает остальное. Поведение сети не меняется.
2. **`f/interest-events`** (~900): `EntityEntered`/`EntityLeft`, `SectorEntered`/`SectorLeft` и клиент, который их применяет; сервер шлёт их по `InterestMap`, а команды ещё всем, клиент терпимо отбрасывает команды для отсутствующих игроков и блоков. Хеш сверяется по внутреннему кольцу. Тесты: клиент сходится с сервером в своём внутреннем кольце при переходе между секторами; откат раньше входа убирает сектор, повтор возвращает; отсутствующие сущности не ломают команды.
3. **`f/interest-filter`** (~700): рассылка команд надмножеству по досягаемости вида команды, `Welcome`/`Resync` и `StateDigest` по подписке, `PlayerJoined`/`PlayerLeft` через вход и выход. Тесты: команды вне досягаемости не приходят; бюджет трафика на N клиентов, разбросанных по станции (`NetLoadBench`); сходимость на случайных перемещениях и отключении клиента.

Дальше как в `network-scaling-plan.md`: `f/interest-sources`, `f/interest-priority`.

## Решённые вопросы

1. Хеш по секторам, а не один на клиента.
2. Срез помещений на границе запаса — стена.
3. `apply_tick = snapshot_tick`, откат клиента на каждый вход в сектор.
4. Игрока, ушедшего из подписки, убирать сразу.
