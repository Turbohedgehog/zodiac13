# План: масштабирование сети до ~200 игроков

## Контекст

Ожидается около 200 игроков на одном сервере, а сервер работает на микрокомпьютере. Сейчас (`client-server-plan.md`) у каждого клиента весь мир, каждый клиент детерминированно повторяет **все** чужие команды, а сервер ретранслирует каждую команду всем по reliable-каналу. Трафик и работа сервера растут квадратично от числа игроков: 200 игроков с мышью (~1,8 КБ/с полезной нагрузки, замер `UplinkBudgetTest`) дают ~363 КБ/с входа и ~72 МБ/с выхода без заголовков.

Нужны три вещи: сжимать крупные сообщения, слать каждому клиенту только актуальное для него (игроков и объекты рядом) и для этого делить сцену на сектора. Связанные пункты техдолга `client-server-plan.md` — непрерывные оси по unreliable.

## Сжатие трафика

- **Порог.** Сообщение сжимается, только если его размер превышает `net.compression_threshold_bytes` (настройка в `net_tuning.fbs`). Мелкие сообщения (команды, пинг) не сжимаются: выигрыша нет, а процессор микрокомпьютера тратится. Основные кандидаты — снимки в `Welcome`/`Resync` (JSON-значения компонентов внутри FlatBuffers, хорошо сжимаются), снимки секторов (см. ниже) и `StateDigest`.
- **Формат.** Признак сжатия — в заголовке конверта сообщения, чтобы получатель не угадывал. Изменение протокола — с ростом `kProtocolVersion`.
- **Алгоритм выбрать замером** на целевом железе: LZ4 (дёшево по процессору), zstd (лучше степень, есть словари для мелких однотипных сообщений), встроенный range coder ENet (`enet_host_compress_with_range_coder`; сжимает все пакеты хоста без порога). Критерий — процессор сервера на 200 клиентов, а не только степень сжатия.
- **Детерминизм не затрагивается:** сжатие без потерь, на уровне транспорта.

## Сектора

- **Сетка секторов.** Сцена делится на сектора фиксированного размера в ячейках сетки строительства (`base-building-plan.md`, `kBlockSize`); размер — `net.sector_size_cells`. Сектор — целочисленная координата `Eigen::Vector3i`, как ячейка блока.
- **Принадлежность — производное.** Сектор сущности вычисляется из позиции; индекс «сектор → сущности» пересобирается системой (как индекс ячеек), в состоянии не хранится.
- **Объекты на границе.** Многоячеечные блоки, помещения и газ (`base-building-plan.md`) могут пересекать границу секторов. Помещение принадлежит сектору своей ячейки-якоря, а клиент, подписанный на любой из его секторов, получает его целиком.

## Управление трафиком: актуальное и неактуальное

- **Интерес клиента.** Клиент подписан на сектор своего игрока и соседние в радиусе `net.interest_radius_sectors`. Сущности, игроки и команды вне интереса ему не отправляются.
- **Приоритет внутри интереса.** Частота обновлений зависит от актуальности: близкие игроки и объекты — каждый интервал отправки, дальние — реже. Оси мыши чужих игроков (ориентация) — с пониженной частотой и по unreliable, нажатия и постройка — всегда и надёжно.
- **Вход в сектор.** При расширении интереса клиент получает снимок сектора (как `Welcome`, но для части мира) и с его тика повторяет команды этого сектора; при выходе сущности сектора удаляются у клиента. `StateDigest` считается по секторам интереса, `Resync` — тоже посекторно.
- **Сервер.** Остаётся единственным источником истины и симулирует весь мир, но сектора без игроков может «усыплять» (не симулировать физику и газ, пока там никого нет) — экономия процессора микрокомпьютера. Пробуждение должно быть детерминированным (по тику, а не по времени).
- **Модель синхронизации меняется.** Сейчас клиент повторяет все команды, теперь — только команды своего интереса. Команда, влияющая на несколько секторов (постройка на границе, взаимодействие игроков из разных секторов), рассылается всем, кто подписан хотя бы на один из них. Это главный риск плана: детерминизм на границах интереса.

## Порядок работ (одна ветка на этап)

1. **`f/net-load-metrics`** (~400): счётчики исходящего трафика сервера по пирам, нагрузочный тест на `InMemoryNetwork` с сотнями безголовых клиентов, замер процессора и трафика на целевом классе железа. Без этих цифр остальные этапы оптимизируют вслепую.
2. **`f/net-compression`** (~400): порог в настройках, признак в конверте, выбранный по замеру алгоритм, `kProtocolVersion`. Тесты: круговое сжатие, сообщение ниже порога не сжимается, снимок `Welcome` укладывается в заданный размер.
3. **`f/sectors`** (~600): сетка секторов, индекс «сектор → сущности», размер в настройках. Тесты: принадлежность, переход через границу, объекты на границе.
4. **`f/interest-management`** (~900): подписка клиента, фильтрация `SequencedCommands`/`PlayerJoined`/`StateDigest` по интересу, снимок сектора при входе. Тесты: клиент сходится с сервером в своём интересе при переходе между секторами; команды вне интереса не приходят; бюджет трафика сервера на N клиентов.
5. **`f/interest-priority`** (~600): частота обновлений по актуальности, чужие оси по unreliable (связано с техдолгом `client-server-plan.md`).
6. **`f/sector-sleep`** (~500): сервер не симулирует пустые сектора, детерминированное пробуждение. Тесты: `StateDigest` совпадает после сна и пробуждения сектора.

Этапы 1–2 независимы от остальных; 4 зависит от 3; 5 и 6 — от 4. Строительство базы (`base-building-plan.md`) лучше начинать с учётом секторов: помещения и чертежи должны знать про границы.

## Открытые вопросы

- Размер сектора и радиус интереса: зависят от дальности видимости и плотности базы; выбрать замером на этапе 1.
- Ориентацию чужих игроков, возможно, лучше передавать как состояние с пониженной частотой, а не как команды мыши: тогда её не нужно повторять детерминированно. Но направление взгляда влияет на постройку (луч кисти) — значит, для команд постройки оно должно входить в саму команду.
- Как совмещается откат клиента (переигрывание тиков) с посекторной подпиской: снимки для отката тоже станут частичными.
- Чертёж базы (`f/base-save`) и помещения, пересекающие много секторов: не раздувают ли они интерес клиента до «всего мира».
