# План: сохранение и восстановление состояния мира

Состояние мира нужно сохранять на диск и восстанавливать по сети (ресинхронизация), поэтому файл — лишь один из транспортов.

## Принципы

- **Observer'ы только для внешних событий:** ввод пользователя, запросы сохранения/загрузки, существующий жизненный цикл (`Register*/Init*`, конфиг, окно, GUI).
- **Всё производное — системы.** Тела Bullet, меши, кисть, группа ввода, камера считаются функцией от компонентов и сверяются по наличию/отсутствию данных, а не по факту добавления. Тогда любой откат данных подхватывается без событий.
- **Модули сами описывают свои типы** для flecs (meta + признак состояния). Рендер и физика ничего не сохраняют: у них только производное состояние.

## Слои

`Capture(world)` → `WorldSnapshot` (в памяти) → кодек (JSON; msgpack уже есть) → транспорт (файл, сеть).

- `Restore(world, snapshot)` принимает готовый снимок без текста (пригодится для истории снимков/отката).
- `WorldJsonStore`: `ToJson(snapshot)` и `FromJson(text) -> std::expected<WorldSnapshot, std::string>`, формат `{"version":1,"entities":[...]}`. Значения компонентов хранятся объектом (`rfl::Generic`), а не экранированной строкой.
- `RestoreWorld` обновляет на месте: совпавшие по имени сущности обновляются, лишние удаляются, лишние теги снимаются, отсутствующие создаются. Сначала полный разбор и проверка (неизвестный тип, версия) — при ошибке мир не тронут.

## Метки состояния

- Свойства задаются внутри структуры компонента независимыми вложенными типами: `using State = void;` (значения — состояние мира, пустые структуры становятся тегами состояния) и `using Singleton = void;` (flecs-синглтон); новые свойства добавляются так же. Вложенный тип не влияет на reflect-cpp; C++-наследование от базы сломало бы авто-meta (проверено). Проверка идёт концептами `StateComponentType`/`SingletonComponentType`, регистрация — `RegisterComponent<T>`, который сам применяет свойства. Meta строится только для `State`-компонентов, так что остальным (например, `Singleton` с `std::optional`) отражаемость не нужна.
- `StateEntity` — тег на сущности, входящей в снимок; `StateComponent` — признак на типе. State-singleton (оба свойства) распознаётся по `StateComponent` + `Singleton` на component-сущности, значение лежит там же.
- Сохраняются только сущности с `StateEntity`, component-сущности state-singleton'ов с заданным значением, и только компоненты с `StateComponent`. Это исключает `ActionListener`, `RigidBody`, `InputListener`, `CurrentActionListenerTag` и подобное. Немаркированные компоненты и singleton'ы без `State` в состояние не входят. Если в снимке нет записи о state-singleton, восстановление оставляет его как есть.
- Meta для общих типов регистрирует ядро до `RegisterComponentsEvent`: `Eigen::Matrix4f` (opaque-массив из 16 float, сначала спайк на flecs 4.1.6), `std::string`, `std::vector<T>`.

## Запросы сохранения/загрузки

- Запросы несут данные в памяти: `RequestLoadWorldState(world, json, callback результата)`, `RequestSaveWorldState(world, callback приёмника)`. Приёмник сам решает, писать ли в файл или слать по сети. Запросы транзиентны и никогда не входят в состояние.
- Ввод публикуется из системы внутри `progress()`, то есть в отложенном режиме flecs. Поэтому запрос просто кладётся в очередь singleton `PendingWorldState` (без observer'ов и событий), а `.immediate()`-система в `PreFrame` выполняет `Save`/`Load` по порядку вне отложенного режима. Остальные системы того же кадра уже видят восстановленные данные (проверено тестами, в том числе запрос из системы внутри кадра).
- Файловые `SaveToFile`/`LoadFromFile` (`std::filesystem::path`) — тонкий адаптер поверх запросов, в план PR 2 не вошёл.
- `Load` и `Save` выполняются только в потоке мира; сетевой поток передаёт данные в главный поток.

## Переделка observer'ов в системы

| Сейчас | Станет |
|---|---|
| bullet `OnBasicBlockAdded`, `OnRigidBodyRemoved` | система сверки тел: создаёт тело для `BasicBlock + Matrix4f` без тела, пересоздаёт при изменившемся трансформе, удаляет тела мёртвых сущностей и сущностей без `BasicBlock` (`PhysicsWorld` отдаёт список id тел) |
| bullet `OnPlayerMoved` (OnSet) | система по `PlayerCollider + Matrix4f` |
| building `OnEnable/OnDisableBuildingTool` | система: у игрока с `BuildingTool` ровно один `Brush`, без тега `Brush` удаляется |
| группа ввода `"Building"` в `ToggleBuildingMode` | система по `BuildingTool`; `ToggleBuildingMode` только переключает тег |
| render `OnBasicBlockAdded/Removed`, `OnBuildingBrushAdded/Moved/Removed` | одна система сверки `BlockModels` (создать, обновить трансформ, выгрузить модели умерших сущностей) |
| render `OnCameraTransform` (OnSet) | система, копирует матрицу в `RaylibCamera` |
| render `OnAddCamera` | удаляется (пустая функция) |

Вспомогательные функции (`EnsureBlockBody`, `ReleaseOrphanBodies`, `SyncBlockModels` и т. п.) — просто декомпозиция систем. `SyncBlockModels` принимает фабрику моделей, чтобы её можно было тестировать с фейком.

## Стабильная идентичность

- Блоки сейчас называются `BasicBlock_{id}`, а flecs id у пиров разные. Имя берётся из счётчика состояния: `Block_{n}`. Это же закрывает коллизии имён после восстановления.
- Счётчики id (`IdCounters`: игроки и блоки) — state-singleton (`State` + `Singleton`); `Gameplay` — рантайм-синглтон без данных (только `Singleton`) и в состояние не входит.

## Что сохраняется в первой версии

Блоки (`BasicBlock` + `Matrix4f`), singleton `IdCounters` и игрок: `Player`, `Camera`, `Matrix4f` (позиция и ориентация), `PlayerCollider`, `LookAngles`, `BuildingTool` (режим строительства). `LookAngles` нужен отдельно от матрицы: `ApplyCameraMove` перезаписывает вращение из него, и без него камера «отскочит» к старым углам. Режим строительства — это тег `BuildingTool`; `Brush` и группа ввода выводятся из него.

## Порядок работ (три PR)

**PR 1. Observer'ы → системы, без сериализации.**
Поведение не меняется, существующие `building_block_test` и `physics_collision_test` остаются зелёными. Новые тесты на системы: блок, созданный напрямую, получает тело через кадр; снятие `BasicBlock` без `destruct` освобождает тело; матрица, изменённая на месте, перемещает тело; прямое добавление/снятие `BuildingTool` создаёт/удаляет `Brush` и группу ввода.

**PR 2. Инфраструктура (`lib_core`).**
Слои `Capture/Restore/ToJson/FromJson`, `StateEntity`/`StateComponent`, meta для `Matrix4f` и `std::vector<T>`, запросы с данными, `PendingWorldState` и immediate-система. Тесты в `src/tests/.../flecs_state`: круг `Matrix4f`, неотмеченное не попадает в JSON, семантика «заменить», ошибки (битый JSON, неизвестный тип, версия) не меняют мир, детерминизм `Save`.

**PR 3. Регистрация типов и интеграционные тесты.**
`z13_module` регистрирует свои типы; `SpawnBlock` с `StateEntity`, счётчиком и порядком «transform → тег»; `CreateTestPlayer` помечает игрока. Тесты в `z13_module/tests/state/` (на `Z13TestWorld`):

1. Основной сценарий: строим и удаляем блоки, двигаем и поворачиваем камеру, входим в режим строительства, `Save`; меняем всё, `Load`; сравниваем число блоков и координаты, камеру, режим.
2. Режим в обе стороны (кисть и группа ввода).
3. Ориентация не отскакивает после кадра движения (случай без `LookAngles` тоже).
4. Физика: тела восстановленных блоков на месте, ПКМ их удаляет.
5. Имена не конфликтуют после `Load`.
6. Два мира обмениваются состоянием через строку (имитация сети), имена и счётчики совпадают.
7. Загрузка через событие, отправленное из системы внутри кадра.

Рендер проверяется вручную через `run`.

## Заметки

- Системы сверки проходят O(число блоков) за кадр; при росте перейти на change detection flecs.
- Лага в кадр нет: кисть, тела блоков и удаления видны следующим системам и рендеру в том же кадре. Для этого системы, которые создают/удаляют сущности или проверяют компоненты внутри тела (`has<>`), объявляют `.write<...>()`/`.read<...>()`, иначе flecs не вставит sync point. Обработка запроса на удаление блока идёт в `PostUpdatePhase`: отдельная поздняя фаза выполнялась бы после рендера.
- Транзиентные `RequestBuildBlock`/`RequestDestroyBlock` в состояние не входят: на границе кадра их нет.
- Лимиты на размер и число сущностей для снимков из сети — позже, вместе с сетевым модулем.
- Быстрое сохранение/загрузка для тестов: действия `SAVE_SCENE`/`LOAD_SCENE` (F5/F9 по умолчанию, группа Control, файл `quick_save.json` в каталоге данных игры, как у конфига клавиш). GUI не входит в план. Действия, которых нет в уже существующем файле конфига клавиш, получают привязки по умолчанию при загрузке (занятая клавиша пропускается). Действие без клавиш сохраняется в конфиг как `KEY_UNKNOWN` и после загрузки остаётся снятым.
- В `CLAUDE.md` добавить правило про observer'ы и системы (в раздел про flecs).
