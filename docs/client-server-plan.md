# План: клиент-сервер (ENet)

Продолжение `network-sync-plan.md`: там уже есть `PlayerActionLog` (с `player_id`), `WorldSnapshotHistory`, `Replay` и proof-of-concept «два мира сливают действия и приходят к одному состоянию». Здесь — первый настоящий транспорт, жизненный цикл сессии и синхронизация **только через команды игроков** `(action_id, value)`. Своя команда применяется сразу, опоздавшие чужие — откатом и повтором (`WorldSnapshotHistory` + `Replay`), см. «Риски».

## Требования

- Сервер создаётся флагом `--server[=PORT]` (порт по умолчанию **26213**). Выделенный сервер не грузит raylib_module (нет окна, GUI, рендера).
- Клиент можно запустить сразу подключённым: `--connect host[:port]` (порт по умолчанию тот же). Несовместим с `--server`.
- Сервер также создаётся из главного меню (диалог выбора порта): тогда это listen-server — с рендером, хост играет сам.
- В главном меню кнопка «Join»: диалог с IP/хостом и портом.
- Транспорт — ENet.
- При подключении клиент получает снимок сцены. Каждый клиент получает уникальный id.
- Чужой игрок виден как октаэдр уникального цвета. Сервер виден клиентам как обычный игрок (id 0).
- **Всё — движение, взгляд, строительство и любые будущие сущности — идёт через команды `(action_id, value)`.** Клиент шлёт серверу только свои команды (экономия трафика); состояние сцены и сущностей по сети не реплицируется.

## Проектные решения

**Роль.** `z13::net::ServerRole`/`ClientRole` — runtime-singleton теги (не state, без данных), лежат в `z13/components/net.h` рядом с командами GUI. Одна и та же сетевая логика обслуживает `--server`, «Start Server» из меню, `--connect` и «Join»; отличие — только в источнике команды и наличии рендера. Ни один тег не выставлен — одиночная игра, поведение не меняется. Отдельные теги, а не одно enum-поле, чтобы будущая составная роль (напр. listen-server = сервер + локальный клиент) не требовала переопределения типа.

**Модуль.** Новый плагин `src/lib_z13/modules/net_module` по образцу `bullet_module` (фабрика, `_objects` для сборки `SHARED`-плагина). Публичные заголовки (`include/net_module/`): `transport.h` (интерфейс), `protocol.h` (сообщения + codec). ENet — только внутри `enet_transport.cpp`: `ENetHost*`/`ENetPeer*` наружу не выходят, соединения адресуются `ConnectionId` (uint32), `ENetHost` под `unique_ptr` с deleter, пары `enet_initialize/deinitialize` — в RAII. Сессия — singleton `NetSession` с pImpl (`State`/`state_`, `shared_ptr` — исключение для обёрток над нативным, как `PhysicsWorld`).

**Однопоточность.** ENet обслуживается системой в начале кадра (`enet_host_service(host, &event, 0)`), потоков нет — тесты детерминированы.

**Запуск без рендера.** Отдельный `config/z13_config_server.yaml` без записи raylib_module; launcher выбирает между ним и обычным `z13_config.yaml` по `Config::IsServer()`. Разбор YAML вынесен из анонимного namespace в тестируемые `ParseModuleList`/`ReadModuleList` (`z13_launcher/module_list.h`), обе возвращают `std::expected<std::vector<std::string>, std::string>`. Выделенный сервер стартует сразу в `Gameplay` (без `Pause`/меню) — `BootstrapSystem::OnSelectInitialState`. Корректное завершение по SIGINT/SIGTERM — `Core::Run()` сам ставит обработчик и сам его опрашивает (сигнальный флаг — `sig_atomic_t`, не указатель на объект; единственное оправданное исключение из «без static/глобалов»), так что `pending_shutdown_` читается и пишется только в главном потоке и не нуждается в atomic.

**`--connect`.** `Endpoint{host, port}` + `ParseEndpoint(text) -> std::expected<Endpoint, std::string>` в `lib_core` (один парсер для CLI и диалога Join; IPv6-литералы пока не поддерживаются). `Config::GetConnectEndpoint() -> std::optional<Endpoint>`. Bootstrap при заданном endpoint оставляет `Pause` (меню показывает «Connecting…») и выдаёт `JoinRequest`; успех закрывает меню, ошибка возвращает в главное меню с причиной.

**Игроки.**
- Сущность игрока именуется `Player_<id>` (снимки сопоставляют сущности по имени — два игрока с одним именем слились бы). `SpawnPlayer(world, id)` — публичный заголовок z13_module, transform считает сама (`id * kSpawnSpacing`, детерминированно, см. ниже); `Z13TestWorld::Player()` ищет локального игрока по `CurrentActionListenerTag`, не по имени.
- Id игроков выдаёт только сервер из `IdCounters.last_player_id` (state, монотонный, не переиспользуется). Сервер-игрок = 0, клиенты 1, 2, … Id блоков и прочих сущностей выделяет сама симуляция — детерминированно и одинаково на всех участниках (см. ниже).
- Точка спавна смещается на `id * kSpawnSpacing`, чтобы октаэдры не совпадали.
- «Локальность» — не state: `CurrentActionListenerTag` + `InputListener` навешивает система (`SyncLocalPlayerListener`) по `LocalPlayer.id` (`std::optional<uint32_t>`). `ActionListener` сама по себе — у **каждого** игрока, локального или нет (отдельная система `EnsurePlayerActionListener`, тоже не state-зависимая): повтор реплеит записи `PlayerActionLog` по `player_id` вне зависимости от того, чей это игрок, и ему нужно куда писать значение. Локальный игрок клиента, пришедший в снимке, получает живой ввод, остальные — нет.
- `Gameplay::OnInit` на клиенте **не** спавнит игрока и не сбрасывает `IdCounters` — сцену даёт снимок.
- Рендер камер ограничивается сущностью с `CurrentActionListenerTag` (`EnsureRaylibCamera`/`SyncRaylibCamera`): иначе `gameplay::Camera` чужих игроков из снимка породит лишние `RaylibCamera`.

**Цвет.** `PlayerColor(id)` — чистая детерминированная функция (шаг по hue на золотое сечение, фиксированные S/V), `z13/components/`. По сети не передаётся.

## Модель синхронизации: серверная последовательность команд

Каждый участник (сервер и все клиенты) исполняет **одни и те же команды на одних и тех же тиках в одном порядке**; состояние сцены — детерминированная функция от `(снимок, поток команд)`. Поэтому новые виды сущностей (не только блоки) не требуют сетевого кода: они появляются как побочный эффект команд, которые уже ходят по сети.

**Клиент → сервер.**
- Локальный ввод считается как сейчас, но на клиенте **не применяется к симуляции напрямую**: значения пишутся в буфер `OutgoingCommands` (запись только при изменении + переутверждение удерживаемых раз в секунду — уже умеет `PlayerActionRecorder`). `NetActionSender` раз в `kNetSendIntervalTicks` (3 тика ≈ 20 Гц) шлёт накопленное одним `CommandBatch`; пустой батч не шлётся — простаивающий клиент трафика не создаёт.
- `PlayerActionLog` хранит **только применённые (упорядоченные сервером) команды** всех игроков — ровно то, что нужно `Replay`. В одиночной игре (`None`) рекордер пишет в него напрямую, как сейчас.
- Каждая команда штампуется тиком клиента `t_i` и **на нём же применяется**: отправитель в `OwnCommandsFramePhase` (между `Record` и `Remote`) кладёт её прямо в `PlayerActionLog` с квантованным значением, как на проводе, — задержки своего ввода нет. `CommandBatch` несёт `t_i` как `apply_tick`; сервер и остальные получают команду с опозданием на путь по сети и чинят его откатом. Эхо собственных команд от сервера не нужно. (До `f/net-instant-input` было `t_i + clock_offset + kInputDelayTicks`, 12 тиков сверху — ощутимые ~200 мс.)

**Сервер: `CommandSequencer`.** Берёт присланный `apply_tick` как есть, ограничивает его разумным диапазоном вокруг своего текущего тика (защита от испорченного/враждебного клиента — не доверие offset'у клиента, а просто санитизация входа), кладёт в свою очередь и рассылает `SequencedCommands` **всем клиентам, кроме отправителя** (он уже применяет её сам). Порядок внутри тика — `(apply_tick, player_id, action_id)`; порядковый номер команды не нужен и по проводу не ходит: рекордер физически не может выдать два значения одного действия на одном тике, так что ключ выводит каждый участник сам. Собственные команды хоста (listen-server) идут тем же путём. Привязка к тику (jitter buffer) сохраняет **длительность** удержания при неравных задержках пакетов. Если команда пришла уже после своего `apply_tick` (`apply_tick ≤ now` на сервере) — из-за задержки сети или неточной оценки offset на клиенте, разница неважна, — сервер откатывается и воспроизводит журнал (см. «Опоздавшие команды»), затем рассылает её остальным как обычно; отправитель ничего не теряет. Rollback тем самым не только чинит сетевые опоздания, но и снимает необходимость в точной синхронизации времени: ошибка оценки `clock_offset` — это просто ещё одна причина опоздать, не отдельный класс отказа.

**Все участники: `RemoteInput`.** Очередь команд по тику → на тике применения обновляет удерживаемое значение `(player_id, action_id)`, дописывает запись в `PlayerActionLog`, а в `CalculateActionFramePhase` (после расчёта живого ввода) перезаписывает значения в `ActionListener` игроков. Логика «удерживаемые значения → ActionListener» выделяется из `Replay` (`ReplayActionState`/`ApplyCurrentValues`), а не дублируется. Дальше системы (`ApplyMoveActionListener`, строительство, `ProcessDestroyBlockRequest`, всё будущее) работают как при живом вводе.

**Часы.** `SimulationClock` — state, поэтому `Restore` при join приводит клиентский тик к серверному тику снимка: сразу после подключения клиент отстаёт на время доставки снимка. Дальше клиент считает тики сам и ведёт свои часы к серверным по оценке `clock_offset` в обе стороны (`ClockAdjustRequest` → `TickWorld`): небольшое расхождение (от `kClockCatchUpThresholdTicks`) закрывается по тику раз в `kClockCatchUpEveryTicks` — лишним тиком, если клиент отстаёт, пропуском кадра, если впереди; расхождение от `kClockJumpThresholdTicks` (фриз любой из сторон: `Core::Run` догоняет медленные кадры по стенным часам, `TickPacer`, но отставание больше `kMaxTickBacklog` отбрасывает) — сразу целиком, иначе команды клиента выпали бы из окна приёма сервера. Образец пинга, промах которого не объясним асимметрией пути (больше RTT), берётся целиком, а не через EWMA. Чем точнее часы, тем меньше глубина откатов у остальных.

**Пинг: синхронизация локального времени клиента.** Раз в секунду клиент шлёт `Ping{client_tick}`; сервер отвечает `Pong{client_tick, server_tick}` — `server_tick` берётся в момент ответа, без ожидания следующего кадра симуляции. Клиент по паре (время отправки `Ping`, время получения `Pong`, оба по своим же тикам) считает `rtt_ticks` и оценку одностороннего запаздывания `rtt_ticks / 2`, откуда новый образец `clock_offset = server_tick + rtt_ticks/2 - client_recv_tick`. Держится сглаженная оценка (EWMA, `kClockOffsetSmoothing`) — не одно сырое значение: разовый всплеск задержки не должен резко сдвигать расписание всех последующих команд. Первая оценка появляется только после первого `Pong` (до этого `clock_offset = 0`, роль `kInputDelayTicks`-запаса и rollback — сгладить стартовую погрешность); `Welcome`/`Resync` больше не несут отдельного `clock_offset` — не нужен, раз есть постоянный источник свежее join. Пинг — не про корректность (её обеспечивает rollback), а про то, чтобы `apply_tick` был близок к реальному и откатов было мало.

**Опоздавшие команды: откат и повтор.** Команда, у которой `apply_tick ≤ now` (клиент получил чужую команду поздно, сервер получил свою от клиента поздно), не отбрасывается:
- запись вставляется в `PlayerActionLog` на своё место (`BoundedHistory::MergeSorted`, ключ `(tick, player_id, порядковый номер)`);
- мир откатывается к самому свежему снимку `WorldSnapshotHistory` с `tick ≤ apply_tick` и доигрывается обычными кадрами до текущего тика (`RequestRollback(world, apply_tick, now)`); всё, что опоздало за один кадр, объединяется в один откат к самому раннему тику;
- откат — **глобальное состояние мира, а не отложенный вызов** (`lib_core/rollback.h`, этап 3). Любая система, нашедшая опоздавшую команду, дописывает её в журнал и зовёт `RequestRollback(world, to_tick, target_tick)`, который только опускает `RollbackRequest.to_tick` до `min` и поднимает `target_tick` до `max` — несколько опоздавших за один кадр коалесятся в один откат к самому раннему тику сами собой, без разбора очереди. Дальше два шага, оба внутри `TickWorld(world, delta)` — **единственного места, откуда вообще зовётся `world.progress()`** (`Core::Update()` и тестовый харнесс зовут только её): `RestoreWorld` из свежайшего снимка с `tick ≤ to_tick`, а затем **обычные кадры**, пока `SimulationClock.tick` не дойдёт до `target_tick`. Восстановление обязано идти между кадрами: подмена сущностей мира изнутри кадра заставляет flecs пропустить остаток пайплайна (проверено — фаза очистки ввода не отрабатывала). Повтор же — ровно те же системы в том же порядке, что и живой кадр, просто под флагом `ReplayInProgress`: живой ввод и рекордер отключены, `NetActionSender` не шлёт повторно уже отправленное, транспорт не обслуживается (он относится к настоящему). Число кадров догона за один `TickWorld` ограничено `kMaxCatchUpTicksPerFrame` — страховка от испорченного `target_tick`, а не планировщик;
- удерживаемые значения действий во время повтора ведёт `ReplayActionState` (`z13_module`, системы `Replay::AdvanceRecordedValues`/`InjectRecordedActionValues`): она — чистая функция от (журнал, текущий тик), и разрыв в тике сам означает «только что откатились», так что пересборка значений не требует отдельного сигнала. Входя в повтор, каждое действие выставляется «ровным» (`current_value` и `prev_value` в последнее известное значение), иначе удерживаемая клавиша прочиталась бы как новый фронт и переключатель сработал бы повторно;
- откат, которому не нашлось достаточно старого снимка, выставляет `RollbackFailed{reason}`; его разбирает тот, кто просил откат (клиент — в `Resync` или `Failed`);
- глубина отката ограничена окном хранения (`Config::GetSnapshotRetentionSeconds`, одно и то же для снимков и журнала): если достаточно старого снимка нет (`RollbackFailed`), это редкий запасной путь — `Resync` (ниже);
- события сессии (`PlayerJoined/Left` на своём тике) пишутся в тот же журнал и воспроизводятся при повторе — иначе откат через тик входа/выхода потерял бы игрока (требует расширения `Replay`);
- стоимость отката — до одного интервала снимков (`Config::GetSnapshotIntervalSeconds`, по умолчанию 1 с = 60 вызовов `progress()`); в сетевых ролях интервал можно уменьшить; глубина и частота откатов считаются в метриках.

**Join.** Вход игрока — тоже упорядоченное событие на тике `J`: на `J` сервер спавнит `Player_<id>` и шлёт `Welcome`; остальные клиенты получают `PlayerJoined{apply_tick=J, entity_state}` заранее и спавнят игрока на том же тике. `Welcome.snapshot` — **не** свежий захват на момент `J` (полный обход мира на каждый join слишком дорог), а последний кэш `WorldSnapshotHistory` (`snapshot_tick` — его тик) плюс `actions`: записи `PlayerActionLog` с `tick > snapshot_tick` — тот же формат, что повтор уже умеет проигрывать. Клиент мержит `actions` в свой `PlayerActionLog` (`BoundedHistory::MergeSorted`), кладёт присланный снимок в собственный `WorldSnapshotHistory` и подаёт обычный `RollbackRequest{to_tick = snapshot_tick, target = server_tick}` — тот же самый механизм отката (см. выше), просто на этот раз «откат» — это бутстрап с нуля, а не коррекция уже идущего мира; отдельного пути для join в коде нет. Так как `ActionListener` не state, `Welcome` кроме снимка несёт `held_values` (сейчас удерживаемые действия всех игроков) и `pending` (уже разосланные команды с `apply_tick > J`). `PlayerLeft{apply_tick}` назначается после последней запланированной команды игрока: у всех участников они успевают исполниться до удаления.

**Требования к детерминизму** (предпосылка всей схемы):
- Симуляция — чистая функция состояния, команд и тика: единый фиксированный `delta_time = 1/TicksPerSecond` на всех участниках (включая клиента), без wall-clock и `rand`.
- Порядок обработки при конкуренции — по `player_id`, а не по порядку итерации ECS (`ProcessBuildBlockRequest` и т.п.): иначе `Block_N` у участников разойдутся (это же отмечено в `network-sync-plan.md` как «не гарантия на будущее»).
- Флоаты: для симуляционных модулей отключить контракцию FMA (`-ffp-contract=off`; MSVC `/fp:precise`). Побитовая идентичность между x64/arm64/Windows и в Bullet не гарантируется — поэтому есть контроль рассинхрона.
- Живой ввод, превью кисти, рендер — вне симуляции.

**Контроль рассинхрона.** Раз в секунду сервер шлёт `StateDigest{tick, state_hash, entity_count, name_hash, [player_id → position]}` на тике, кратном интервалу снимков (`WorldSnapshotHistory` уже снимает состояние именно на таких тиках). Сервер шлёт дайджест тика T не сразу, а когда `now ≥ T + kMaxLateTicks`: раньше его могла бы изменить опоздавшая команда, а по упорядоченному каналу 0 все команды тика ≤ T приходят клиенту раньше дайджеста. Дайджест считается в PostFrame на тиках снимков (`StateDigests.local`), повтор пересчитывает его сам. Клиент, дойдя до этого тика (и после отката от команд, полученных вместе с ним), сравнивает со своим хэш снимка тика (`state_hash`, `HashSnapshot`) — точное равенство; имена и позиции только поясняют расхождение в логе (до `f/net-digest-state-hash` сравнивались они, позиции с допуском ε, и всё остальное расходилось незамеченным). Откат по опоздавшим командам расхождение не вызывает (после повтора состояние равно «как будто пришло вовремя»); дайджест ловит то, что откат не объясняет: числовой дрейф платформ, событие вне окна журнала, ошибку в коде. При расхождении шлёт `ResyncRequest`, сервер отвечает как на join (`Resync`: снимок + `held_values` + `pending`); клиент делает `RestoreWorld` и продолжает, сохраняя `LocalPlayer.id`.

## Согласование `action_id`

**Проблема.** Команда по сети — это `(action_id, value)`, а `ActionInfo::IdType` сейчас выдаётся локально при сборке `ActionMap` из конфига модулей. На клиенте и сервере набор модулей может различаться (например, подключён строительный модуль только у одной стороны), и тогда один и тот же `action_id` означает разные действия — или не означает ничего.

**Правило.** Все `action_id` на сервере и всех клиентах одинаковые, и назначает их сервер.

- При join клиент в `ClientHello` сообщает список своих действий — стабильные имена `(enum_name, value_name)`, а не локальные id.
- Сервер сверяет их со своей таблицей. Известные действия получают уже закреплённый за ними id. Неизвестные (из модуля, подключённого только у клиента) сервер регистрирует у себя и выдаёт им новый уникальный id. Закреплённое сервером не переиспользуется и не меняется до перезапуска сервера (по аналогии с `IdCounters.last_player_id`).
- `Welcome` (и `Resync`) несёт таблицу `имя → action_id`; клиент перестраивает по ней свой `ActionMap`, не трогая биндинги клавиш и конфиг ввода — меняется только соответствие имя ↔ id.
- Действие, у которого на стороне сервера нет обработчика (модуль не подключён), сервер всё равно регистрирует и пишет в `PlayerActionLog` и рассылает: исполнит его тот, у кого модуль есть. Иначе журналы и повтор разошлись бы.
- Действие, которое не удалось согласовать (расхождение в семантике или превышен лимит), отвергается через `Rejected{reason}` на join, а не молча отбрасывается позже.
- Снимки, `PlayerActionLog` и `held_values` всегда используют серверные id: клиент переводит свои локальные id в серверные до записи в `OutgoingCommands` и обратно при чтении входящих.
- Нужен тест: клиент с лишним действием получает серверный id, сервер его регистрирует и рассылает остальным; два клиента с разными наборами действий сходятся по `WorldJsonStore::Save`.

**Сделано** (`f/net-action-ids`, `z13_module/input/action_negotiation.*`). Отличия от текста выше: `ClientHello.actions` несёт `(enum_name, value_name, enum_value)`, а `Welcome.action_ids` — серверные id в том же порядке (параллельный список, не таблица имён). `Resync` таблицу не несёт: id клиента после `Welcome` не меняются. Идентичность действия — имя: другое `enum_value` у известного имени игнорируется (клиент хранит свою нумерацию), а занятое значение у нового действия сервер сдвигает на следующее свободное. Сервер отказывает (`Rejected`) до выдачи `player_id`: пустое/длинное имя, больше `kMaxActionsPerClient` (1024) действий в списке, уже занято `kMaxRemoteActions` (4096) зарегистрированных удалённо действий (защита от переполнения карты одним клиентом), нет свободного id (≤65535, ширина `CommandWire`). Повтор того же действия в списке не ошибка, id тот же. Зарегистрированные сервером действия лежат в группе `kRemoteActionGroup`, в конфиг ввода и GUI не попадают; имена хранит `ActionMap::owned_names`. Клиент без действия, которое зарегистрировал сервер для другого клиента, его команды просто не исполняет.

Открытые вопросы: стабильность id между перезапусками сервера (если нужны сохранения с журналом действий, таблицу надо сохранять), и как вести себя, когда второй клиент приходит с тем же новым действием — сервер просто возвращает уже закреплённый id.

## Протокол

FlatBuffers (`modules/net_module/fbs/net.fbs`, уже подключённый генератор): фиксированные `struct` для горячих сообщений вместо msgpack-«карт» с именами полей, `Verifier` для недоверенных байт. Снимок — таблица `z13.fbs.state.WorldSnapshot` (`lib_core/fbs/world_snapshot.fbs`) прямо в сообщении (`ToFlatbuffer`/`FromFlatbuffer`), из `CaptureState`, а не `CaptureWorld`: фильтр `DefaultEntityFilter` исключает любую сущность с `flecs::Component`, а значение singleton-компонента живёт как раз на ней, так что `IdCounters`/`SimulationClock` в снимок не попали бы. Обычно это готовый снимок из кэша `WorldSnapshotHistory` (см. «Join» выше), свежий `CaptureState` — только пока кэша нет. `kProtocolVersion` в handshake. Все сообщения — reliable, канал 0 (потерянная команда нарушила бы детерминизм), **кроме `Ping`/`Pong`** — им нужна не гарантия доставки, а честное время в пути: на reliable-канале 0 они встали бы в очередь за `CommandBatch`/`SequencedCommands` и мерили бы не сеть, а очередь. Отдельный канал 1, unreliable-unsequenced; пропавший `Ping` просто ничего не даёт для этой секунды, следующий — через секунду.

| Сообщение | Канал | Направление |
|---|---|---|
| `ClientHello{version, actions: [имя действия]}` (см. «Согласование `action_id`») | 0, reliable | C→S |
| `CommandBatch{base_tick, [CommandWire]}` (`base_tick` — уже `apply_tick`) | 0, reliable | C→S |
| `ResyncRequest{}` | 0, reliable | C→S |
| `Ping{client_tick}` | 1, unreliable | C→S |
| `Welcome{player_id, action_ids, fps, tuning, server_tick, snapshot, snapshot_tick, actions, held_values, pending}` / `Rejected{reason}` | 0, reliable | S→C |
| `Resync{server_tick, snapshot, snapshot_tick, actions, held_values, pending}` | 0, reliable | S→C |
| `PlayerJoined{apply_tick, entity_state}` / `PlayerLeft{apply_tick, player_id}` | 0, reliable | S→все |
| `SequencedCommands{player_id, base_tick, [CommandWire]}` (`base_tick` — уже `apply_tick`) | 0, reliable | S→все, кроме отправителя |
| `StateDigest{tick, entity_count, name_hash, state_hash, [PoseWire]}` | 0, reliable | S→все |
| `Pong{client_tick, server_tick}` | 1, unreliable | S→C |

- `CommandWire {tick_delta: ubyte, action_id: ushort, value: short}` — 6 байт (с выравниванием); `value` квантуется (`kActionValueScale`), булевы точно. Квантует рекордер при записи в журнал (`CanonicalActionValue`) и пишет то же значение обратно в `ActionListener`, так что живая игра, реплей и пиры видят одно и то же число, а провод переносит его без потерь. Остаток дельты мыши, который отбросило бы округление, переносится на следующий кадр.
- `PoseWire {player_id, x, y, z}` — только для лога расхождения дайджеста.
- `Welcome.actions`, `held_values` и `pending` — не `CommandWire` (тот несёт только относительный `tick_delta` в пределах одного `base_tick` для одного игрока — тесно для произвольного окна истории нескольких игроков), а `[ActionRecordWire]` (`tick, player_id, action_id, value`, 24 байта) — `PlayerActionRecord`, который `PlayerActionLog` уже хранит на любом участнике.
- `PlayerJoined` использует уже существующий `EntitySnapshot`: в `lib_core` добавляются `SaveEntityState(world, entity)` и `ApplyWorldStateDelta(world, bytes)` (как `ApplyWorld`, но **без** удаления остальных — `RestoreWorld` для дельты не годится).
- Сырые flecs entity id по сети не ходят — только имена и `player_id`. `CommandBatch` не содержит `player_id`: сервер знает `ConnectionId → player_id`, подменить чужого игрока клиент не может.
- Сервер отбрасывает `action_id`, которого нет в `ActionMap`, ограничивает частоту команд на соединение и игнорирует `CommandBatch` до `Welcome`.

## Жизненный цикл и UI

- Server: `StartServerRequest{port}` (CLI или GUI) → открыть host → роль → `add<Gameplay>` (спавн игрока 0). Порт занят → `ConnectionStatus = Failed(reason)`; для CLI — critical-лог и код возврата 1.
- Join: `JoinRequest{endpoint}` (CLI `--connect` или GUI) → `Connecting` → `ClientHello` → `Welcome`: `LocalPlayer.id` сразу, снимок — обычным откатом (см. «Откат и повтор» выше) → `add<Gameplay>` → `Connected` в первом же кадре после догона. Если `snapshot_tick == server_tick` (кэша ещё не было, нечего проигрывать), догон не делает ни одного тика — локальному игроку тогда неоткуда получить `InputListener`/`CurrentActionListenerTag` до следующего тика, поэтому такой join сразу подчищается `EnsureLocalPlayerReady` (eager-эквивалент того, что `SyncLocalPlayerListener` сделала бы на следующем тике). `PlayerJoined`/`PlayerLeft` планируются по `apply_tick` (`ScheduledSessionDeltas`); до `Welcome` клиент их игнорирует, а сервер сразу после `Welcome` досылает всё новее снимка. Таймаут/отказ/битый снимок → `Failed(reason)`, `Gameplay` не добавляется.
- Выход: «Exit to Main Menu» (`remove<Gameplay>`) → система согласования гасит сессию (сервер рассылает disconnect, клиент закрывает соединение). Потеря сервера → клиент снимает `Gameplay` (главное меню) и показывает причину. Отключение клиента → `PlayerLeft`.
- Всё производное (локальный игрок, модели октаэдров, тела блоков) восстанавливается системами, а не `OnAdd`-обсерверами.
- **GUI/рендер (raylib_module).** Команды/статус — в `z13/components/net.h` (`StartServerRequest`, `JoinRequest`, `LeaveRequest`, `ConnectionStatus`), GUI net_module не знает. Два окна на существующем стеке `Window`: `StartServerWindow` (порт) и `JoinWindow` (host, порт, статус «Connecting…»/ошибка, Cancel), валидация — через `ParseEndpoint`. Октаэдр: один общий меш (без `Model` на сущность), рисуется для каждой `Player` + `Matrix4f` без `CurrentActionListenerTag`, цвет из `PlayerColor`.

## Порядок работ (одна ветка на этап)

Этапы тесно связаны (сессия без транспорта, команды без сессии и UI без сети бессмысленны), но каждый — самостоятельная, мержимая в `main` ветка: следующий этап начинается от `main` после того, как предыдущий смержен, а не веткой поверх ветки. Задумывалось в пределах нормы «≤ ~1000 строк на ветку» из CLAUDE.md; этапы 3 и 4 её превысили (~1750 и ~3000+). Тесты каждого этапа идут в той же ветке, что и код. Оценки грубые.

1. ✅ **`f/net-server-launch`** (~400): `--server[=PORT]`/`--connect` в `Config` (`kDefaultServerPort` в `constants.h`, валидация 1–65535), `Endpoint`/`ParseEndpoint`, второй конфиг модулей для сервера и выбор между ними в launcher, SIGINT, старт сразу в `Gameplay`, `ServerRole`/`ClientRole`. Без сети.
2. ✅ **`f/net-transport`** (~700): зависимость `enet` в `vcpkg.json` (+`overrides`, 1.3.18), `net_module` со скелетом, `Transport` + `EnetTransport` + `InMemoryTransport` (drop/reorder/delay/jitter для тестов), два канала (0 reliable, 1 unreliable), `net.fbs` + codec.
3. ✅ **`f/net-session`** (оценка ~700, по факту ~1750 — превышение лимита, см. ниже): handshake, id, join/leave (пока применяются сразу, без расписания), `JoinRequest` из bootstrap; рефакторинг спавна (`Player_<id>`, `SpawnPlayer`, `OnInit` по роли, `ActionListener` у каждого игрока через `EnsurePlayerActionListener`); `SaveEntityState`/`ApplyWorldStateDelta`; снимок в `Welcome` — кэш `WorldSnapshotHistory` + батч `PlayerActionLog`, доигрывается откатом (не свежий `CaptureState` на каждый join); `rollback.h` в `lib_core` (`RollbackRequest`/`ReplayInProgress`/`RollbackFailed` + `TickWorld`, см. «Откат и повтор»); расширение `Z13TestWorld` и `TestNetwork`. Перерасход — не разросшийся скоуп, а то, что откат-на-join и общая дисциплина работы с `progress()` оказались нужны уже здесь, не в этапе 4/5, как предполагалось изначально.
4. ✅ **`f/net-commands`** (оценка ~1000, по факту ~3000+, PR #69): `Ping`/`Pong` + оценка `clock_offset` (EWMA), `ScheduleTick`, `OutgoingCommands` + `NetActionSender`, `CommandSequencer`, `RemoteInput` (вынос из `Replay`), `SequencedCommands`, `held_values`/`pending` в `Welcome`, перевод `PlayerJoined/Left` на расписание. Сверх плана забрал у этапа 5 откат опоздавших команд и событий сессии (см. «Итоги этапа 4»).
- ✅ **`f/system-phases`** (отдельная ветка перед этапом 5): события-теги жизненного цикла заменены колбэками по этапам (`lib_core/lifecycle.h`: `OnRegisterComponents` → `OnInitPhases` → `OnInitSystems` → `OnInitWorldData`), которые `Core::CreateWorld` вызывает сам, без обсерверов и defer — лишний `OnUpdate` у систем больше не остаётся. Порядок фаз делается полным в `Core::CreateWorld` (`LinearizePhases`): топологическая сортировка объявленных `DependsOn` плюс порядок встроенных фаз (во flecs они не связаны друг с другом, и `PostFrame` выполнялся раньше физики), ничьи между независимыми фазами — по пути фазы, а не по id, так что Debug и Release совпадают, а модули (в том числе сторонние) не обязаны знать друг о друге. Затем каждая фаза висит только на своём якоре из цепочки якорей, как встроенные во flecs, — отключение фазы не останавливает остальные. Порядок закреплён `PhaseOrderTest`.
5. ✅ **`f/net-rollback`** (~800): `order_by<Player>` у систем постройки/сноса; `-ffp-contract=off` / `/fp:precise` на весь проект (Bullet из vcpkg — со своими флагами); `StateDigest` + `Resync` (`RollbackFailed` на клиенте после join → `Resync`); `RollbackMetrics` (число, последняя и максимальная глубина). `Resync` несёт тот же payload, что `Welcome` (кэш снимка + `actions`), и клиент применяет его тем же откатом, но журнал, историю снимков и очередь **заменяет** серверными, а часы назад не двигает. Пока клиент ждёт `Resync`, `NetActionSender` придерживает его ввод: по упорядоченному каналу 0 всё отправленное до `ResyncRequest` уже в ответе, так что серверная очередь полна без слияния. После ресинка придержанное уходит, сжатое на текущий тик (последнее значение каждого действия): ожидание не добавляет задержки ввода и не выводит команду за окно сервера. `Welcome`/`Resync` несут не последний снимок, а самый свежий старше `now − kMaxLateTicks` (иначе самый старый): опоздавшая команда, принятая сервером уже после ответа, не оставит клиента без снимка для отката. Расхождение никогда не завершает сессию — только потеря соединения или провал самого join.
6. ✅ **`f/net-ui`** (~750): диалоги Start Server/Join, «Connecting…»/Cancel и причина ошибки в главном меню, октаэдры, `PlayerColor`, камера только у локального игрока. `--server` и меню идут через `StartServerRequest`; роли ставит и снимает net_module (`EndSession`), выход в меню (`remove<Gameplay>`) закрывает сессию, закрытие транспорта шлёт пирам disconnect. Команды хоста идут тем же путём, что у клиента: `kInputDelayTicks` + `SequencedCommands` всем.
- **`f/net-instant-input`** (после плана, ~250 без тестов): своя команда применяется на тике записи (`OwnCommandsFramePhase`), `kInputDelayTicks`/`ScheduleTick` убраны, окна приёма и задержка событий сессии — свои константы, плавный догон часов клиента (`RequestExtraTick`). Коалесцирование откатов и частые снимки — следующей веткой.
- **`f/pause-vs-simulation`** (после плана): `Pause` больше не останавливает симуляцию в сети, заморозка мира в одиночной игре — одно решение на уровне фаз. См. «Пауза и симуляция».
- **`f/net-live-clock`** (после плана, по итогам живого прогона `--server` + `--connect`): см. «Живой прогон».
- **`f/render-throttle`** (после плана): догоняющие тики не рисуются. `TickWorld` перед каждым `progress()` сообщает подписчикам `OnFrameStart` вид кадра (`FrameKind`): `kLive`; `kCatchUp`, если `Core::Run` отстаёт от стенных часов или это лишний тик `ClockAdjustRequest`; `kReplay`, если это повтор после отката. Что с этим делать, решает модуль рендера: он выключает свои фазы `PreRender`…`FinalizeRender` на `kReplay` и на `kCatchUp`, но на `kCatchUp` не больше `kMaxSkippedFrames` подряд. `ImGui::NewFrame` перенесён в `PreRender`, события в ImGui по-прежнему передаются каждый тик. Последний кадр повтора (на текущем тике) получает вид кадра вызывающего и рисуется; кадр, в котором откат уже запрошен к моменту рендера, не рисуется (`RenderGate`, tick source всех рендер-систем, выставляется в `RenderGatePhase` перед `PreRender`) — за один `TickWorld` с откатом на экран попадает один кадр с уже исправленным состоянием, без задержки на кадр.
- **`f/net-config`** (после плана): настройки живут в `settings.json` в каталоге данных игры, рядом с конфигом биндингов (`z13_settings/environment.h`, `GetGameSettingsJsonPath()`); нет файла — лаунчер создаёт его из значений по умолчанию схемы (все поля записаны), битый файл — ошибка запуска, а не перезапись. Схемы и рантайм-типы без дублирующих структур — сгенерированные `*T` (`--gen-compare`): `lib_core` владеет собственной `fbs/core_settings.fbs` (`CoreSettings`: fps, интервал/срок хранения снимков, пороги pacer и отката; синглтон мира `ActiveCoreSettings`) и ничего не знает про схемы и окружение z13; `schemas/fbs/settings.fbs` (корень `Settings { core, connect_timeout, net }`, `net_tuning.fbs`) и библиотека `z13_settings` (`Settings`, `NetTuning`, валидация, каталог данных, `InstallSettings`) лежат в `lib_z13`. Вложенные таблицы — `unique_ptr`, их гарантирует `MakeSettings()`. Лаунчер кладёт `core` в `Config::SetCoreSettings` до создания мира, а после — `NetTuning`/`ConnectTimeout` синглтонами (`InstallSettings`). Поля схем несут атрибуты (`lib_core/fbs/attributes.fbs`, читаются из бинарной схемы универсально, `lib_core/schema_attributes.h`): `(min: 1, max: 1000)` — границы скаляра, проверяются `ValidateRanges` для любой таблицы, вложенные обходятся рекурсивно; `(cli)` / `(cli: "-f,--fps")` — опция командной строки (как в argparse: длинная и необязательная однобуквенная форма; без значения длинное имя берётся из поля, `max_late_ticks` → `--max-late-ticks`), `--help` показывает путь поля, значение по умолчанию и диапазон. Приоритет: умолчания схемы < `settings.json` < командная строка; значения с CLI проходят ту же проверку. Опции регистрирует приложение (`Core(argc, argv, configure)` вызывает хук до разбора, лаунчер — `AddSettingsOptions`), `lib_core` схем не знает; совпадение имени с существующей опцией — ошибка. Остаются кодом только условия между полями: `clock_jump_threshold_ticks` ≥ `clock_catch_up_threshold_ticks`, `max_timeout_ms` ≥ `min_timeout_ms` и срок хранения снимков не короче `max_late_ticks` + интервал. **Клиент живёт на настройках сервера:** `Welcome` несёт `fps` и `NetTuning`, клиент проверяет их вместе со своим сроком хранения (не подходят — `Failed`, ничего не применено) и включает (`Config::OverrideFps`, синглтон `NetTuning`); `Core::Run` пересоздаёт `TickPacer` при смене fps или `max_tick_backlog`; `EndSession` возвращает собственные значения. Остальное (снимки, пороги pacer/отката, таймаут соединения) — локальное. `kProtocolVersion` = 2.

Каждая ветка начинается только после того, как предыдущая смержена в `main` — так следующая сессия перечитывает актуальный `main` и план, а не держит в контексте весь путь с начала.

## Тесты

Единая инфраструктура: `Z13TestWorld` принимает доп. аргументы командной строки и транспорт; `TestNetwork` гоняет N миров и сервисы транспорта до условия или лимита тиков (без `sleep`). Основная масса — на `InMemoryTransport` (детерминированно, drop/reorder/delay/jitter с фиксированным seed), плюс отдельный набор на реальном ENet через loopback.

**Config/launcher (1).**
- Значения по умолчанию (`server=false`, порт 26213, `connect` пуст); `--server`; `--server 30000`; невалидный порт (`0`, `70000`, `abc`) → ошибка; `--help` содержит опции.
- `--connect host`, `--connect host:port`, `--connect :80`, `--connect host:0` → корректный разбор/ошибка; `--server` + `--connect` → ошибка.
- `ParseEndpoint`: IP, hostname, пустое, порт вне диапазона.
- `ParseModuleList`: скаляр и `path:`-запись читаются одинаково, битая запись пропускается (не фатально), отсутствие `modules:`/битый YAML → ошибка.
- Сервер-мир стартует с `Gameplay`, без `Pause`, игрок id 0 есть.

**Codec (2).** Round-trip каждого сообщения; квантование значений действий (`ActionQuantizationTest`: ошибка ≤ 1/`kActionValueScale`, булевы точно, медленная мышь не теряется); несовпадение версии; усечённые/мусорные/пустые байты отвергаются `Verifier`, без крэша (табличный тест); `tick_delta` не переполняется при максимальном интервале отправки.

**Транспорт (2), реальный ENet, порт эфемерный.** Connect + обмен reliable в обе стороны; корректный disconnect и событие на второй стороне; соединение на закрытый порт → ошибка за ограниченное время; порт занят → ошибка старта; сверх `kMaxClients` → отказ; RAII: создание/уничтожение хоста N раз без утечек дескрипторов.

**Сессия (3), сервер + клиенты на in-memory транспорте.**
- Снимок: блоки, построенные на сервере до подключения, есть на клиенте; `IdCounters` и `SimulationClock.tick` совпадают.
- Id: три клиента получают {1,2,3}, сервер = 0; id не переиспользуется после выхода и переподключения.
- У клиента ровно один локальный игрок (`CurrentActionListenerTag`), его id = выданному; у чужих нет `InputListener`; лишнего игрока `OnInit` не создал; клиент не трогает `IdCounters` при join.
- Имена сущностей уникальны, игроки не сливаются при `RestoreWorld`.
- `PlayerJoined` у уже подключённых; `PlayerLeft` → сущность удалена на сервере и у остальных.
- `--connect`: bootstrap выдаёт `JoinRequest`, меню остаётся до результата; провал → главное меню с причиной.
- Потеря сервера / `remove<Gameplay>` на сервере → клиент теряет `Gameplay`, `ConnectionStatus` = Disconnected с причиной.
- `Rejected` при другой `kProtocolVersion`; битый снимок → `Failed`, сцена не создана; мусорный пакет от клиента → пир отброшен, сервер жив.
- Большой снимок (≈5000 блоков) доезжает целым.
- (Сверх исходного списка, добавлено по ходу этапа 3) Три клиента подключаются одновременно: у каждого корректный набор игроков, включая тех, кто присоединился позже — потребовало придержать `PlayerJoined`/`PlayerLeft`, пришедшие во время догона, в `PendingSessionDeltas`, иначе более поздняя дельта терялась под откатом на старый снимок (см. «Откат и повтор»).
- (Сверх исходного списка) Движение хоста после кэшированного снепшота, но до подключения клиента — воспроизводится клиенту повтором из батча действий, а не остаётся «замороженным» на момент кэша.
- (Сверх исходного списка) Несколько `RequestRollback` за один кадр коалесятся в один запрос: самый ранний `to_tick`, самый поздний `target_tick`.
- (Сверх исходного списка, по итогам ревью) Клиент, подключающийся к серверу старше одного интервала снимков, получает собственную сущность игрока: `Welcome` несёт кэш **до** его спавна, поэтому сам спавн приезжает к нему тем же `PlayerJoined`, что и остальным. До этого теста весь набор зеленел по ложной причине — `ConnectionStatus` ездил в снимке (вложенный `enum class State` подходил под маркер state-компонента `T::State`), и клиент наследовал `kConnected` от сервера.

**Последовательность команд (4).**
- **Пинг:** `Ping`/`Pong` round-trip на codec-уровне; при фиксированной задержке `InMemoryTransport` оценка `clock_offset` сходится к истинному значению за несколько секунд; при seeded-jitter сглаженная оценка не скачет вслед за одним всплеском; потерянный `Ping` не рвёт цикл — следующий через секунду доходит и оценка продолжается; `Ping` идёт по каналу 1 и не блокируется очередью `CommandBatch` на канале 0 (тест с насыщенным каналом 0).
- **Расписание:** `apply_tick` своей команды — тик её записи; порядок внутри тика одинаков у всех участников при любом порядке прибытия пакетов; сервер отбрасывает `apply_tick` вне окна `[now − kMaxLateTicks, now + kMaxScheduleAheadTicks]` и не падает. Догон часов — `ClockSyncTest` (без скачков больше тика за кадр).
- **Нет эха:** сервер не шлёт отправителю его собственные команды (тест на счётчик сообщений), при этом мир отправителя сходится с остальными.
- **Опоздавшая вверх команда** (транспорт задерживает клиент → сервер): сервер откатывается, применяет команду на её тике и рассылает остальным; итоговое состояние равно контрольному миру, где команда пришла вовремя; `Resync` не понадобился (`LateCommandsAndJoinsStillConvergeUnderHighLatency`). С `f/net-instant-input` опаздывает каждая чужая команда — это обычный путь.
- **Главный инвариант:** сервер + 2 клиента, скриптованный сеанс (движение, взгляд, постройка, снос, поздний join, выход игрока); на каждом контрольном тике полный `WorldJsonStore::Save` у всех трёх миров совпадает (паттерн `ForwardOnlyRunIsDeterministicAcrossIndependentWorlds`).
- Локальная команда клиента двигает его мир на том же тике, на котором нажата (`LocalCommandMovesTheClientOnTheTickItIsPressed`).
- Длительность удержания сохраняется при seeded-jitter ±2 тика; постоянная задержка не меняет результат.
- Одновременная постройка двумя клиентами на одном тике: одинаковые имена и позиции блоков на всех независимо от порядка прибытия пакетов; все блоки на месте.
- Поздний join посреди удержания клавиши: по `held_values` + `pending` мир клиента сходится с серверным на тике `J + k`.
- `PlayerLeft`: запланированные команды ушедшего исполнены у всех до удаления сущности.
- Трафик: простаивающий клиент не шлёт ничего, кроме keepalive ENet; удержание W = 2 записи + переутверждение раз в секунду. Пик полезной нагрузки (мышь, 2 действия на тик) — ~1,8 КБ/с, бюджет 2560 Б/с, простой — 64 Б/с (константы `UplinkBudgetTest`).
- Защита: неизвестный `action_id` отброшен; превышение лимита — отброшено; `CommandBatch` до `Welcome` игнорируется; батч от A меняет только `Player_A`.
- `PlayerActionLog` у всех участников содержит одинаковый набор применённых команд с `player_id` (совместимость с `Replay`); в режиме `None` поведение и все существующие тесты `Replay`/`PlayerActionLog` без изменений.

**Детерминизм и рассинхрон (5).**
- Порядок обработки по `player_id`: результат не зависит от порядка создания сущностей игроков (тест с перестановкой).
- `StateDigest` совпадает после скриптованного сеанса; принудительное расхождение (правка блока на клиенте / выброшенная команда) → обнаружено за интервал дайджеста → `Resync` → состояние снова равно серверному.
- `Resync` сохраняет `LocalPlayer.id`, `Gameplay` и не дублирует сущности.
- Опоздавшая на клиенте чужая команда и откат через тик `PlayerJoined/Left` — сделано в этапе 4 (`LateCommandsAndJoinsStillConvergeUnderHighLatency`); коалесцирование нескольких откатов за кадр — в этапе 3.
- Во время повтора клиент не шлёт команд повторно (счётчик исходящих сообщений); рекордер не дублирует записи.
- Команда старше окна журнала (`RollbackFailed`) → `Resync`, мир сходится с сервером.

**ENet e2e (3–5).** Один сервер-мир + один-два клиента через loopback: join, id, снимок, движение, постройка блока с совпадением состояния. Суиты именуются `NetEnet*`, чтобы их можно было отфильтровать.

**Чистые функции (6).** `PlayerColor` — стабильность и уникальность на первых 256 id, различимость (минимальная дистанция в HSV/RGB).

**Вручную (GUI/GL юнит-тестами не покрыть).** Выделенный сервер + 2 клиента на localhost (в том числе через `--connect`): октаэдры разных цветов, двигаются; постройка блока одним клиентом видна другому; выход клиента убирает октаэдр; остановка сервера возвращает клиента в меню с сообщением; listen-server из меню. Чек-лист — в описании ПР.

**CI.** `pr_tests.yml` собирает только `z13_test_runner` — enet должен собраться на x64-windows/x64-linux/arm64-linux; тесты используют только loopback.

## Итоги этапа 4

Смержен в `main` (PR #69). Отличия от исходного плана и то, что стоит помнить дальше:

- **Намерение и применённое разделены.** `RecordChangedActions` пишет в `OutgoingCommands`; вне клиента `ApplyOwnCommands` перекладывает их в `PlayerActionLog`, на клиенте `NetActionSender` шлёт `CommandBatch` и сам ставит ту же команду в `ScheduledCommands`. (С `f/net-resync-wait` одна `ApplyOwnCommands` применяет свою запись в её тик во всех ролях, `NetActionSender` только шлёт.) `RecordChangedActions` сравнивает со своим `LastRecordedActionValues`, а не с `ActionListener.prev_value`, который каждый тик переписывает инжект.
- **`Replay` обобщён на живые тики.** `ReplayActionState` → `RemoteActionState`; `AdvanceRecordedValues`/`InjectRecordedActionValues` работают каждый тик, не только под `ReplayInProgress`. Инжект проходит по всем `action_id` из `ActionMap`, обнуляя отсутствующие, — иначе впервые нажатое действие утекало в `Apply` на клиенте на один кадр.
- **Новые фазы** (полный порядок кадра — см. `f/system-phases`), закреплены `PhaseOrderTest`: `PreFrame` → `ScheduledCommandsPhase` → `ClearActionFramePhase` → … → `CalculateActionFramePhase` → `RecordActionFramePhase` → `RemoteActionFramePhase` → `ApplyActionFramePhase` → `PostUpdate` → … → `PostFrame`.
- **Откат опоздавших (забран у этапа 5).** Тик команды никто не сдвигает: сервер принимает его в окне `[now − kMaxLateTicks, now + kMaxScheduleAheadTicks]` или отбрасывает. (С `f/net-late-commands` не отбрасывает, а переносит на ближний край окна: опоздавшую — на самый ранний тик, с которого ещё можно откатиться, слишком раннюю — на `now + max_schedule_ahead_ticks`. Перенесённая не встаёт на тик предыдущей команды того же действия и раньше него, иначе одна скрыла бы другую; отправитель получает `CommandsRetimed` и переносит свою запись так же.) `CommitDueCommands` и `ApplyDueSessionDeltas` вставляют опоздавшее на своё место и зовут `RequestRollback`; `ScheduledSessionDeltas.history` переигрывает join/leave при откате. Сервер держит базовый снимок с первого кадра (`EnsureBaselineSnapshot`).
- **Join/leave** планируются через `kSessionEventDelayTicks` на всех, включая сервер; id выдаёт рантайм-`PlayerIdAllocator`, чтобы откат не выдал id повторно. `held_values` — свёртка журнала на тик снимка.
- **Защита сервера:** неизвестный `action_id` отбрасывается поштучно, лимит частоты — `CommandRateLimits` (скользящее окно).
- **Методика:** главный инвариант (полный `WorldJsonStore::Save` клиента против сервера) ловит баги, которые не видят тесты «клиент B видит клиента A». Для этапа 5 писать такой тест до правки, а не после.

## Пауза и симуляция

**Проблема (найдена вручную на listen-сервере).** Потеря фокуса окна ставит `Pause`, а `ApplyMoveActionListener`, `ApplyBuildActionListener` и системы кисти были зарегистрированы с `.without<Pause>()`. Хост, переключившийся на окно клиента, переставал двигать **всех** игроков, в том числе клиентского, по уже пришедшим командам; раз в секунду `StateDigest` расходился, клиент получал `Resync` и телепортировался в серверную (отставшую) позицию. Откаты тут ни при чём — они сходятся (`OwnCameraMovesSmoothlyThroughRollbacks`). При этом часы (`IncrementTick` в `PreFrame`) и Bullet на `Pause` не смотрели, так что и в одиночной игре пауза была лишь частичной.

**Решение: «меню открыто» и «мир заморожен» — разные вещи.**
- `Pause` — только «UI открыт, локальный ввод нейтрален». Симуляционные системы её не проверяют. На паузе `CalculateInputValues` ничего не добавляет (значения уже обнулены фазой Clear), дельта мыши не копится (`OnMouseMove` в `ReadEvents` фильтрует `Pause` — иначе движения над меню разом повернули бы камеру после паузы), а рекордер продолжает работать — так удерживаемая при нажатии Esc клавиша записывается как отпущенная и уходит остальным, а не «залипает».
- Заморозка — runtime-синглтон `SimulationFrozen` (`lib_core/simulation_clock.h`), который выводит `GameplaySystem::SyncSimulationFrozen` из `Pause` без `ServerRole`/`ClientRole` (в сети мир не замораживается никогда). `TickWorld` между кадрами (`ApplySimulationFreeze`) отключает все фазы, **не** помеченные `PresentationPhase`; `LinearizePhases` уже вешает каждую фазу на свой якорь, так что отключение одних не останавливает другие. Презентационные: `PreFrame` (сеть, запросы save/load, сама синхронизация заморозки — иначе мир не разморозится) и фазы raylib (`ReadEvents`, `ConsumeEvents`, `PreRender`…`FinalizeRender`). Всё остальное — симуляция по умолчанию: новая фаза модуля, про которую забыли, замёрзнет вместе с миром, а не разойдётся с ним.
- `SimulationClock::IncrementTick` вынесен из `PreFrame` в собственную `SimulationTickPhase` **перед** `PreFrame` (порядок «тик → обслуживание сети» прежний), иначе часы, снимки и окна журнала шли бы и на заморозке.
- Задержка — один кадр: маркер выставляется в `PreFrame` кадра N, применяется перед кадром N+1 (на кадре N ввод уже нейтрален, так что лишний тик ничего не двигает).

**Тесты.** `PausedPeerTest`: хост на паузе продолжает симулировать клиента и наоборот — ни одного `Resync` за несколько сверок дайджеста, виды совпадают; Esc с зажатым W останавливает игрока у всех. `PauseTest`: в одиночной игре на паузе не растут ни тик, ни позиция, после снятия — растут. `PhaseOrderTest`: `SimulationTick` идёт первым.

## Живой прогон

- **Отставание часов.** Опоздания команд на 10–24 тика воспроизводились искусственно замедленным клиентом (~46 кадров/с): старый `Core::Run` терял время медленных кадров, тики клиента шли медленнее реального времени, а пинг раз в секунду поправлял часы с запаздыванием. Теперь `Core::Run` ведёт тики по стенным часам (`TickPacer`): медленный кадр добирается следующими тиками подряд, отставание больше `kMaxTickBacklog` считается фризом и отбрасывается. Опережение сервера над тем же замедленным клиентом — 2–3 тика (было 7–28), в простое на loopback — те же 2–3 (путь плюс сброс очереди ENet на следующем кадре). Оценка `clock_offset` сама по себе была верна.
- **Quick save/load в сессии.** F9 клиента уходил командой, и **выделенный сервер загружал свой quick save**: часы сервера уходили назад, команды выпадали из окна, клиент замирал, пропуская кадры до новых часов (в тестовом мире — бесконечный цикл перезагрузок). Quick save/load теперь только у локального игрока в одиночной игре (`QuickSaveInSessionTest`).
- **Занятый порт** у `--server` завершает процесс с кодом 1 (`Core::Shutdown(exit_code)`).
- **Плагины на Linux.** Overlay-триплеты `triplets/{x64,arm64}-linux.cmake` собирают flecs динамически (остальное статично). `z13_plugin_smoke` (ctest `PluginSmoke`) грузит серверные плагины через `boost::dll` в один мир, как лаунчер (`z13_test_runner` линкует те же `.so`/`.dll` напрямую, статических двойников модулей больше нет).

## Технический долг

- **`AssetSourceTest` мешал сам себе при параллельном ctest** — решено (`f/asset-source-test-dirs`). Было: три теста писали в одну папку, и уборка одного падала на файлах другого (`remove_all: Access is denied` в CI). Теперь у каждого теста своя папка по его имени, как в `file_io_test`.
- **`SendWelcome` без кэша снимка** (свежий захват в `PreFrame`) отстаёт на кадр. С базовым снимком практически недостижим.
- **Стоимость откатов** (`f/net-rollback-cost`). Опоздавшие команды откатываются пачкой (`DeferRollback`: до `kMaxDeferredRollbacks` запросов или `kMaxRollbackDelayTicks` после первого), в сетевых ролях снимков 4 на интервал. Два клиента, жмущие W через тик 2 с: 65 откатов глубиной до 65 тиков → 15 глубиной до 26. Замер (Debug, ARM, 100 блоков): тик ≈1,3 мс, `CaptureState` ≈3,9 мс, `RestoreWorld` ≈3,6 мс. Осталось: dirty-tracking снимков, если этого окажется мало на живой сети.
- **Ручная проверка с вводом.** `--server` + `--connect` прогнан (join, пинг, часы); движение/постройка двумя живыми клиентами и listen-server из меню — по чек-листу вручную.
- **Миграция на модули C++20** — отложена: flecs не даёт довести её до конца (ветка `f/cpp-modules`; пилот лежит в `git stash`, «cpp-modules pilot»). Прошлая попытка (`37725d9`, откат `d396c47`) упиралась в `lib_ogre_module`; Ogre заменён raylib. Пилот на MSVC 19.51 / CMake 4.4 / VS-генератор: `tick_pacer`, `endpoint`, `phase_order`, `world_state_requests` стали модулями, 286 тестов зелёные; интерфейс — типы и объявления, тела — в implementation unit, шаблонный код остаётся в заголовках. Что выяснено: (1) **блокер — C1116** при импорте flecs-модулей: если интерфейс модуля включает `flecs.h`, TU, импортирующая два таких модуля, падает с «специализация `flecs::world::entity` с аргументами `entity_t`» (в проекте триггером был `flecs::world world = it.world();` в системе после include'ов); минимальный репро — `#include <flecs.h>` + `import` одного flecs-модуля + пустой `main`; импорт до include'ов не помогает (ломаются заголовки STL, C2572). Почти весь `lib_core` и компоненты завязаны на flecs, так что модулями остались бы только листовые части без flecs (`endpoint`, `tick_pacer`, `config`) — выгоды нет. - **Непрерывные оси (мышь) — в неподтверждаемый канал.** Сейчас все команды идут по reliable-каналу 0: потеря пакета задерживает все последующие (head-of-line blocking), а сервер ретранслирует каждую дельту мыши всем остальным, так что трафик сервера растёт квадратично с числом игроков. Оси слать по unreliable с избыточностью (последние K значений в каждом пакете), дискретные действия (нажатия, постройка) оставить reliable. Серверная последовательность при этом остаётся единственным источником истины: сервер сам решает, что применено на тике, и порядок для клиентов должен сохраниться (unreliable с избыточностью и дозапросом пропуска либо reliable в обратную сторону). Связано с бюджетом трафика (`UplinkBudgetTest`). Ожидается ~200 игроков, а сервер — микрокомпьютер: буферы повторов и ACK на каждый пакет мыши каждого пира ему не по силам. Но и без надёжности ретрансляция всех осей всем — квадратичная: 200 игроков с мышью по ~1,8 КБ/с дают ~363 КБ/с входа и ~72 МБ/с выхода (без заголовков). Значит, кроме канала нужно сократить, что ретранслируется: чужим клиентам — не каждую дельту, а реже и/или только видимым (интерес-менеджмент), что затрагивает модель «весь мир у всех» и детерминированный повтор чужих команд. - **Клиента выкидывает сразу после входа, экран не рисуется** — решено (`f/net-clock-jump`). Было: пока сервер ~20 с строил станцию, вошедший клиент ждал `Welcome`, а его часы шли (замораживался только одиночный режим) и уходили до тика ~900; снимок сервера на тике 3 к приходу был уже за пределами истории (5 с), и первый же откат падал с `no retained snapshot that old` — сессия рвалась, сцены нет. То же у клиента с `--connect`. Теперь клиент без сцены заморожен (`SyncSimulationFrozen`), заморозка применяется перед каждым кадром, а не раз за `TickWorld`, и снимается при `Welcome` (`ListenServerTest.AJoinAnsweredAfterTheSnapshotHistoryLands`).
- **Сервер открывает порт до постройки станции** — решено (`f/net-clock-jump`). Было: хост и `--server` слушали порт сразу и потом ~20 с (Debug, `spire`) строили станцию, никого не обслуживая; клиент, пришедший в эти секунды, через 3 с получал «disconnected before joining». Теперь при старте порт только проверяется (занятый — ошибка сразу, без сцены), а слушать сервер начинает тиком позже постройки (`ServerRole::listen_after_tick`, `ListenServerTest.TheServerListensOnlyOnceItsSceneIsBuilt`); строка `listening on port` значит, что сервер уже отвечает. `InMemoryNetwork` теперь, как ENet, повторяет попытку подключения секунду (`kInMemoryConnectAttemptTicks`).
- **Долгий повтор после входа** — решено (`f/join-replay-cost`). Было: на `spire` после входа ~20 с неподвижная картинка без признаков загрузки, и казалось, что повтор идёт ~94 мс на тик. Замер (Windows, Debug, `StationSessionTest.DISABLED_TheJoinReplayCost`): кадр входа 12,1 с, из них `RoomSystem::UpdateRooms` 10,6 с (разовая полная сборка комнат после `RestoreWorld`: станции у клиента до снимка нет), `SyncBlockBodies` 0,42 с, `SyncBlockIndex` 0,12 с; обычный откат на 90 тиков после входа — ~400 мс (≈4,4 мс на тик, ровно между `StateDigest::Record`, `StepPhysicsWorld` и снимком). Повтор не медленный; «94 мс на тик» — эта сборка, поделённая на 97 тиков. Теперь: запуск игры, запуск сервера, выход в меню и вход клиента показывают экран «Loading…» (`PendingTransition`: действие ждёт, пока кадр с плашкой выведен на экран; `gui/loading_screen.h`). Осталось: сама сборка комнат (10,6 с в Debug) — перемерить после `f/oblique-rooms`, который меняет герметичность; вынести загрузку и выгрузку в фон (мир заморожен, `BuildRooms` считается в потоке) — отдельной веткой.
- **Пинг посреди прыжка даёт ложное смещение** — решено (`f/clock-catch-up-and-session-logs`, запись о долге устарела: `ClockSync::applied_at_ping` и `ClockAdjustRequest::applied` вычитают прогнанные тики из пути, оставшиеся тики прибавляются к часам; тест `APongDuringAJumpCountsTheTicksStillToRun`). Было: Клиент, отстающий на ~1200 тиков, во время прыжка получил ответ на пинг со смещением −31 и прыгнул на 31 тик назад (2026-10-17, `spire`): `ApplyPong` считает часы с ещё не прогнанными тиками прыжка, а время пути — за вычетом прогнанных, и при прыжке длиннее кадра (`max_catch_up_ticks_per_frame`) счёт расходится. Игрок этого почти не видит (тики прыжка не рисуются), но лишние откаты и переносы команд остаются. Часть Н5 в [net-core.md](net-core.md).
- **Чёрный экран после неудачного входа** — решено (`f/failed-join-menu`). Было: сессия рвалась после `Welcome` (например, `RollbackFailed` в `FinishPendingJoin`), `FailSession` убирал роль, но `Gameplay` из `JoinFromWelcome` оставался, и клиент сидел «в игре» без сцены. Теперь `FailJoin` (`client_session.cpp`) снимает `Gameplay` и ставит `Pause`: показывается главное меню с причиной, как при отказе до входа.
- **Перенесённая команда и дайджесты** — решено (`f/retimed-digests`). Было: дайджест тика T сервер шлёт, когда T вышел из окна опоздания, — раньше, чем до него дойдёт своя команда клиента, застрявшая на отправке; клиент сравнивал дайджест до `CommandsRetimed` и уходил в ресинк. Теперь дайджест несёт `input_through` — по каждому игроку тик, до которого сервер получил весь его ввод к моменту отправки, и клиент не сравнивает дайджест, пока в его журнале есть своя команда не позже тика дайджеста, которой сервер к отправке ещё не подтвердил (иначе перенос его команд уже пришёл раньше дайджеста по тому же каналу). Простаивающий клиент команд не шлёт и подтверждения не продвигает, но и неподтверждённых команд у него нет — он сверяет каждый дайджест. Остаётся предел: если отправка застряла дольше истории снимков за вычетом окна (~3,4 с при 5 с истории и окне 96 тиков), откатиться к исходному тику команды не к чему (`RollbackFailed`) — это ресинк, ввод при нём сохраняется (`AdoptCatchUp`).
- **Лимит частоты команд отбрасывал ввод** — решено (`f/command-rate-budget`). Был `CommandRateLimits`: 128 команд на 60 тиков, а мышь даёт до 2 команд на тик, и пачка, накопленная за подвисание сети, теряла остаток. Теперь у соединения бюджет: пополняется на число действий `ActionMap` за тик (клиент записывает не больше одной команды на действие за тик, `RecordChangedActions`) и копит до этого числа × (`max_late_ticks` + `max_schedule_ahead_ticks`) — столько ввода клиент законно приносит после подвисания. Отбрасывается только то, чего честный клиент не пришлёт; настройки `command_rate_limit_window_ticks` и `max_commands_per_rate_limit_window` убраны (`kProtocolVersion` 10).
- **Короткое нажатие в одном кадре терялось** — решено (`f/input-taps`). События клавиатуры и мыши сразу писали в `InputState` «нажата / нет», а действия считаются раз в кадр: нажатие и отпускание, пришедшие в одном кадре (длинный кадр при постройке, низкий fps в сети), не давали ни одной записи — клик мышью при постройке на отпускание не строил блок. Теперь события копятся в `InputState::pending` и применяются по одному переходу на клавишу за тик (`ApplyKeyTransitions`): нажатие — тик t, отпускание — t + 1, двойное нажатие — четыре тика; автоповтор зажатой клавиши тика не занимает.
- **Схемы FlatBuffers — рядом с модулем, который их использует** — решено (`f/schemas-by-module`). Было: все схемы `lib_z13` лежали в `src/lib_z13/schemas/fbs/`. Теперь схема с одним владельцем лежит у него и генерируется его `CMakeLists` через `z13_generate_schemas` (`cmake/z13_schemas.cmake`): `net` и `discovery` — в `modules/net_module/fbs/`, `blueprint` и `decor` — в `primitives/fbs/`, `building` — в `modules/building_module/fbs/`. В общем месте остались схемы, которыми пользуются несколько библиотек: `common`, `geometry`, `actions`, `input_config`, `primitives` (его берёт и `components`), `building_tuning`, `net_tuning`, `physics_tuning`, `settings`.
- **Ревизия тестов по времени.** Полный ctest в Debug в PRoot идёт ~10 мин (~690 активных тестов), заметную долю дают медленные группы (`RandomRoomEditsTest` — ~9 с на зерно); весь код тестов — в одном `z13_test_runner`, так что правка широкого заголовка пересобирает и его. Порядок: снять длительности всех тестов из ctest и взять 20–30 самых медленных; сначала дешёвые меры без потери покрытия — меньше зёрен или сцены меньше, меньше тиков ожидания, метка `slow` (локально пропускаются, в CI идут все); дубликаты удалять, только если для каждого удаляемого теста ясно, какой оставшийся ловит тот же сбой (тест, воспроизводящий исправленную ошибку, — не дубликат); цифры до и после — сюда. Стоит ли игра свеч, решает первый шаг: если время размазано ровно, ревизия даст мало. Первый замер (Debug, PRoot, `f/retimed-digests`, ctest последовательно): 365 с на 692 теста, из них сами тесты — 276 с; медиана 0,24 с, 413 тестов короче 0,3 с и вместе дают 89 с — это в основном запуск процесса `z13_test_runner` на каждый тест (`gtest_discover_tests`). Десять самых медленных — 69 с (`NetSessionTest.LargeSnapshotArrivesWhole` 14,6 с, три зерна `RandomRoomEditsTest` по ~10 с, `ChunkMeshTest.ChunksOfAShippedStationHoldEveryBlock` 5,4 с), тридцать — 98 с. Значит, удалением тестов много не выиграть; больше даст параллельный ctest локально (в CI уже `--parallel 4`; в PRoot — с ограничением, как сборка; `EnetTransportTest` открывает настоящие порты — проверить, что параллельные прогоны их не делят) и укорачивание десятка медленных. Параллельный ctest сделан (`f/parallel-tests`): скрипты передают `--parallel` (3 в PRoot, как у сборки), `EnetTransportTest` — отдельно с `RUN_SERIAL`; тот же набор — 101 с вместо 365. Осталось укоротить медленные. Укорочены (`f/faster-tests`, Debug, PRoot, без конкуренции): `NetSessionTest.LargeSnapshotArrivesWhole` 15,1 → 1,1 с (1000 блоков вместо 5000: транспорт в памяти не дробит сообщения, «большой» — это много сущностей, а не порог размера). `RandomRoomEditsTest` на пуле стал медленнее (9–10 → 16–17 с на зерно: на маленькой сцене раздача мелкой работы дороже её самой) — оставлен последовательным; см. долг «Пул на мелкой работе». `CommandStreamTest.LateJoinMidHoldSeesTheHeldMovement` (5,6 с) задан интервалом снимков и окном опоздания — не тронут. Весь ctest после этого (Debug, PRoot, `--parallel 3`, 730 тестов): сумма длительностей 289 → 216 с, прогон 103 с; самые долгие теперь — три зерна `RandomRoomEditsTest` (~10 с) и `RoomParallelTest` (8,6 с: две полные сборки каждой станции, «Шпиль» тоже).
- **Пул на мелкой работе** — решено (`f/pool-threshold`). Было: после `f/rooms-parallel` правка станции (постройка, снос) тоже идёт через `ThreadPool`, без порога: на маленькой сцене `RandomRoomEditsTest` с пулом медленнее вдвое (Debug), а `ThreadPoolBench` показывает, что вызов на десятки микросекунд работы быстрее без пула. Замерить `RoomEditBench` (правка стены) последовательно и на пуле, Debug и Release; ввести порог — мелкую работу вызывающий делает сам (число индексов или оценка работы), в настройке или по замеру. Теперь: `ThreadPool` раздаёт цикл, только если в нём не меньше `min_parallel_count` индексов (настройка ядра, 64), иначе делает его сам; правка стены на «Шпиле» с порогом — как в одном потоке, на тестовой станции 70 → 66 мс (без порога было +5…36 %). `RoomParallelTest` собирает только тестовую станцию.
- **Сервер на телефоне.** Кроме микрокомпьютера, выделенный сервер должен по возможности работать на телефоне. В PRoot под Termux он уже собирается как `arm64-linux` (так идёт разработка), но под нагрузкой там не проверялся. APK нет: нужны Android NDK, триплет vcpkg `arm64-android` (с теми же общими библиотеками, что в `triplets/`), сборка без `raylib_module`, загрузка плагинов `boost::dll` из каталога приложения и запуск сервера без окна (фоновый сервис, чтобы система не убила процесс). Бюджеты — по замерам [network-scaling-plan.md](network-scaling-plan.md) и [dynamic-objects-plan.md](dynamic-objects-plan.md), с учётом троттлинга телефона при нагреве. Сборка под Android в целом — [android-plan.md](android-plan.md), этот долг — его этап `f/android-server`.
- **Освещение станции после `f/block-textures`.** (1) Запечённый свет (`cell_light`) даёт размытые прямоугольники под лампами: узлы 4×4×4 клетки, а между ними интерполяция; видно на гладких стенах. (2) Блики стен берутся из направления запечённого света (`sheen` в `CellLight`), а не от самих ламп: блик плавает и не повторяет форму лампы; `kShininess` и `kMetalSpecular` подобраны на глаз. (3) Блоки `Lamp` рисуются шахматкой из двух близких цветов: под лампой видна сетка. (4) Теневые карты солнца и fill накрывают всю станцию, около 5 см на пиксель при 4096; смещение глубины теперь 0,08 м (`kDirectionalBiasM`) и должно оставаться ниже толщины стены 0,25 м, а на ещё больших станциях карту придётся делить на части. (5) Тайлы текстур 256 px на метр, цвета почти белые; PBR-карт (шероховатость, металличность) нет, блеск везде одинаковый.
- **Отладочные режимы света (F11/F12)** — оставлены на время работы над освещением: `render/debug_view.*`, `debugView` в `lighting.fs`, строка `Light view` в оверлее F3. Убрать или оставить за флагом, когда свет станет стабильным.

## Риски и заметки

- **Ресинк в одном потоке.** Приём `Resync` (разбор снимка, `RestoreWorld`, повтор тиков) и сборка `MakeCatchUp` на сервере идут в потоке мира: пока всё делаем в одном потоке. Если фриз при ресинке на больших станциях станет заметен, кандидаты на отдельный поток — разбор снимка (`DecodeCatchUp`, чистые данные) у клиента и кодирование снимка из неизменяемой истории у сервера; восстановление и повтор меняют мир flecs и остаются в его потоке.
- **Предсказание своего ввода — через откат.** Своя команда применяется сразу; чужие опоздавшие команды чинятся откатом у каждого участника. Цена — откаты, собранные в пачки (см. «Технический долг»).
- **Кросс-платформенный детерминизм не гарантирован** (FMA, libm, Bullet на x64/arm64/Windows). Смягчается флагами FP и `StateDigest` + `Resync`; между платформами проверяется в CI: `CrossPlatformStateTest` пишет состояние сценария (ходьба, мышь, постройка, снос, выталкивание) по контрольным тикам, задача `cross-platform-state` в `pr_tests.yml` сравнивает дампы Windows, x64 и arm64 и показывает первое расхождение. Первый прогон нашёл два: Bullet из vcpkg на arm64 собирался с FMA (теперь `-ffp-contract=off` в `triplets/`) и имя `Eigen::Matrix4f` выводилось компилятором по-разному (теперь задано явно); после этого все три платформы совпадают побитово. Если снова разойдутся — детерминированная математика (`sin`/`cos` без libm) и/или округление `State`-полей в конце тика, моды при этом остаются на `float`.
- Пороги догона часов (`kClockCatchUpThresholdTicks`, `kClockCatchUpEveryTicks`) и окно `kMaxLateTicks`/`kMaxScheduleAheadTicks` подбираются по замерам на живой сети.
- Оценка `clock_offset` по пингу предполагает симметричную задержку (сеть туда и обратно занимает поровну) — на асимметричных каналах офсет будет немного смещён; это не ломает корректность (offset — только вход в scheduling, ошибку гасит rollback), только слегка меняет частоту откатов.
- Откат и повтор — пачкой опоздавших команд, до 10 раз в секунду; `CaptureState`/`RestoreWorld` без dirty-tracking (см. «Заметки» в `network-sync-plan.md`) стоят по ≈3 тика каждый. Ресинк (полный снимок) остаётся редким запасным путём.
- Все команды идут по reliable-каналу: при потерях возможна задержка из-за head-of-line blocking — цена гарантированной доставки.
- Мышиные дельты не коалесцируются внутри интервала отправки — точность траектории важнее; бюджет трафика проверяется тестом.
- `Camera` остаётся state (правится только рендер); удаление её из state изменило бы содержимое снимков и потребует проверки JSON-тестов.
- `two_player_replay_test.cpp` вручную заводит «дублёра» — после перехода на `Player_<id>` проверить коллизии имён и что вынос логики удерживаемых значений из `Replay` его не ломает.
- `Pause` лишь делает локальный ввод нейтральным; мир замораживается (`SimulationFrozen`) только в одиночной игре, см. «Пауза и симуляция».
- Полная реплика состояния (`CaptureState` без dirty-tracking) на каждый join/resync — нормально для десятков игроков; узкое место отмечено в `network-sync-plan.md`.
- Проверить при реализации: `enet_host_create` с портом 0 возвращает выбранный порт в `host->address.port` (нужно тестам).
- **CLI-флагов становится много.** Ревью этапа 1 отметило, что рост числа отдельных `boost::program_options`-флагов (`--server`, `--connect`, `--skip-main-menu`, `--quick-save-path`, ...) со временем станет неудобно контролировать; предложена идея конфиг-генератора вместо ручного добавления флагов. Не в рамках этого плана — оценить при следующем этапе, если флагов станет заметно больше.
- **Плагины и линковка flecs (уточнено при ручной проверке этапа 3).** Часть process-wide состояния flecs дублируется, если flecs слинкован статически отдельно в exe и в каждый модуль: `ecs_os_api` чинится `ModuleFactoryBase::SyncFlecsOsApi` (см. `core.cpp`), но ~90 встроенных `const`-констант (`EcsSparse`, `EcsModule`, ...) — нет, публичного сеттера у них не существует, и импорт первого же модуля падает. Зависит это целиком от триплета: на `x64-windows` vcpkg отдаёт `flecs.dll` (`flecs::flecs_static` там — просто алиас на неё), состояние одно на процесс, и полный плагинный путь работает — `zodiac13 --server` поднимает все четыре фабрики через `boost::dll` и слушает UDP 26213. На Linux flecs теперь собирается динамически overlay-триплетом (см. «Живой прогон»).
- **Экспорт символов между плагинами (MSVC).** `net_module` линкует `z13_module` ради `SpawnPlayer`/`PlayerEntityName`/`EnsureLocalPlayerReady`. В ELF символы видны по умолчанию, в MSVC — нет, поэтому `net_module.dll` не линковался. Решено `WINDOWS_EXPORT_ALL_SYMBOLS` на SHARED-целях `z13_module`, `bullet_module`, `net_module` (тесты линкуют их напрямую и берут внутренние символы), а не макросом-аннотацией в заголовках.
- **Смешение msgpack и FlatBuffers (обнаружено на этапе 3)** — снято: снимок и списки действий едут таблицами и структурами FlatBuffers, msgpack из проекта убран ([serialization-plan.md](serialization-plan.md), этап 1). Остались JSON-значения компонентов внутри снимка (этап 2 того же плана).
