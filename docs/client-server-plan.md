# План: клиент-сервер (ENet)

Продолжение `network-sync-plan.md`: там уже есть `PlayerActionLog` (с `player_id`), `WorldSnapshotHistory`, `Replay` и proof-of-concept «два мира сливают действия и приходят к одному состоянию». Здесь — первый настоящий транспорт, жизненный цикл сессии и синхронизация **только через команды игроков** `(action_id, value)`. Опоздавшие команды обрабатываются откатом и повтором (`WorldSnapshotHistory` + `Replay`); клиентское предсказание своих команд сюда **не входит** (см. «Риски»).

## Требования

- Сервер создаётся флагом `--server[=PORT]` (порт по умолчанию **26213**). Выделенный сервер не грузит raylib_module (нет окна, GUI, рендера).
- Клиент можно запустить сразу подключённым: `--connect host[:port]` (порт по умолчанию тот же). Несовместим с `--server`.
- Сервер также создаётся из главного меню (диалог выбора порта): тогда это listen-server — с рендером, хост играет сам.
- В главном меню кнопка «Join»: диалог с IP/хостом и портом.
- Транспорт — ENet.
- При подключении клиент получает снимок сцены. Каждый клиент получает уникальный id.
- Чужой игрок виден как октаэдр уникального цвета. Сервер виден клиентам как обычный игрок (id 0).
- **Всё — движение, взгляд, строительство и любые будущие сущности — идёт через команды `(action_id, value)`.** Клиент шлёт серверу только свои команды (экономия трафика); состояние сцены и сущностей по сети не реплицируется.

## Проектные решения

**Роль.** `z13::net::ServerRole`/`ClientRole` — runtime-singleton теги (не state, без данных), лежат в `z13/components/net.h` рядом с командами GUI. Одна и та же сетевая логика обслуживает `--server`, «Start Server» из меню, `--connect` и «Join»; отличие — только в источнике команды и наличии рендера. Ни один тег не выставлен — одиночная игра, поведение не меняется. Отдельные теги, а не одно enum-поле, чтобы будущая составная роль (напр. listen-server = сервер + локальный клиент) не требовала переопределения типа.

**Модуль.** Новый плагин `src/lib_z13/modules/net_module` по образцу `bullet_module` (фабрика, `_objects` + `_static` близнец для тестов). Публичные заголовки (`include/net_module/`): `transport.h` (интерфейс), `protocol.h` (сообщения + codec). ENet — только внутри `enet_transport.cpp`: `ENetHost*`/`ENetPeer*` наружу не выходят, соединения адресуются `ConnectionId` (uint32), `ENetHost` под `unique_ptr` с deleter, пары `enet_initialize/deinitialize` — в RAII. Сессия — singleton `NetSession` с pImpl (`State`/`state_`, `shared_ptr` — исключение для обёрток над нативным, как `PhysicsWorld`).

**Однопоточность.** ENet обслуживается системой в начале кадра (`enet_host_service(host, &event, 0)`), потоков нет — тесты детерминированы.

**Запуск без рендера.** Отдельный `config/z13_config_server.yaml` без записи raylib_module; launcher выбирает между ним и обычным `z13_config.yaml` по `Config::IsServer()`. Разбор YAML вынесен из анонимного namespace в тестируемые `ParseModuleList`/`ReadModuleList` (`z13_launcher/module_list.h`), обе возвращают `std::expected<std::vector<std::string>, std::string>`. Выделенный сервер стартует сразу в `Gameplay` (без `Pause`/меню) — `BootstrapSystem::OnSelectInitialState`. Корректное завершение по SIGINT/SIGTERM — `Core::Run()` сам ставит обработчик и сам его опрашивает (сигнальный флаг — `sig_atomic_t`, не указатель на объект; единственное оправданное исключение из «без static/глобалов»), так что `pending_shutdown_` читается и пишется только в главном потоке и не нуждается в atomic.

**`--connect`.** `Endpoint{host, port}` + `ParseEndpoint(text) -> std::expected<Endpoint, std::string>` в `lib_core` (один парсер для CLI и диалога Join; IPv6-литералы пока не поддерживаются). `Config::GetConnectEndpoint() -> std::optional<Endpoint>`. Bootstrap при заданном endpoint оставляет `Pause` (меню показывает «Connecting…») и выдаёт `JoinRequest`; успех закрывает меню, ошибка возвращает в главное меню с причиной.

**Игроки.**
- Сущность игрока именуется `Player_<id>` (снимки сопоставляют сущности по имени — два игрока с одним именем слились бы). `SpawnPlayer(world, id)` — публичный заголовок z13_module, transform считает сама (`id * kSpawnSpacing`, детерминированно, см. ниже); `Z13TestWorld::Player()` ищет локального игрока по `CurrentActionListenerTag`, не по имени.
- Id игроков выдаёт только сервер из `IdCounters.last_player_id` (state, монотонный, не переиспользуется). Сервер-игрок = 0, клиенты 1, 2, … Id блоков и прочих сущностей выделяет сама симуляция — детерминированно и одинаково на всех участниках (см. ниже).
- Точка спавна смещается на `id * kSpawnSpacing`, чтобы октаэдры не совпадали.
- «Локальность» — не state: `CurrentActionListenerTag` + `InputListener` навешивает система (`SyncLocalPlayerListener`) по `LocalPlayer.id` (`std::optional<uint32_t>`). `ActionListener` сама по себе — у **каждого** игрока, локального или нет (отдельная система `EnsurePlayerActionListener`, тоже не state-зависимая): повтор реплеит записи `PlayerActionLog` по `player_id` вне зависимости от того, чей это игрок, и ему нужно куда писать значение. Локальный игрок клиента, пришедший в снимке, получает живой ввод, остальные — нет.
- `Gameplay::OnInit` на клиенте **не** спавнит игрока и не сбрасывает `IdCounters` — сцену даёт снимок.
- Рендер камер ограничивается сущностью с `CurrentActionListenerTag` (`EnsureRaylibCamera`/`SyncRaylibCamera`): иначе `gameplay::Camera` чужих игроков из снимка породит лишние `RaylibCamera`.

**Цвет.** `PlayerColor(id)` — чистая детерминированная функция (шаг по hue на золотое сечение, фиксированные S/V), `z13/components/`. По сети не передаётся.

## Модель синхронизации: серверная последовательность команд

Каждый участник (сервер и все клиенты) исполняет **одни и те же команды на одних и тех же тиках в одном порядке**; состояние сцены — детерминированная функция от `(снимок, поток команд)`. Поэтому новые виды сущностей (не только блоки) не требуют сетевого кода: они появляются как побочный эффект команд, которые уже ходят по сети.

**Клиент → сервер.**
- Локальный ввод считается как сейчас, но на клиенте **не применяется к симуляции напрямую**: значения пишутся в буфер `OutgoingCommands` (запись только при изменении + переутверждение удерживаемых раз в секунду — уже умеет `PlayerActionRecorder`). `NetActionSender` раз в `kNetSendIntervalTicks` (3 тика ≈ 20 Гц) шлёт накопленное одним `CommandBatch`; пустой батч не шлётся — простаивающий клиент трафика не создаёт.
- `PlayerActionLog` хранит **только применённые (упорядоченные сервером) команды** всех игроков — ровно то, что нужно `Replay`. В одиночной игре (`None`) рекордер пишет в него напрямую, как сейчас.
- Каждая команда штампуется тиком клиента `t_i`. Тик применения — чистая функция `ScheduleTick(t_i, clock_offset) = t_i + clock_offset + kInputDelayTicks`. `clock_offset` клиент оценивает сам по пингу (ниже) и **сразу применяет** её: в `CommandBatch` идёт уже посчитанный `apply_tick`, не сырой `t_i` — сервер не пересчитывает `ScheduleTick` и ему не нужно знать offset клиента. Клиент кладёт свою команду прямо в очередь `RemoteInput` тем же `apply_tick` (значение квантуется так же, как на проводе) — **эхо собственных команд от сервера не нужно**.

**Сервер: `CommandSequencer`.** Берёт присланный `apply_tick` как есть, ограничивает его разумным диапазоном вокруг своего текущего тика (защита от испорченного/враждебного клиента — не доверие offset'у клиента, а просто санитизация входа), кладёт в свою очередь и рассылает `SequencedCommands` **всем клиентам, кроме отправителя** (он уже применяет её сам). Порядок внутри тика — `(apply_tick, player_id, action_id)`; порядковый номер команды не нужен и по проводу не ходит: рекордер физически не может выдать два значения одного действия на одном тике, так что ключ выводит каждый участник сам. Собственные команды хоста (listen-server) идут тем же путём. Привязка к тику (jitter buffer) сохраняет **длительность** удержания при неравных задержках пакетов. Если команда пришла уже после своего `apply_tick` (`apply_tick ≤ now` на сервере) — из-за задержки сети или неточной оценки offset на клиенте, разница неважна, — сервер откатывается и воспроизводит журнал (см. «Опоздавшие команды»), затем рассылает её остальным как обычно; отправитель ничего не теряет. Rollback тем самым не только чинит сетевые опоздания, но и снимает необходимость в точной синхронизации времени: ошибка оценки `clock_offset` — это просто ещё одна причина опоздать, не отдельный класс отказа.

**Все участники: `RemoteInput`.** Очередь команд по тику → на тике применения обновляет удерживаемое значение `(player_id, action_id)`, дописывает запись в `PlayerActionLog`, а в `CalculateActionFramePhase` (после расчёта живого ввода) перезаписывает значения в `ActionListener` игроков. Логика «удерживаемые значения → ActionListener» выделяется из `Replay` (`ReplayActionState`/`ApplyCurrentValues`), а не дублируется. Дальше системы (`ApplyMoveActionListener`, строительство, `ProcessDestroyBlockRequest`, всё будущее) работают как при живом вводе.

**Часы.** `SimulationClock` — state, поэтому `Restore` при join приводит клиентский тик к серверному тику снимка: сразу после подключения расхождение — это в основном время, потраченное на доставку снимка. Дальше клиент считает тики сам (1 на каждый `world.progress()`, тот же фиксированный `delta_time`, что и сервер), поэтому без коррекции расхождение с сервером не растёт от кадра к кадру, но и не проходит само — отсюда пинг. `kInputDelayTicks` — не порог корректности, а компромисс: чем он меньше, тем ниже задержка своих команд, но тем чаще они приходят после своего тика и вызывают откат.

**Пинг: синхронизация локального времени клиента.** Раз в секунду клиент шлёт `Ping{client_tick}`; сервер отвечает `Pong{client_tick, server_tick}` — `server_tick` берётся в момент ответа, без ожидания следующего кадра симуляции. Клиент по паре (время отправки `Ping`, время получения `Pong`, оба по своим же тикам) считает `rtt_ticks` и оценку одностороннего запаздывания `rtt_ticks / 2`, откуда новый образец `clock_offset = server_tick + rtt_ticks/2 - client_recv_tick`. Держится сглаженная оценка (EWMA, `kClockOffsetSmoothing`) — не одно сырое значение: разовый всплеск задержки не должен резко сдвигать расписание всех последующих команд. Первая оценка появляется только после первого `Pong` (до этого `clock_offset = 0`, роль `kInputDelayTicks`-запаса и rollback — сгладить стартовую погрешность); `Welcome`/`Resync` больше не несут отдельного `clock_offset` — не нужен, раз есть постоянный источник свежее join. Пинг — не про корректность (её обеспечивает rollback), а про то, чтобы `apply_tick` был близок к реальному и откатов было мало.

**Опоздавшие команды: откат и повтор.** Команда, у которой `apply_tick ≤ now` (клиент получил чужую команду поздно, сервер получил свою от клиента поздно), не отбрасывается:
- запись вставляется в `PlayerActionLog` на своё место (`BoundedHistory::MergeSorted`, ключ `(tick, player_id, порядковый номер)`);
- мир откатывается к самому свежему снимку `WorldSnapshotHistory` с `tick ≤ apply_tick` и доигрывается обычными кадрами до текущего тика (`RequestRollback(world, apply_tick, now)`); всё, что опоздало за один кадр, объединяется в один откат к самому раннему тику;
- откат — **глобальное состояние мира, а не отложенный вызов** (`lib_core/rollback.h`, этап 3). Любая система, нашедшая опоздавшую команду, дописывает её в журнал и зовёт `RequestRollback(world, to_tick, target_tick)`, который только опускает `RollbackRequest.to_tick` до `min` и поднимает `target_tick` до `max` — несколько опоздавших за один кадр коалесятся в один откат к самому раннему тику сами собой, без разбора очереди. Дальше два шага, оба внутри `TickWorld(world, delta)` — **единственного места, откуда вообще зовётся `world.progress()`** (`Core::Update()` и тестовый харнесс зовут только её): `RestoreWorld` из свежайшего снимка с `tick ≤ to_tick`, а затем **обычные кадры**, пока `SimulationClock.tick` не дойдёт до `target_tick`. Восстановление обязано идти между кадрами: подмена сущностей мира изнутри кадра заставляет flecs пропустить остаток пайплайна (проверено — фаза очистки ввода не отрабатывала). Повтор же — ровно те же системы в том же порядке, что и живой кадр, просто под флагом `ReplayInProgress`: живой ввод и рекордер отключены, `NetActionSender` не шлёт повторно уже отправленное, транспорт не обслуживается (он относится к настоящему). Число кадров догона за один `TickWorld` ограничено `kMaxCatchUpTicksPerFrame` — страховка от испорченного `target_tick`, а не планировщик;
- удерживаемые значения действий во время повтора ведёт `ReplayActionState` (`z13_module`, системы `Replay::AdvanceRecordedValues`/`InjectRecordedActionValues`): она — чистая функция от (журнал, текущий тик), и разрыв в тике сам означает «только что откатились», так что пересборка значений не требует отдельного сигнала. Входя в повтор, каждое действие выставляется «ровным» (`current_value` и `prev_value` в последнее известное значение), иначе удерживаемая клавиша прочиталась бы как новый фронт и переключатель сработал бы повторно;
- откат, которому не нашлось достаточно старого снимка, выставляет `RollbackFailed{reason}`; его разбирает тот, кто просил откат (клиент — в `Resync` или `Failed`);
- глубина отката ограничена окном хранения (`Config::GetSnapshotRetentionSeconds`, одно и то же для снимков и журнала): если достаточно старого снимка нет (`RollbackFailed`), это редкий запасной путь — `Resync` (ниже);
- события сессии (`PlayerJoined/Left` на своём тике) пишутся в тот же журнал и воспроизводятся при повторе — иначе откат через тик входа/выхода потерял бы игрока (требует расширения `Replay`);
- стоимость отката — до одного интервала снимков (`Config::GetSnapshotIntervalSeconds`, по умолчанию 1 с = 60 вызовов `progress()`); в сетевых ролях интервал можно уменьшить; глубина и частота откатов считаются в метриках.

**Join.** Вход игрока — тоже упорядоченное событие на тике `J`: на `J` сервер спавнит `Player_<id>` и шлёт `Welcome`; остальные клиенты получают `PlayerJoined{apply_tick=J, entity_state}` заранее и спавнят игрока на том же тике. `Welcome.snapshot` — **не** свежий захват на момент `J` (полный обход мира на каждый join слишком дорог), а последний кэш `WorldSnapshotHistory` (`snapshot_tick` — его тик) плюс `actions`: записи `PlayerActionLog` с `tick > snapshot_tick` — тот же формат, что повтор уже умеет проигрывать. Клиент мержит `actions` в свой `PlayerActionLog` (`BoundedHistory::MergeSorted`), кладёт присланный снимок в собственный `WorldSnapshotHistory` и подаёт обычный `RollbackRequest{to_tick = snapshot_tick, target = server_tick}` — тот же самый механизм отката (см. выше), просто на этот раз «откат» — это бутстрап с нуля, а не коррекция уже идущего мира; отдельного пути для join в коде нет. Так как `ActionListener` не state, `Welcome` кроме снимка несёт `held_values` (сейчас удерживаемые действия всех игроков) и `pending` (уже разосланные команды с `apply_tick > J`). `PlayerLeft{apply_tick}` назначается после последней запланированной команды игрока: у всех участников они успевают исполниться до удаления.

Практическое следствие для этапа 3 (до появления `CommandBatch`/`RemoteInput` в этапе 4): `actions` содержит только действия **хоста** (listen-server) — `RecordChangedActions` пишет в лог только локального игрока (`CurrentActionListenerTag`), а действия удалённых клиентов на сервер вообще не попадают, пока команды не пошли по сети. Позиции уже подключённых клиентов в снимке сервера поэтому не «протухают» сильнее, чем раньше — сервер их и так не обновляет живьём до этапа 4.

**Требования к детерминизму** (предпосылка всей схемы):
- Симуляция — чистая функция состояния, команд и тика: единый фиксированный `delta_time = 1/TicksPerSecond` на всех участниках (включая клиента), без wall-clock и `rand`.
- Порядок обработки при конкуренции — по `player_id`, а не по порядку итерации ECS (`ProcessBuildBlockRequest` и т.п.): иначе `Block_N` у участников разойдутся (это же отмечено в `network-sync-plan.md` как «не гарантия на будущее»).
- Флоаты: для симуляционных модулей отключить контракцию FMA (`-ffp-contract=off`; MSVC `/fp:precise`). Побитовая идентичность между x64/arm64/Windows и в Bullet не гарантируется — поэтому есть контроль рассинхрона.
- Живой ввод, превью кисти, рендер — вне симуляции.

**Контроль рассинхрона.** Раз в секунду сервер шлёт `StateDigest{tick, entity_count, name_hash, [player_id → position]}` на тике, кратном интервалу снимков (`WorldSnapshotHistory` уже снимает состояние именно на таких тиках). Клиент, дойдя до этого тика, сравнивает со своим снимком: структура (набор имён) — точное равенство, позиции — с допуском ε. Откат по опоздавшим командам расхождение не вызывает (после повтора состояние равно «как будто пришло вовремя»); дайджест ловит то, что откат не объясняет: числовой дрейф платформ, событие вне окна журнала, ошибку в коде. При расхождении шлёт `ResyncRequest`, сервер отвечает как на join (`Resync`: снимок + `held_values` + `pending`); клиент делает `RestoreWorld` и продолжает, сохраняя `LocalPlayer.id`.

## Протокол

FlatBuffers (`schemas/fbs/net.fbs`, уже подключённый генератор): фиксированные `struct` для горячих сообщений вместо msgpack-«карт» с именами полей, `Verifier` для недоверенных байт. Снимок — `SaveState`/`LoadState` (msgpack) в `[ubyte]`: обёртки над `CaptureState`/`RestoreWorld` (не `SaveWorldState`/`ApplyWorld` — тот фильтр `DefaultEntityFilter` исключает любую сущность с `flecs::Component`, а значение singleton-компонента живёт как раз на его собственной component-сущности, так что `IdCounters`/`SimulationClock` в снимок не попали бы). `SaveState` перегружен: `SaveState(world)` — свежий захват (fallback, когда кэша ещё нет), `SaveState(snapshot)` — сериализует уже готовый `WorldSnapshot` (кэш `WorldSnapshotHistory`, обычный путь для `Welcome`, см. «Join» выше). `kProtocolVersion` в handshake. Все сообщения — reliable, канал 0 (потерянная команда нарушила бы детерминизм), **кроме `Ping`/`Pong`** — им нужна не гарантия доставки, а честное время в пути: на reliable-канале 0 они встали бы в очередь за `CommandBatch`/`SequencedCommands` и мерили бы не сеть, а очередь. Отдельный канал 1, unreliable-unsequenced; пропавший `Ping` просто ничего не даёт для этой секунды, следующий — через секунду.

| Сообщение | Канал | Направление |
|---|---|---|
| `ClientHello{version}` | 0, reliable | C→S |
| `CommandBatch{base_tick, [CommandWire]}` (`base_tick` — уже `apply_tick`) | 0, reliable | C→S |
| `ResyncRequest{}` | 0, reliable | C→S |
| `Ping{client_tick}` | 1, unreliable | C→S |
| `Welcome{player_id, server_tick, snapshot, snapshot_tick, actions, held_values, pending}` / `Rejected{reason}` | 0, reliable | S→C |
| `Resync{server_tick, snapshot, held_values, pending}` | 0, reliable | S→C |
| `PlayerJoined{apply_tick, entity_state}` / `PlayerLeft{apply_tick, player_id}` | 0, reliable | S→все |
| `SequencedCommands{player_id, base_tick, [CommandWire]}` (`base_tick` — уже `apply_tick`) | 0, reliable | S→все, кроме отправителя |
| `StateDigest{tick, entity_count, name_hash, [PoseWire]}` | 0, reliable | S→все |
| `Pong{client_tick, server_tick}` | 1, unreliable | S→C |

- `CommandWire {tick_delta: ubyte, action_id: ubyte, value: short}` — 4 байта; `value` квантуется (`kActionValueScale`), булевы точно. Отправитель применяет **то же квантованное значение**, что получают остальные, поэтому квантование не создаёт расхождений.
- `PoseWire {player_id, x, y, z}` — только для сверки дайджеста.
- `Welcome.actions` — не `CommandWire` (тот несёт только относительный `tick_delta` в пределах одного `base_tick` для одного игрока — тесно для произвольного окна истории нескольких игроков), а `[PlayerActionRecord]` (`tick, player_id, action_id, value`) через `rfl::msgpack`, тем же типом, что и `PlayerActionLog` уже хранит на любом участнике.
- `PlayerJoined` использует уже существующий `EntitySnapshot`: в `lib_core` добавляются `SaveEntityState(world, entity)` и `ApplyWorldStateDelta(world, bytes)` (как `ApplyWorld`, но **без** удаления остальных — `RestoreWorld` для дельты не годится).
- Сырые flecs entity id по сети не ходят — только имена и `player_id`. `CommandBatch` не содержит `player_id`: сервер знает `ConnectionId → player_id`, подменить чужого игрока клиент не может.
- Сервер отбрасывает `action_id`, которого нет в `ActionMap`, ограничивает частоту команд на соединение и игнорирует `CommandBatch` до `Welcome`.

## Жизненный цикл и UI

- Server: `StartServerRequest{port}` (CLI или GUI) → открыть host → роль → `add<Gameplay>` (спавн игрока 0). Порт занят → `ConnectionStatus = Failed(reason)`; для CLI — critical-лог и код возврата 1.
- Join: `JoinRequest{endpoint}` (CLI `--connect` или GUI) → `Connecting` → `ClientHello` → `Welcome`: `LocalPlayer.id` сразу, снимок — обычным откатом (см. «Откат и повтор» выше) → `add<Gameplay>` → `Connected` в первом же кадре после догона. Если `snapshot_tick == server_tick` (кэша ещё не было, нечего проигрывать), догон не делает ни одного тика — локальному игроку тогда неоткуда получить `InputListener`/`CurrentActionListenerTag` до следующего тика, поэтому такой join сразу подчищается `EnsureLocalPlayerReady` (eager-эквивалент того, что `SyncLocalPlayerListener` сделала бы на следующем тике). `PlayerJoined`/`PlayerLeft`, пришедшие пока мир догоняет, ждут в `PendingSessionDeltas` и применяются в порядке прибытия, когда мир вернулся в настоящее (этап 4 заменит это расписанием по `apply_tick`). Таймаут/отказ/битый снимок → `Failed(reason)`, `Gameplay` не добавляется.
- Выход: «Exit to Main Menu» (`remove<Gameplay>`) → система согласования гасит сессию (сервер рассылает disconnect, клиент закрывает соединение). Потеря сервера → клиент снимает `Gameplay` (главное меню) и показывает причину. Отключение клиента → `PlayerLeft`.
- Всё производное (локальный игрок, модели октаэдров, тела блоков) восстанавливается системами, а не `OnAdd`-обсерверами.
- **GUI/рендер (raylib_module).** Команды/статус — в `z13/components/net.h` (`StartServerRequest`, `JoinRequest`, `LeaveRequest`, `ConnectionStatus`), GUI net_module не знает. Два окна на существующем стеке `Window`: `StartServerWindow` (порт) и `JoinWindow` (host, порт, статус «Connecting…»/ошибка, Cancel), валидация — через `ParseEndpoint`. Октаэдр: один общий меш (без `Model` на сущность), рисуется для каждой `Player` + `Matrix4f` без `CurrentActionListenerTag`, цвет из `PlayerColor`.

## Порядок работ (одна ветка на этап)

Этапы тесно связаны (сессия без транспорта, команды без сессии и UI без сети бессмысленны), но каждый — самостоятельная, мержимая в `main` ветка: следующий этап начинается от `main` после того, как предыдущий смержен, а не веткой поверх ветки. Это укладывается в норму «≤ ~1000 строк на ветку» из CLAUDE.md без исключений (только этап 4 — на самой границе). Тесты каждого этапа идут в той же ветке, что и код. Оценки грубые.

1. **`f/net-server-launch`** (~400): `--server[=PORT]`/`--connect` в `Config` (`kDefaultServerPort` в `constants.h`, валидация 1–65535), `Endpoint`/`ParseEndpoint`, второй конфиг модулей для сервера и выбор между ними в launcher, SIGINT, старт сразу в `Gameplay`, `ServerRole`/`ClientRole`. Без сети.
2. **`f/net-transport`** (~700): зависимость `enet` в `vcpkg.json` (+`overrides`, 1.3.18), `net_module` со скелетом, `Transport` + `EnetTransport` + `InMemoryTransport` (drop/reorder/delay/jitter для тестов), два канала (0 reliable, 1 unreliable), `net.fbs` + codec.
3. **`f/net-session`** (оценка ~700, по факту ~1750 — превышение лимита, см. ниже): handshake, id, join/leave (пока применяются сразу, без расписания), `JoinRequest` из bootstrap; рефакторинг спавна (`Player_<id>`, `SpawnPlayer`, `OnInit` по роли, `ActionListener` у каждого игрока через `EnsurePlayerActionListener`); `SaveEntityState`/`ApplyWorldStateDelta`; снимок в `Welcome` — кэш `WorldSnapshotHistory` + батч `PlayerActionLog`, доигрывается откатом (не свежий `CaptureState` на каждый join); `rollback.h` в `lib_core` (`RollbackRequest`/`ReplayInProgress`/`RollbackFailed` + `TickWorld`, см. «Откат и повтор»); расширение `Z13TestWorld` и `TestNetwork`. Перерасход — не разросшийся скоуп, а то, что откат-на-join и общая дисциплина работы с `progress()` оказались нужны уже здесь, не в этапе 4/5, как предполагалось изначально.
4. **`f/net-commands`** (~1000, на границе лимита): `Ping`/`Pong` + оценка `clock_offset` (EWMA), `ScheduleTick`, `OutgoingCommands` + `NetActionSender`, `CommandSequencer`, `RemoteInput` (вынос из `Replay`), `SequencedCommands`, `held_values`/`pending` в `Welcome`, перевод `PlayerJoined/Left` на расписание.
5. **`f/net-rollback`** (~800): откат опоздавших команд и контроль рассинхрона — вставка в `PlayerActionLog` + откат/повтор через `Replay` (клиент и сервер), события сессии в журнале, порядок обработки по `player_id`, флаги FP, `StateDigest` + `Resync` как запасной путь.
6. **`f/net-ui`** (~600): диалоги, кнопка Join, октаэдры, `PlayerColor`, ограничение рендера камерой локального игрока.

Каждая ветка начинается только после того, как предыдущая смержена в `main` — так следующая сессия перечитывает актуальный `main` и план, а не держит в контексте весь путь с начала.

## Тесты

Единая инфраструктура: `Z13TestWorld` принимает доп. аргументы командной строки и транспорт; `TestNetwork` гоняет N миров и сервисы транспорта до условия или лимита тиков (без `sleep`). Основная масса — на `InMemoryTransport` (детерминированно, drop/reorder/delay/jitter с фиксированным seed), плюс отдельный набор на реальном ENet через loopback.

**Config/launcher (1).**
- Значения по умолчанию (`server=false`, порт 26213, `connect` пуст); `--server`; `--server 30000`; невалидный порт (`0`, `70000`, `abc`) → ошибка; `--help` содержит опции.
- `--connect host`, `--connect host:port`, `--connect :80`, `--connect host:0` → корректный разбор/ошибка; `--server` + `--connect` → ошибка.
- `ParseEndpoint`: IP, hostname, пустое, порт вне диапазона.
- `ParseModuleList`: скаляр и `path:`-запись читаются одинаково, битая запись пропускается (не фатально), отсутствие `modules:`/битый YAML → ошибка.
- Сервер-мир стартует с `Gameplay`, без `Pause`, игрок id 0 есть.

**Codec (2).** Round-trip каждого сообщения; квантование `CommandWire` (ошибка ≤ 1/`kActionValueScale`, булевы точно); несовпадение версии; усечённые/мусорные/пустые байты отвергаются `Verifier`, без крэша (табличный тест); `tick_delta` не переполняется при максимальном интервале отправки.

**Транспорт (2), реальный ENet, порт эфемерный.** Connect + обмен reliable в обе стороны; корректный disconnect и событие на второй стороне; соединение на закрытый порт → ошибка за ограниченное время; порт занят → ошибка старта; сверх `kMaxClients` → отказ; RAII: создание/уничтожение хоста N раз без утечек дескрипторов.

**Сессия (3), сервер + клиенты на in-memory транспорте.**
- Снимок: блоки, построенные на сервере до подключения, есть на клиенте; `IdCounters` и `SimulationClock.tick` совпадают.
- Id: три клиента получают {1,2,3}, сервер = 0; id не переиспользуется после выхода и переподключения.
- У клиента ровно один локальный игрок (`CurrentActionListenerTag`), его id = выданному; у чужих нет `InputListener`; лишнего игрока `OnInit` не создал; клиент не трогает `IdCounters` при join.
- Имена сущностей уникальны, игроки не сливаются при `RestoreWorld`.
- `PlayerJoined` у уже подключённых; `PlayerLeft` → сущность удалена на сервере и у остальных.
- `--connect`: bootstrap выдаёт `JoinRequest`, меню остаётся до результата; провал → главное меню с причиной.
- Потеря сервера / `remove<Gameplay>` на сервере → клиент теряет `Gameplay`, `ConnectionStatus` = Disconnected с причиной.
- `Rejected` при другой `kProtocolVersion`; битый снимок → `Failed`, сцена не создана; мусорный пакет от клиента → пир отброшен, сервер жив.
- Большой снимок (≈5000 блоков) доезжает целым.
- (Сверх исходного списка, добавлено по ходу этапа 3) Три клиента подключаются одновременно: у каждого корректный набор игроков, включая тех, кто присоединился позже — потребовало придержать `PlayerJoined`/`PlayerLeft`, пришедшие во время догона, в `PendingSessionDeltas`, иначе более поздняя дельта терялась под откатом на старый снимок (см. «Откат и повтор»).
- (Сверх исходного списка) Движение хоста после кэшированного снепшота, но до подключения клиента — воспроизводится клиенту повтором из батча действий, а не остаётся «замороженным» на момент кэша.
- (Сверх исходного списка) Несколько `RequestRollback` за один кадр коалесятся в один запрос: самый ранний `to_tick`, самый поздний `target_tick`.
- (Сверх исходного списка, по итогам ревью) Клиент, подключающийся к серверу старше одного интервала снимков, получает собственную сущность игрока: `Welcome` несёт кэш **до** его спавна, поэтому сам спавн приезжает к нему тем же `PlayerJoined`, что и остальным. До этого теста весь набор зеленел по ложной причине — `ConnectionStatus` ездил в снимке (вложенный `enum class State` подходил под маркер state-компонента `T::State`), и клиент наследовал `kConnected` от сервера.

**Последовательность команд (4).**
- **Пинг:** `Ping`/`Pong` round-trip на codec-уровне; при фиксированной задержке `InMemoryTransport` оценка `clock_offset` сходится к истинному значению за несколько секунд; при seeded-jitter сглаженная оценка не скачет вслед за одним всплеском; потерянный `Ping` не рвёт цикл — следующий через секунду доходит и оценка продолжается; `Ping` идёт по каналу 1 и не блокируется очередью `CommandBatch` на канале 0 (тест с насыщенным каналом 0).
- **Расписание:** `ScheduleTick` — чистая функция, юнит-тест; клиент считает `apply_tick` и кладёт его в `CommandBatch` как есть; порядок внутри тика одинаков у всех участников при любом порядке прибытия пакетов; сервер клампит подозрительный `apply_tick` (слишком в прошлом/будущем) и не падает.
- **Нет эха:** сервер не шлёт отправителю его собственные команды (тест на счётчик сообщений), при этом мир отправителя сходится с остальными.
- **Опоздавшая вверх команда** (этап 5; транспорт задерживает клиент → сервер > `kInputDelayTicks`): сервер откатывается, применяет команду на её тике и рассылает остальным; итоговое состояние равно контрольному миру, где команда пришла вовремя; `Resync` не понадобился.
- **Главный инвариант:** сервер + 2 клиента, скриптованный сеанс (движение, взгляд, постройка, снос, поздний join, выход игрока); на каждом контрольном тике полный `WorldJsonStore::Save` у всех трёх миров совпадает (паттерн `ForwardOnlyRunIsDeterministicAcrossIndependentWorlds`).
- Локальная команда клиента не меняет его мир до своего `apply_tick` (нет немедленного предсказания); на тике применения — одновременно с остальными участниками.
- Длительность удержания сохраняется при seeded-jitter ±2 тика; постоянная задержка не меняет результат.
- Одновременная постройка двумя клиентами на одном тике: одинаковые имена и позиции блоков на всех независимо от порядка прибытия пакетов; все блоки на месте.
- Поздний join посреди удержания клавиши: по `held_values` + `pending` мир клиента сходится с серверным на тике `J + k`.
- `PlayerLeft`: запланированные команды ушедшего исполнены у всех до удаления сущности.
- Трафик: простаивающий клиент не шлёт ничего, кроме keepalive ENet; удержание W = 2 записи + переутверждение раз в секунду; скриптованный 10-секундный сеанс (W 5 с + вращение мыши 2 с) укладывается в бюджет `kClientUplinkBudgetBytesPerSecond`.
- Защита: неизвестный `action_id` отброшен; превышение лимита — отброшено; `CommandBatch` до `Welcome` игнорируется; батч от A меняет только `Player_A`.
- `PlayerActionLog` у всех участников содержит одинаковый набор применённых команд с `player_id` (совместимость с `Replay`); в режиме `None` поведение и все существующие тесты `Replay`/`PlayerActionLog` без изменений.

**Детерминизм и рассинхрон (5).**
- Порядок обработки по `player_id`: результат не зависит от порядка создания сущностей игроков (тест с перестановкой).
- `StateDigest` совпадает после скриптованного сеанса; принудительное расхождение (правка блока на клиенте / выброшенная команда) → обнаружено за интервал дайджеста → `Resync` → состояние снова равно серверному; позиции сравниваются с допуском ε.
- `Resync` сохраняет `LocalPlayer.id`, `Gameplay` и не дублирует сущности.
- Опоздавшая на клиенте чужая команда (транспорт задерживает > `kInputDelayTicks` + отставание): клиент откатывается к снимку `≤ apply_tick`, воспроизводит журнал, и состояние равно контрольному миру, где команда пришла вовремя; `Resync` нет; глубина отката попадает в метрику.
- Несколько опоздавших команд за один кадр → один откат к самому раннему тику; итог тот же, что при последовательных откатах.
- Откат через тик `PlayerJoined/Left` сохраняет/удаляет игрока правильно (события в журнале).
- Во время повтора клиент не шлёт команд повторно (счётчик исходящих сообщений); рекордер не дублирует записи.
- Команда старше окна журнала (`RollbackFailed`) → `Resync`, мир сходится с сервером.

**ENet e2e (3–5).** Один сервер-мир + один-два клиента через loopback: join, id, снимок, движение, постройка блока с совпадением состояния. Суиты именуются `NetEnet*`, чтобы их можно было отфильтровать.

**Чистые функции (6).** `PlayerColor` — стабильность и уникальность на первых 256 id, различимость (минимальная дистанция в HSV/RGB).

**Вручную (GUI/GL юнит-тестами не покрыть).** Выделенный сервер + 2 клиента на localhost (в том числе через `--connect`): октаэдры разных цветов, двигаются; постройка блока одним клиентом видна другому; выход клиента убирает октаэдр; остановка сервера возвращает клиента в меню с сообщением; listen-server из меню. Чек-лист — в описании ПР.

**CI.** `pr_tests.yml` собирает только `z13_test_runner` — enet должен собраться на x64-windows/x64-linux/arm64-linux; тесты используют только loopback.

## Состояние этапа 4 (в работе, ветка `f/net-commands`)

Записано, чтобы работу можно было подобрать с другой машины. Всё перечисленное ниже собирается и проходит тесты; незакрытое отмечено отдельно.

**Готово.**
- `Ping`/`Pong` по каналу 1, оценка `clock_offset` (EWMA, `kClockOffsetSmoothing`), чистые `ScheduleTick`/`ApplyPong` — `net_module/clock_sync.h`. Тесты: `ClockSyncTest`.
- Разделение намерения и применённого: `RecordChangedActions` пишет в `OutgoingCommands` (новый singleton в `player_action.h`), система `ApplyOwnCommands` (`PostUpdate`, `.without<ClientRole>()`) перекладывает его в `PlayerActionLog`. Вне клиента поведение прежнее.
- `NetActionSender` (`PostUpdate`, `.with<ClientRole>()`): раз в `kNetSendIntervalTicks` собирает буфер в `CommandBatch` с посчитанным `apply_tick` и квантованными значениями; пустой батч не шлётся. Сразу же кладёт ту же команду (дековантованную) в свою собственную `ScheduledCommands` тем же `apply_tick` — эха от сервера не нужно (`ScheduleLocally`).
- Сервер: `HandleCommandBatch` санитизирует `apply_tick` в окно `(now, now + kMaxScheduleAheadTicks]`, кладёт в общий `ScheduledCommands` в порядке применения и рассылает `SequencedCommands` всем, кроме отправителя. Клиент кладёт полученные `SequencedCommands` в ту же очередь. Тесты: `CommandStreamTest`.
- **`RemoteInput` (`net_module`) разбирает очередь.** Новая фаза `ScheduledCommandsPhase` (`PreFrame` → `ScheduledCommandsPhase` → `ClearActionFramePhase`): `CommitDueCommands` переносит из `ScheduledCommands` в `PlayerActionLog` записи с `tick ≤ now` (префикс — очередь отсортирована).
- **`Replay` обобщён на живые тики, не только на откат.** `ReplayActionState` → `RemoteActionState`, `synced_replay_from_tick` убран (достаточно разрыва тика). `AdvanceRecordedValues`/`InjectRecordedActionValues` переехали в новую фазу `RemoteActionFramePhase` (между `Calculate` и `Apply`, после нового `RecordActionFramePhase`) и **больше не требуют `ReplayInProgress`** — читают лог каждый тик, не только во время повтора. Инжект в `ActionListener` идёт всегда для чужих игроков; для локального — только под `ClientRole` или во время повтора (`IsLogDriven`), иначе `None`/сервер продолжают жить на живом вводе как раньше.
- `RecordChangedActions` переехал в новую фазу `RecordActionFramePhase` (сразу после `Calculate`, до `RemoteActionFramePhase`) — иначе перезапись `ActionListener` игрока чужим/отложенным значением произошла бы раньше, чем «живое» значение попадёт в `OutgoingCommands`.
- Порядок фаз обновлён и закреплён `PhaseOrderTest`: `PreFrame` → `ScheduledCommandsPhase` → `ClearActionFramePhase` → `OnLoad`…`OnUpdate` → `CalculateActionFramePhase` → `RecordActionFramePhase` → `RemoteActionFramePhase` → `ApplyActionFramePhase` → `PostUpdate` → … → `PostFrame`.
- `InMemoryTransport` теряет пакеты только на ненадёжном канале (надёжный в ENet ретранслируется), иначе тест на потерю `Ping` сносил бы рукопожатие.
- **`held_values`/`pending` в `Welcome`/`Resync`.** Формат сменён с `[CommandWire]` (нет `player_id`, годился только на одного игрока) на `[ubyte]` — `[PlayerActionRecord]` через `rfl::msgpack`, как и `actions`. Сервер: `HeldValues()` сериализует текущий `RemoteActionState.current_values` (все игроки) с `tick = snapshot_tick`, чтобы клиентский пересбор (`AdvanceRecordedValues`) подхватил его как «историю» перед `actions`; `pending` — это просто `ScheduledCommands.records` на момент отправки. Клиент мёржит `held_values` + `actions` в `PlayerActionLog` одним вызовом `MergeSorted` (порядок по тику это гарантирует) и раскладывает `pending` в свою `ScheduledCommands` через `QueueInOrder`. Тест: `CommandStreamTest.LateJoinMidHoldSeesTheHeldMovementImmediately` — клиент присоединяется, пока другой ещё держит клавишу, и его копия продолжает двигаться, а не замирает на снимке.
- **`PlayerJoined`/`PlayerLeft` на расписание, `PendingSessionDeltas` удалён.** `PendingSessionDeltas` (очередь «применить, когда мир вернётся в настоящее») заменён на `ScheduledSessionDeltas` (`{apply_tick, SessionDelta}`), которую разбирает `ApplyDueSessionDeltas` — **каждый тик, включая повтор** (иначе собственный спавн джойнера, у которого `apply_tick` может совпасть с последним тиком его же догона, было бы негде применить: `ServiceNetSession` во время догона пропускает всё остальное). `BroadcastPlayerJoined` берёт `apply_tick = server_tick` на момент спавна (тот же тик, до которого доигрывает джойн). `BroadcastPlayerLeft` — новый `LeaveApplyTick`: максимум по `ScheduledCommands` этого игрока (иначе `now`), чтобы уже отправленные им команды успели примениться everywhere. Сервер теперь **тоже** планирует своё удаление через `ScheduledSessionDeltas` вместо немедленного `destruct()` — симметрично с остальными участниками, и по той же причине (не терять команды этого игрока, которые сервер ещё не разобрал). Тесты: `PlayerLeftWaitsForAlreadyScheduledCommandsToApply` (новый); `PlayerLeftRemovesEntityOnServerAndOtherClients` обновлён (комментарий про «синхронное» удаление на сервере был неверным дольше).
- **Защита сервера от `CommandBatch`.** `HandleCommandBatch` отбрасывает команду с неизвестным `action_id` (не весь батч — только эту запись, `IsKnownActionId` через `ActionMap::IdTag`) и обрывает разбор батча, как только соединение выбирает свой лимит (`CommandRateLimits`, новый singleton в `net_session_system.cpp`: скользящее окно `kCommandRateLimitWindowTicks`/`kMaxCommandsPerRateLimitWindow`, обе константы — в `protocol.h`, т.к. нужны и тесту). Запись на соединение чистится при дисконнекте. Игнор `CommandBatch` до `Welcome` был уже в этапе 3. Тесты: `UnknownActionIdIsDroppedButOtherCommandsInTheBatchAreKept`, `CommandsPastTheRateLimitAreDroppedForThatConnection`.
- **Найден и исправлен настоящий баг предсказания на клиенте**, ловя главный инвариант тестом (см. ниже): `InjectRecordedActionValues` перезаписывала только те `action_id`, что уже были в `RemoteActionState.current_values` — для **впервые нажатого** действия (например, первое открытие режима строительства) запись отсутствовала, и живое значение `Calculate` беспрепятственно доходило до `Apply` на клиенте один кадр — ровно то самое немедленное предсказание, которого быть не должно. Исправлено: инжект теперь проходит по **всем** известным `action_id` из `ActionMap` и обнуляет то, чего нет в `current_values`, а не только перезаписывает найденное. Это, в свою очередь, вскрыло вторую проблему: `RecordChangedActions` сравнивал с `ActionListener.prev_value`, который теперь каждый тик переписывает тот же инжект — держащееся действие каждый тик выглядело как новое нажатие и уходило в `OutgoingCommands` бесконечно. Решение — `LastRecordedActionValues` (новый singleton в `player_action.h`): `RecordChangedActions` сравнивает со своим собственным «последним отправленным значением» на action_id, не трогая `ActionListener.prev_value` вовсе — полностью развязывает две системы, которые иначе спорили за одно и то же поле. Тесты: `LocalCommandDoesNotMoveTheClientBeforeItsApplyTick` (новый, целевой) плюс регрессия ловится главным инвариантом.
- **Главный инвариант и оставшиеся тесты этапа 4 дописаны.** `NetSessionTest.ScriptedSessionConvergesToIdenticalStateEverywhere` — сервер + 2 клиента, скрипт (движение, взгляд, постройка, снос, поздний join, join+leave стороннего игрока), сравнение `WorldJsonStore::Save` (через `Checkpoint`, нормализуя `tick` и — ново для сети — `IdCounters.last_player_id`, который сервер-only и легитимно расходится с клиентами: они не отслеживают чужие join/leave сверх своего собственного, см. `WithoutLastPlayerId`). `CommandStreamTest`: `HeldDurationSurvivesJitteredDelivery` (seeded `FaultConfig` jitter ±2 тика, `apply_tick` едет с командой и не зависит от времени доставки), `SimultaneousBuildsFromTwoClientsLandOnBothWorlds` (два клиента строят на одном локальном тике), `HeldKeyReassertsPeriodicallyNotEveryTick` (держим клавишу через 2 границы `SnapshotIntervalSeconds`, в логе — единицы записей, не одна на тик). Бюджет трафика в байтах/сек **не реализован** — в плане никогда не было конкретного числа для `kClientUplinkBudgetBytesPerSecond`, а придумывать его самому — не моё решение; закрыта только измеримая часть (периодичность переутверждения).

**Находка по ходу дела (важно для будущих фаз).** Вставка двух новых фаз между `Calculate` и `Apply` удлинила цепочку `input`-фаз и сломала 6 тестов, завязанных на «видно в этом же кадре» (`BuildingModeTest`, `BlockDestroyTest`, `GameStateTest`) — `z13::gameplay`-цепочка (`PreUpdatePhase → UpdatePhase → UpdateBuildingToolPhase → PostUpdatePhase → OnValidate`) висит на `flecs::OnUpdate` отдельной веткой, а не в цепочке `input`-фаз, и её порядок относительно `ApplyActionFramePhase` держался на случайном (не документированном) поведении `depends_on` при равном ранге, а не на явной зависимости. `.depends_on()` в flecs — это `add(DependsOn, target)`; в проверенных нами конфигурациях наблюдалось поведение, похожее на **замену**, а не добавление нового равноправного предка (эмпирически, второй вызов на ту же фазу отменял первый); порядок веток-сиблингов с общим предком (в т.ч. относительно builtin `PreStore`/`OnStore`/`PostFrame`) непредсказуем и **не масштабируется** с длиной цепочки. Исправлено точечно: `UpdateBuildingToolPhase` теперь явно `depends_on<ApplyActionFramePhase>()` (не `UpdatePhase` — реально ничего не ломает, `UpdatePhase` пуст), и `flecs::OnStore` явно `depends_on<z13::gameplay::PostUpdatePhase>()` (`building_system.cpp`), иначе поздний builtin-читатель мог оказаться раньше отката/применения. Для этапа 5 (откаты, `StateDigest`) держать в уме: если ещё раз понадобится удлинить цепочку `input`-фаз, **сначала перепроверять** такие межветочные зависимости эмпирически (маленький временный probe-тест с `log_info`/маркерами на каждой фазе — единственный надёжный способ, замерено в этой сессии), а не полагаться на рассуждения о рангах.

Отдельно: главный инвариант (сравнение `WorldJsonStore::Save` между сервером и живой копией клиента, а не только «удалённый вид» на другом участнике) оказался ценным сам по себе — именно он поймал баг предсказания выше, который ни один из более ранних, точечных тестов не мог обнаружить (все они либо проверяли ремоут-вид ИЗВНЕ, либо не сравнивали клиента с сервером напрямую). Держать в уме для этапа 5: тест, сравнивающий состояние клиента с состоянием сервера напрямую, а не только «клиент B видит клиента A», ловит целый класс багов вида «клиент видит у себя не то, что видит сервер».

**Не сделано — дальше по порядку.**
1. Опоздавшая команда (`apply_tick <= now`) сейчас сдвигается на `now + 1` — заглушка, настоящий ответ это откат из этапа 5 (отмечено комментарием в `SanitizeApplyTick`).
2. Бюджет трафика в байтах/сек: нужно сперва решить конкретное число (`kClientUplinkBudgetBytesPerSecond`), которого план пока не называет, прежде чем писать тест на него.

## Технический долг (оставлен этапом 3)

Ничего из этого не блокирует этап 4; список здесь, чтобы не потерялось.

- **`PendingSessionDeltas` — временная конструкция.** Пока `PlayerJoined`/`PlayerLeft` применяются сразу, дельта, пришедшая во время догона, ждёт в очереди и применяется, когда мир вернулся в настоящее. Этап 4 переводит эти события на расписание по `apply_tick` через `PlayerActionLog` — очередь надо **удалить**, а не оставить вторым путём рядом с расписанием.
- **Тесты тикают миры мимо `TickWorld`.** Около 70 прямых `world.progress()` в тестах (`Frames`/`RealFrames` в каждом файле, плюс `bullet_module`): отката они не просят, поэтому не ломаются, но «единственная точка входа» соблюдается не везде. Механическая зачистка на отдельный маленький PR.
- **`OpenAsServer` и `OpenAsClient` идентичны.** После удаления не читавшегося `is_server` их тела совпадают побайтово; различие на месте вызова осталось только документирующим. Либо схлопнуть в `Open(...)`, либо дождаться listen-server, где роль снова станет содержательной.
- **Плагины не грузятся там, где flecs слинкован статически.** На `x64-windows` проверено, что весь путь работает (см. «Риски и заметки»); на триплете со статическим flecs (по умолчанию `x64-linux`) импорт первого же модуля падает из-за дублирования process-wide состояния. Пока живьём гоняется только Windows-сборка; если понадобится Linux — сначала заставить vcpkg собирать flecs динамически.
- **Ручная проверка этапа 3 сделана наполовину.** `zodiac13 --server` поднимает все четыре плагина и слушает UDP 26213; живой клиент через `--connect` (окно, рендер) не прогонялся.

## Риски и заметки

- **Нет предсказания.** Своя команда применяется не сразу, а на тике `t_i + clock_offset + kInputDelayTicks` (порядка 100–250 мс с учётом отставания клиента от сервера), включая взгляд камеры — это ощутимо. Откат и повтор уже есть, поэтому предсказание — естественное следующее расширение: применять свою команду сразу, а на её настоящем тике откатываться и переигрывать. Если задержка взгляда окажется неприемлемой уже на этом этапе — вынести взгляд камеры в локальную часть первым.
- **Кросс-платформенный детерминизм не гарантирован** (FMA, libm, Bullet на x64/arm64/Windows). Смягчается флагами FP и `StateDigest` + `Resync`; в CI проверяется только идентичность внутри одной платформы (все тестовые миры в одном процессе).
- `kInputDelayTicks` подбирается по замерам (стартовое — порядка 12 тиков): меньше — ниже задержка, но чаще откаты.
- Оценка `clock_offset` по пингу предполагает симметричную задержку (сеть туда и обратно занимает поровну) — на асимметричных каналах офсет будет немного смещён; это не ломает корректность (offset — только вход в scheduling, ошибку гасит rollback), только слегка меняет частоту откатов.
- Откат и повтор — на каждую опоздавшую команду, потенциально десятки раз в секунду при плохой сети, а `CaptureState`/`RestoreWorld` без dirty-tracking (см. «Заметки» в `network-sync-plan.md`) — кандидат на бенчмарк до оптимизации. Ресинк (полный снимок) остаётся редким запасным путём.
- Все команды идут по reliable-каналу: при потерях возможна задержка из-за head-of-line blocking — цена гарантированной доставки.
- Мышиные дельты не коалесцируются внутри интервала отправки — точность траектории важнее; бюджет трафика проверяется тестом.
- Основной рефакторинг — разделение «намерения» (живой ввод → `OutgoingCommands`) и «применённого» (`ActionListener`, пишется `RemoteInput`) на клиенте; в режиме `None` оставить прежний путь. Порядок фаз замерен перед этапом 4 и закреплён тестом `PhaseOrderTest`: `PreFrame` → `ClearActionFramePhase` (сдвиг `current`→`prev`) → `OnLoad`/`OnUpdate` → `CalculateActionFramePhase` (`CalculateInputValues`, живой ввод) → `ApplyActionFramePhase` (`ApplyMoveActionListener`, стройка, `RecordChangedActions`) → `PostFrame` (`WorldSnapshotHistory`). «Перезапись после живого ввода» внутри `CalculateActionFramePhase` держится только на порядке регистрации систем — для `RemoteInput` лучше завести отдельную фазу между `Calculate` и `Apply`, чтобы порядок был явным и покрывался тем же тестом.
- `Camera` остаётся state (правится только рендер); удаление её из state изменило бы содержимое снимков и потребует проверки JSON-тестов.
- `two_player_replay_test.cpp` вручную заводит «дублёра» — после перехода на `Player_<id>` проверить коллизии имён и что вынос логики удерживаемых значений из `Replay` его не ломает.
- `Pause` в онлайне лишь блокирует ввод/стройку (`without<Pause>`), симуляцию не останавливает.
- Полная реплика состояния (`CaptureState` без dirty-tracking) на каждый join/resync — нормально для десятков игроков; узкое место отмечено в `network-sync-plan.md`.
- Проверить при реализации: `enet_host_create` с портом 0 возвращает выбранный порт в `host->address.port` (нужно тестам).
- **CLI-флагов становится много.** Ревью этапа 1 отметило, что рост числа отдельных `boost::program_options`-флагов (`--server`, `--connect`, `--skip-main-menu`, `--quick-save-path`, ...) со временем станет неудобно контролировать; предложена идея конфиг-генератора вместо ручного добавления флагов. Не в рамках этого плана — оценить при следующем этапе, если флагов станет заметно больше.
- **Плагины и линковка flecs (уточнено при ручной проверке этапа 3).** Часть process-wide состояния flecs дублируется, если flecs слинкован статически отдельно в exe и в каждый модуль: `ecs_os_api` чинится `ModuleFactoryBase::SyncFlecsOsApi` (см. `core.cpp`), но ~90 встроенных `const`-констант (`EcsSparse`, `EcsModule`, ...) — нет, публичного сеттера у них не существует, и импорт первого же модуля падает. Зависит это целиком от триплета: на `x64-windows` vcpkg отдаёт `flecs.dll` (`flecs::flecs_static` там — просто алиас на неё), состояние одно на процесс, и полный плагинный путь работает — `zodiac13 --server` поднимает все четыре фабрики через `boost::dll` и слушает UDP 26213. На триплете со статическим flecs (по умолчанию `x64-linux`) проблема остаётся, и правильный фикс — заставить vcpkg собирать flecs динамически, как уже сделано для SDL3/raylib/imgui. Отдельная инфраструктурная задача, не входит в этот план.
- **Экспорт символов между плагинами (MSVC).** `net_module` линкует `z13_module` ради `SpawnPlayer`/`PlayerEntityName`/`EnsureLocalPlayerReady`. В ELF символы видны по умолчанию, в MSVC — нет, поэтому `net_module.dll` не линковался. Решено `WINDOWS_EXPORT_ALL_SYMBOLS` на SHARED-цели `z13_module`, а не макросом-аннотацией в заголовках: объектные файлы общие со статическим тестовым близнецом, которому `dllexport` не нужен.
- **Смешение msgpack и FlatBuffers (обнаружено на этапе 3, шире этого плана).** Снимок (`Welcome.snapshot`) и батч действий (`Welcome.actions`) сейчас едут как непрозрачные msgpack-блобы (reflect-cpp) внутри `[ubyte]`-полей FlatBuffers-сообщения — два формата сериализации в одном протоколе. Решено на будущее свести к одному (FlatBuffers — даже ценой двойной сериализации в байты), но это не задача net_module: `WorldSnapshot`/msgpack используется по всему `lib_core` (`SaveState`/`LoadState`, `WorldSnapshotHistory`, откат, QuickSave), так что унификация — это переделка `lib_core/world_serializer.*`, отдельная инфраструктурная задача вне этого плана. Дополнительно: значения компонентов внутри `WorldSnapshot` — уже JSON-строки (`ComponentValue.value` из `world.to_json()`), это отдельный источник «двойной сериализации» (JSON-текст внутри контейнера), который смена контейнера сама по себе не уберёт — придётся явно решить, мириться с этим или переписывать генерацию значений тоже.
