# Снимок состояния: что и как кодируется, во что обходится

Описание текущего устройства (2026-11-15) и замер на хабе. Повод: хост-сервер рывками (каждый 60-й тик 100-150 мс), см. `hub-wiring-notes.md`.

## Когда берётся

`WorldSnapshotHistory::CaptureSnapshot` (`lib_core/state/world_snapshot_history.cpp`, `PostFrame`) раз в `snapshot_interval_seconds` (1 с = 60 тиков), `SnapshotCaptureRate::per_interval` раз за интервал. Одиночная игра ставит ставку 0 (launcher), сетевая сессия -- `net.rollback_snapshots_per_interval`. `SnapshotCaptureRate` -- `SessionScoped`, его значение по умолчанию 1, а не 0: не проверено, берёт ли одиночная игра снимки после выхода из сессии (`ResetSessionScopedComponents`). В сессии сразу после снимка `StateDigest::Record` считает дайджест того же тика.

## Из чего состоит снимок

`CaptureState` -> `CaptureImpl` (`world_serializer.cpp`), две независимые части:

1. **`CaptureUngrouped`**: все именованные сущности со `StateEntity` без компонента-члена группировки (`Block`). Запрос строится заново на каждом снимке. Для сущности:
   - `hash_ungrouped(e)` (у хаба только `HashOfWallEntity`: ровно три компонента -- имя, `StateEntity`, один компонент стены) и совпадение с кэшем -- сущность берётся из кэша;
   - иначе `CaptureEntity`: обход всех компонентов, `EncodeValue` (reflect-cpp в байты) каждого state-компонента, связи, путь строкой -- полное кодирование;
   - если `WallWatch` (`hashed_unchanged`) говорит, что компоненты стен не менялись, их сущности не посещаются, а берутся целым отсортированным списком (`reuse_members`).
2. **`CaptureGroups`**: блоки. Группа -- `(grid, chunk)`, чанк `index_chunk_cells` (`MakeGroupOf` в `building_module/block_snapshot_system.cpp`).
   - `BlockWatch::Unchanged` (change detection запросов по `Block` и `SpawnPoint` плюс счёт блоков, чтобы поймать удаление): не менялись -- группы прошлого снимка берутся как есть;
   - иначе `ScanGroups` проходит по всем блокам, `HashOf` (имя, `Block`, `SpawnPoint`) складывается в отпечаток группы; группа с прежним отпечатком переиспользуется, остальные кодируются.

Снимок -- `WorldSnapshot{entities, groups}` из `shared_ptr`, поэтому неизменённое делится между снимками.

## Хэши (три разных, не связаны)

- `HashOf` блока и отпечаток группы (`building_module`), вручную, покрывает только известные компоненты.
- `HashOfWallEntity`, вручную, для кэша ungrouped.
- `HashSnapshot` (`lib_core/state/snapshot_hash.cpp`): FNV по закодированным байтам всех ungrouped-сущностей плюс отпечатки групп; цена растёт с их числом и размером.
- В `ComputeStateDigest` (`net_module/protocol/state_digest.cpp`) сверх этого: пути всех ungrouped-сущностей (`e.path()`), сортировка, `HashBySector` (сектор -- куб `net.sector_size_cells`, кратный чанку) и хэши по гридам, позиции игроков.

## Что не обобщено

Сделано (`f/snapshot-cache`). Общее правило для ungrouped: если у сущности нет ручного `hash_ungrouped`, `FingerprintOf` (`world_serializer.cpp`) берёт хэш имени (путь, если есть родитель), id пар и сырые байты принятых компонентов; совпавшая с прошлым снимком сущность берётся из кэша без кодирования. Сырые байты стоят за кодирование только у «плоских» значений (`IsFlatValue`, `component_codec.cpp`): числа, enum, структуры и массивы из них, Eigen и `std::array` (opaque-массив скаляров, занимающий всю память значения); строка, ссылка на сущность или другой opaque делают сущность некэшируемой, она кодируется заново, как раньше. Не замечается переименование цели пары (в хэш идёт id цели). Ручные `HashOf` блоков и `HashOfWallEntity` остаются: у них свой отпечаток группы и `Watch`, который не посещает сущности вовсе.

## Замер: хаб, Debug, Windows (`SnapshotCostBench.DISABLED_HubSnapshot`)

Мир загружен, 300 тиков, затем снимки через каждые 60 тиков (`z13_test_runner --gtest_also_run_disabled_tests --gtest_filter='SnapshotCostBench.*'`).

| Шаг | Время |
|---|---|
| первый `CaptureState` (кэши пусты) | 560-580 мс |
| `CaptureState` после 60 тиков | 75-110 мс |
| из него кодирование ungrouped (на ~1100 сущностях) | 62-72 мс |
| из него блоки (783 группы, не менялись) | 0-10 мс |
| `HashSnapshot` | 3-6 мс |
| `ComputeStateDigest` | 21-30 мс |

Снимок хаба: 3103 ungrouped-сущности и 783 группы. Ungrouped: 1036 `WallNode`, 908 `WallSegment`, 48 `WallOpening` (кэш по хэшу, `reuse_members` после второго снимка), 1013 `Conduit` и ~100 прочих (`RoomAirEntry` 74, `Dock`, игроки, предметы, лифт).

**Кодируются заново на каждом снимке 1111 сущностей: 1013 `Conduit` без хэша (они не меняются после постройки) и ~100 прочих.** Это около 0,06 мс на сущность, 90% времени `CaptureState`. Блоки и стены при неизменной станции почти ничего не стоят.

Чем заняты 21-30 мс `ComputeStateDigest` (пути 3103 сущностей и сортировка, `HashBySector`), отдельно не замерено.

Разбивка по типам "каждая сущность кодируется отдельно" в бенче (`CaptureEntityState`, ~0,9 мс на сущность) завышена: каждый вызов заново проходит весь мир. Верны только числа сущностей и байтов по типам.

## После общего кэша (2026-11-16, `f/snapshot-cache`, те же стенды и сборка)

Хаб, `SnapshotCostBench`: первый `CaptureState` 452 мс (было 486); снимки 0-4: `CaptureState` 42 / 33 / 15 / 15 / 15 мс (было 105 / 99 / 80 / 78 / 77), `HashSnapshot` 3,0-3,6 мс, `ComputeStateDigest` 20-25 мс (не менялся). Хэши снимков те же, что до правки (`65e552f9b48980dc`, `f8038ea509852cca`, ...), то есть кэш отдаёт то же состояние. Первые два снимка после загрузки дороже: по ним сущности ещё входят в кэш.

Итог на финальной сборке, `ServerClient`, p95 / максимум, мс (было → стало): `hub` клиент 78 / 128 → 22 / 50, сервер 81 / 132 → 23 / 66; `octant` клиент 18 / 37 → 20 / 32; `spire` 50 / 78 → 40 / 75; `test` 44 / 80 → 32 / 57. `CaptureSnapshot` за тик на `hub` 5,5 → 1,3 мс, на `spire` 2,4-2,9 → 2,0, на `test` → 1,4. Кадров сверх бюджета на `hub` по-прежнему ~20: это уже не захват, а `StateDigest::Record` (около 25-30 мс раз в секунду), остаток захвата и `DoorLeafSystem::DeriveLeaf`, `PowerSystem::Balance`, `AtmosSystem::Update` каждый тик (на `spire`/`test` `DeriveLeaf` 6,6). В игре на хабе отчёт кадров показал ещё пересчёт света ячеек (`SyncCellLighting`, три кадра по ~700 мс за 10 с): это рендер, снимки ни при чём.

Рассинхроны, пойманные полным ctest: запись состояния через `get_mut` без `modified` не видна watch (поправлено в системах), а отпечаток группы по сырым байтам различался между сервером и клиентом (паддинг), поэтому публикуемый отпечаток группы теперь считается от закодированных значений, а сырые байты служат только для локального «изменилось».

Ещё ступень (хэш сущности один раз в `ShareEntity`, имена digest из снимка, игроки `SplitBySector` по имени, захват ungrouped по таблицам, запомненный порядок сортировки): `SnapshotCostBench` на хабе, `CaptureState` 22 → 11 мс, `ComputeStateDigest` 25 → 5 мс, `HashSnapshot` 4 → 0,2 мс; хэши снимков те же. `ServerClient` на `hub`: клиент p95 / максимум 22 / 50 → 16 / 35, сервер 23 / 66 → 18 / 32, кадров сверх бюджета 20 → 14-18, `CaptureSnapshot` за тик 1,3 → 0,8 мс; на `spire` и `test` кадр определяют `DeriveLeaf` (7,7-8), `PowerSystem::Balance` (2,4-2,5), `AtmosSystem::Update`, их числа между прогонами гуляют на ±10 мс p95. Остаток захвата хаба: индекс блочных групп ~3 мс и сборка групп ~3 мс.

`DoorLeafSystem::DeriveLeaf` (дверь, створка и лампа каждый тик): лампа ищется по таблице дверь → лампа, а не по имени `DoorLamp_<id>`, доступ игрока считается раз за тик, список замков на дверь не строится. `ServerClient` (мс за тик, `DeriveLeaf`): `spire` 7,9 → 2,9, `test` 7,7 → 2,7, `hub` 1,3 → 0,5; p95 клиента на `hub` 16 → 14, `spire` 47 → 37, `test` 41 → 30, медиана `spire`/`test` 13 → 7.

## Единая схема (сделано, `f/snapshot-cache`)

Решение пользователя (2026-11-16): без исключительной логики по видам сущностей, правило в `CLAUDE.md`. Ручные `HashOf` блоков, `HashOfWallEntity`, `WallWatch` и `BlockWatch` удалены; `SnapshotGrouping` несёт только `member` и `make_layout`.

- `FingerprintOf`: хэш имени и сырых байт принятых компонентов (плоские значения, `IsFlatValue`); непригодная к этому сущность отпечатывается хэшем своего кодирования.
- `StateWatch` (`lib_core/state/state_watch.h`): по запросу с `detect_changes` на каждый компонент состояния; помнит таблицы, в которые писали или чьё число сущностей изменилось, с прошлого захвата. Запросы строятся вне кадра (`PrimeSnapshotGrouping`), в кадре без них watch считает всё изменённым. Синглтоны всегда «записаны».
- Ungrouped: сущность из таблицы без записей берётся из кэша, не отпечатываясь; иначе отпечаток и, если он изменился, кодирование.
- Блоки: индекс групп (`SnapshotGroupingState::grouped`, `index`) обновляется только для сущностей изменённых таблиц, группа кодируется заново, когда меняется её ключ в индексе (сумма отпечатков по сырым байтам), а публикуемый отпечаток группы хэшируется от кодирования. `RestoreWorld` обновляет тот же индекс и сверяет группы снимка с ним.
- Запись компонента во время обхода его таблицы теперь роняет assert flecs при включённом change detection (`StoreRoomAir` исправлен): такой код надо писать после обхода.

## Первый захват (2026-11-18, `f/first-capture-state`)

Хаб, Debug, Windows, `SnapshotCostBench`: первый `CaptureState` 464 мс (5594 сущности), из них `EncodeValue` 312 мс, путь, отпечаток, связи и хеш сущности ~62 мс. `z13_core` теперь собирается с `OPTIMIZE_IN_DEBUG` (Debug обходил мету flecs без оптимизации): 207 мс. План кодирования (`EncodePlanOf`/`EncodeWithPlan`, `component_codec.h`): плоский тип один раз за захват раскладывается в шаги «скопировать байты, перед массивом Eigen/`std::array` число элементов», значение кодируется копированием, а не обходом меты; строки, ссылки на сущности и указатель-ширина идут прежним путём. Первый захват 78 мс, хеши снимков те же (`a5320932447353e4`, `5af4704b4e4743e1`), тест `AnEncodePlanWritesWhatTheWalkWrites` сверяет байты плана и обхода. Остаток первого захвата — путь, отпечаток, связи, индекс групп и сортировка.

Свет хаба, та же ветка (Debug, Windows): запечатанные коробки панелей (`SealedBoxesOf`) 1104 → 70 мс (маски на `uint8_t`, шаги по граням без `vector<bool>`); пачка ламп: текстели меток 24.6 → 5.6 мс (4 потока, обновляются только плитки перевернувшихся кубов); лампы зажигаются по бюджету кадра (`LightLamps`, без сбора блоков). Причина 8–18 fps после зажигания была не в свете: у систем `SyncCellLighting`/`SyncGridCellLights` стоял необязательный терм `RaylibCamera*` с источником `$this`, и `each` вызывался для каждой сущности мира (~3500 раз за кадр); камера теперь берётся запросом внутри. Хаб после зажигания: 60 fps, худший кадр 19.8 мс.
