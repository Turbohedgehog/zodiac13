# План: quake-подобная консоль

## Контекст

Нужна внутриигровая консоль в стиле Quake: выезжает сверху по `` ` ``/`~` поверх любого экрана (главное меню, игра), показывает лог и принимает команды. Основное применение — отладка и настройка без перезапуска. К клиент-серверной работе (`client-server-plan.md`) не относится.

## Проектные решения

- **Контракт и GUI разделены.** Реестр команд и состояние консоли — в `z13/components` (или `lib_core`, если нужно модулям вне z13), окно — в `raylib_module`. Команды регистрируют сами модули, поэтому рендер не знает их набор.
- **Реестр команд.** Синглтон `ConsoleCommands`: `имя → {описание, обработчик, дополнение аргументов}`. Обработчик берёт `std::span<const std::string>` и возвращает `std::expected<std::string, std::string>`. Модули регистрируют команды на этапе `OnInitSystems`.
- **Состояние.** Синглтон `ConsoleState`: открыта ли консоль, строка ввода, история, позиция прокрутки. Это локальное состояние окна, не игровое: не `State`, не `SessionScoped`.
- **Лог.** Кольцевой буфер записей `{уровень, текст}`. spdlog-sink в `lib_core/log.h` пишет в него все сообщения, вывод команд — туда же. Уровень задаёт цвет.
- **Окно.** Отдельный слой в ImGui поверх стека `Window` (не модальное окно): анимация выезда, прокрутка (`PgUp`/`PgDn`), история (стрелки), Tab-дополнение по реестру.
- **Ввод.** Пока консоль открыта, ввод геймплея и биндингов до мира не доходит (тот же механизм, что глушит ввод под ImGui). Симуляцию консоль не останавливает.
- **Где логировать ошибки.** Консоль показывает весь лог, поэтому вывод нужно держать под контролем: библиотечный код и функции модулей не пишут ошибку в лог, а возвращают её через `std::expected`, и решение — показать, повторить, проглотить — принимает вызывающий. Логируют только границы, которым возвращать некуда: системы, обсерверы, колбэки, `main`/лаунчер; повторяющуюся каждый кадр ошибку — один раз, а не каждый тик.
- **Разбор строки.** Токены через пробел, кавычки `"..."` и экранирование `\`. Ошибка разбора — сообщение в консоль, не исключение.

## Порядок работ

1. **`f/log-to-expected`** — сделано: библиотечный код (загрузчики input-конфига и моделей, список модулей, порядок фаз, отправка команд, сверка дайджестов) возвращает ошибки через `std::expected`, логируют системы, обсерверы и лаунчер; ошибка захвата снимка пишется один раз, пока не сменится. Сетевые обработчики пакетов и quick save/load — границы, остались с логом.
2. **`f/console-core`**: `ConsoleCommands`, `ConsoleState`, разбор строки, лог-sink и буфер, команды `help`, `clear`, `echo`. Без GUI. Тесты: разбор (кавычки, экранирование, пустая строка), регистрация команд из двух модулей, повторное имя — ошибка, отказ при неверных аргументах.
3. **`f/console-ui`**: окно в `raylib_module`, переключение клавишей, глушение ввода, прокрутка, история, дополнение. Отрисовка проверяется вручную.
4. **`f/console-commands`**: `get`/`set` по полям `settings.json` (через атрибуты схемы и `ValidateRanges`), `quit`; позже — команды сети (`host`, `connect`, `disconnect`) поверх существующих запросов.

Каждая ветка — самостоятельная, мержится в `main` перед началом следующей; лимит ~1000 строк на ветку из CLAUDE.md.

## Открытые вопросы

- Нужен ли `set`, или достаточно `get`: часть полей (`fps`, `NetTuning`) клиент берёт у сервера, а часть применяется только при старте.
- Нужен ли консоли доступ к ECS (список сущностей, `spawn`, чтение компонента)? Состояние в сети меняется только командами игроков, так что прямая запись в мир на клиенте разведёт его с сервером.
- Сохранять ли историю ввода между запусками.
