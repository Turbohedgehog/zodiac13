# План: отладочный сервер для MCP

## Контекст

Замеры на телефоне делаются вручную: Esc, «Profile...», копирование отчёта, вставка в чат (`frame-time-plan.md`, 6–10 кадров/с в атриуме `hub` на Release-APK). Нужен канал, по которому ассистент в PRoot на том же планшете сам читает отчёт о кадре и ставит игру в нужное состояние. `adb` не годится: в PRoot демон стартует только как `adb -L tcp:5037 server nodaemon`, а сопряжение настраивается на каждом устройстве (`android-local-toolchain.md`).

## Решения

- **Плагин `debug_module`** (клиентский, hot-loadable, как остальные): слушает TCP на `127.0.0.1`, один запрос — одна строка JSON, один ответ — одна строка. PRoot делит с Android сеть, поэтому `127.0.0.1` из PRoot должен доходить до игры; проверяется первым шагом заглушкой.
- **Отключается двумя способами.** (1) Список модулей: `debug_module` стоит в `z13_config.yaml` только у сборок для разработки, у релизной его нет, код не загружается. (2) Настройка `debug` в `settings.json` (таблица `DebugServer` в `settings.fbs`, по умолчанию выключена): `enabled` (`--debug-server`), `port` (`--debug-port`, 38123), `token` (`--debug-token`; пустой отказывает в работе, пока не задан). Выключенный модуль не открывает сокет.
- **Безопасность.** Только loopback, токен в каждом запросе (на Android любое приложение может подключиться к чужому loopback-порту), команды только на чтение и на безопасные действия игры (позиция, настройки графики); сетевой клиент не может ими воспользоваться.
- **Команды берёт из реестра консоли**, когда она будет (`console-plan.md`, `ConsoleCommands`): сервер лишь перенаправляет строку в тот же реестр, команды не дублируются. До консоли — собственный небольшой реестр в модуле на три команды: `frame_report` (текст `FrameReport`), `teleport` (точка из `StationViewpoints`, `TeleportLocalPlayer`), `set` (параметр графики, например тени и режимы света).
- **MCP-мост** — `tools/debug/mcp_bridge.py` (stdio, Python): инструменты `frame_report`, `teleport`, `set_setting` переводятся в запросы сокета. Адрес и токен берёт из переменных окружения.
- **Агент не знает игры, и не должен.** MCP самоописывающийся: клиент берёт список инструментов (`tools/list`) с описанием и JSON-схемой аргументов и по ним вызывает `tools/call`. Поэтому описание каждого инструмента — вся документация для агента: единицы измерения, допустимые значения (имена точек из `StationViewpoints`, имена параметров графики и их пределы), пример вызова, условие «игра на экране». Ошибки мост возвращает словами (что не так и что допустимо), а не кодами. Агент без MCP работает прямо с сокетом: протокол, порт и токен описаны на странице «как пользоваться».
- **Мост, а не MCP в игре.** Игра ничего не знает о MCP: протокол меняется в мосту. Если игре понадобится быть MCP-сервером самой (HTTP, без Python), это замена моста, а не переделка модуля.
- **Игра должна быть на экране.** Пока на экране Termux, Android ставит SDL на паузу и кадров нет: замер идёт в режиме разделённого экрана или плавающего окна.

## Порядок работ

1. **`f/debug-server`** — `debug_module` с сокетом и тремя командами, настройка `DebugServer`, мост, тест протокола (запрос без токена отказывает, выключенный модуль не слушает), страница «как пользоваться». Проверка: из PRoot по loopback на телефоне.
2. Скриншот кадра и вызов команд консоли, когда она появится.
3. Ввод (касания) — только если замеры потребуют.

## Открытые вопросы

- Доходит ли `127.0.0.1` из PRoot до игры (проверка заглушкой в этапе 1).
- Хватит ли описаний инструментов агенту, не видевшему проекта: проверить в этапе 1 запуском чистой сессии без `CLAUDE.md`.
- Версия протокола и ответ при несовместимом клиенте: нужна ли.
- Хранить ли токен в `settings.json` или только в аргументе: файл читается любым приложением с доступом к данным игры.
