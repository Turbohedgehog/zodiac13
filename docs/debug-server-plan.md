# План: отладочный сервер для MCP

## Контекст

Замеры на телефоне делаются вручную: Esc, «Profile...», копирование отчёта, вставка в чат (`frame-time-plan.md`, 6–10 кадров/с в атриуме `hub` на Release-APK). Нужен канал, по которому ассистент в PRoot на том же планшете сам читает отчёт о кадре и ставит игру в нужное состояние. `adb` не годится: в PRoot демон стартует только как `adb -L tcp:5037 server nodaemon`, а сопряжение настраивается на каждом устройстве (`android-local-toolchain.md`).

## Решения

- **Плагин `mcp_module`** (клиентский, hot-loadable, как остальные): слушает TCP на `127.0.0.1`, один запрос — одна строка JSON, один ответ — одна строка. PRoot делит с Android сеть, поэтому `127.0.0.1` из PRoot должен доходить до игры; проверяется первым шагом заглушкой.
- **Отключается двумя способами.** (1) Список модулей: `mcp_module` стоит в `z13_config.yaml` только у сборок для разработки, у релизной его нет, код не загружается. (2) Настройка `debug` в `settings.json` (таблица `McpServer` в `settings.fbs`, по умолчанию выключена): `enabled` (`--mcp-server`), `port` (`--mcp-port`, 38123), `token` (`--debug-token`) — позже, см. «Порядок работ». Выключенный модуль не открывает сокет.
- **Безопасность.** Только loopback, токен в каждом запросе — отложен: в первой ветке без токена, он остаётся опциональным шагом (ниже; на Android любое приложение может подключиться к чужому loopback-порту), команды только на чтение и на безопасные действия игры (позиция, настройки графики); сетевой клиент не может ими воспользоваться.
- **Команда — компонент-запрос, обработчик — система** (решения 2026-11-11). Структура с полями-аргументами и вложенным `using Command = z13::Command<Result, "описание", Tags<"debug">>` (имя из типа, `CommandName<"x">` задаёт своё); регистрирует тот же `RegisterComponent<T>`. Статических функций в команде нет. Вызов создаёт сущность с компонентом команды и `ReplyOf<T>` (тип выводится из `Command::Result`), системы-обработчики фазы `CommandPhase` (между вводом и симуляцией) заполняют ответ, `CommandCollect` отдаёт его вызвавшему на том же кадре; команда выполняется на следующем кадре после вызова. Обработчиков любое число (`CommandSystem<T>`): каждый видит и может изменить `ReplyOf<T>`, порядок — по регистрации. Ядро принимает аргументы и отдаёт ответ как `rfl::Generic` (`SubmitCommand`), без текста: консоль (`lib_z13/console_input`) делает из слов `Generic` по типу каждого поля (`CommandField::kind`), мост MCP — из JSON агента, схему инструмента строит мост по списку полей.
- **Теги вместо каналов.** Ядро не знает ни консоли, ни MCP: у команды есть теги (`Tags<"debug">`, смысл: `debug`, `cheat`, `admin`; константы в `lib_core/commands/tags.h`), а каждый канал (консоль, отладочный сервер, будущие биндинги Python) сам настраивает, какие теги показывать (`McpServer.tags`). Команда без подходящего тега у канала: «unknown command».
- **Команда без обработчика:** предупреждение в лог при создании мира, вызов отвечает «no handler»; тест рядом с `PluginSmoke` падает, если такая есть.
- **Реестр команд** — синглтон `Commands` в `lib_core/commands/`: имя, описание, теги, список полей с видом (`FieldKind`). Разбор строки консоли (позиционно или `имя=значение`) — в `lib_z13/console_input`, не в ядре.
- **MCP-мост** — `tools/debug/mcp_bridge.py` (stdio, Python): инструменты `frame_report`, `teleport`, `set_setting` переводятся в запросы сокета. Адрес и токен берёт из переменных окружения.
- **Агент не знает игры, и не должен.** MCP самоописывающийся: клиент берёт список инструментов (`tools/list`) с описанием и JSON-схемой аргументов и по ним вызывает `tools/call`. Поэтому описание каждого инструмента — вся документация для агента: единицы измерения, допустимые значения (имена точек из `StationViewpoints`, имена параметров графики и их пределы), пример вызова, условие «игра на экране». Ошибки мост возвращает словами (что не так и что допустимо), а не кодами. Агент без MCP работает прямо с сокетом: протокол, порт и токен описаны на странице «как пользоваться».
- **Мост, а не MCP в игре.** Игра ничего не знает о MCP: протокол меняется в мосту. Если игре понадобится быть MCP-сервером самой (HTTP, без Python), это замена моста, а не переделка модуля.
- **Игра должна быть на экране.** Пока на экране Termux, Android ставит SDL на паузу и кадров нет: замер идёт в режиме разделённого экрана или плавающего окна.

## Порядок работ

1. **`f/debug-server`** — подсистема команд в `lib_core/commands/` (запрос-компонент, теги, обработчики-системы, `RegisterComponent`). Сделано (`f/debug-server`): `command.h`, `command_registry.h/.cpp`, тесты (`CommandRegistryTest`: разбор строки, позиционные и именованные аргументы, пропущенные поля берут значения по умолчанию, теги, структура в JSON, два обработчика, команда без обработчика), предупреждение в `z13_launcher`. Отличия от замысла: отдельной веткой, без сокета и моста; `RegisterComponent` правит `world_state.h`, полная пересборка около 5 минут при `-j3` без рендерера. Тест консольного ввода (`ConsoleInputTest`) — в той же ветке. Не сделано: тест CI на команды без обработчика (рядом с `PluginSmoke`), счётчик ответов (долг ниже).
2. **`f/mcp-module`** — `mcp_module` с сокетом, настройка `McpServer` (`enabled`, `port`), команды `frame_report`, `teleport`, `set` в `raylib_module`, мост, тест протокола (выключенный модуль не слушает), страница «как пользоваться». Проверка: из PRoot по loopback на телефоне. Сделано (`f/mcp-module`, каркас): плагин `mcp_module` (TCP на 127.0.0.1 в Boost.Asio, свой поток, построчный JSON `{"id","command","arguments"}`), настройка `McpServer` (`enabled=true`, `port=38123`, `tags="debug"`; `--mcp-server`, `--mcp-port`), команды `ping` и `commands`, система `McpServerSystem::Pump` (`.immediate()`, запросы уходят в `SubmitCommand`), тесты `McpProtocolTest`, `McpFilterTest`, `McpServerWorldTest` (выключенный не слушает, ping, список команд, отказ). Проверено: полная сборка и 248 быстрых тестов проходят. Не сделано: `frame_report`, `teleport`, `set`, мост `tools/debug/mcp_bridge.py`, проверка с устройства (путь PRoot → игра по loopback не проверен); модуль есть и в релизных сборках, включён по умолчанию (флажок «MCP server» в главном меню).
3. Скриншот кадра и вызов команд консоли, когда она появится.
4. Ввод (касания) — только если замеры потребуют.
5. **Консоль** (`console-plan.md`, ветки `f/console-*`) — после плагина, не вместе с ним. Реестр команд, лог-буфер и окно закладываем так, чтобы сервер подключался к ним без переделки: команды регистрирует модуль, отладочный сервер лишь пересылает строку в реестр и отдаёт буфер лога (`tail_log`).
6. **Разговор с ассистентом из игры** (после консоли): строка, которую игрок вводит в окне консоли без `/`-команды, уходит через сокет мосту; мост пишет её в файл, который сессия ассистента читает через `Monitor` (каждая строка — уведомление), ответ ассистент шлёт инструментом `console_say`, и он появляется в окне консоли. Ограничение: работает, пока сессия ассистента открыта; ассистент отвечает по ходам, не мгновенно.
7. **Токен** (опционально): `McpServer.token` в `settings.json` или аргумент запуска; без него остаётся только loopback.

## Долги

- **Несколько обработчиков одной команды не различаются.** Каждый видит и может поменять `ReplyOf<T>`; если два обработчика изменили ответ, «последний побеждает» и это нельзя обнаружить. Нужно уметь определять, что ответ менялся больше одного раза (счётчик ответов в `CommandReply`, предупреждение в `CommandCollect`, проверка в тесте); до этого порядок обработчиков одной фазы — порядок регистрации.
- **Перехватчики подключаются только кодом модуля**, не на лету (например, командой MCP).

- **`ping` с планшета не отвечал — причина найдена (2026-11-12).** В главном меню симуляция заморожена (`SimulationFrozen`), и `ApplySimulationFreeze` отключает все фазы, кроме презентационных; `Pump` в `OnUpdate` отработал два кадра и замолчал (`server_status` показал `pumps=2` без роста). Теперь `Pump` в `PreFrame`, а `CommandPhase` и `CommandCollectPhase` презентационные: команды отвечают каждый кадр, в том числе в меню и на паузе. Цена: обработчик команды, меняющий состояние симуляции, на паузе сделает это вне тика (откаты, сетевая сходимость): команды, меняющие состояние, должны сами ставить работу в тик. Встроенный запрос `server_status` (`pumps`, `queued_calls`, `ms_since_pump`) отвечает поток сервера без игрового потока; оставлен для диагностики. Проверка на планшете — после этого APK.
- **Сборка Android пишет в `bin/`.** `build-android` кладёт `libz13_core.so` в тот же `bin/`, что и Linux-сборка, и затирает её (Linux-бинарник после этого не находит `libspdlog.so`); лечится удалением `bin/libz13_core.so` и пересборкой. Исправлено: `build_libs.py` собирает в `android_bin_release/`.

## Открытые вопросы

- Доходит ли `127.0.0.1` из PRoot до игры (проверка заглушкой в этапе 1).
- Хватит ли описаний инструментов агенту, не видевшему проекта: проверить в этапе 1 запуском чистой сессии без `CLAUDE.md`.
- Версия протокола и ответ при несовместимом клиенте: нужна ли.
- Токен (шаг 6): хранить в `settings.json` (удобно, но файл читается любым приложением с доступом к данным игры) или только в аргументе запуска (на планшете без командной строки неудобно); пока отложен.
