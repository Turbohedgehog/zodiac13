# План: редактор станции в игре

## Контекст

Станцию строят скрипты `docs/station-layout/generate_*.py` (`hub` 1805 строк, `octant`, `spire`, `shard`, общий `station_blueprint.py`): геометрия зашита в код, и каждая новая правка тянет за собой подгонку стыков, фасок и проёмов вручную (`station-geometry`). Строить станцию дальше, не меняя способ, значит копить артефакты, которые потом долго исправлять.

Цель: **граф станции с параметрами** как единственный источник правды и конвейер, который из него строит всё — помещения, коридоры, проводку и трубы, инфраструктуру, обшивку. Редактор — режим офлайн-игры: он показывает результат в самой игре и меняет параметры; ассистент правит их по просьбе из чата.

Решение пользователя 2026-11-18: веб-редактор (браузер, TypeScript, Node) отвергнут; редактор делается внутри игры, на её рендере и ImGui. Из этого плана ушли сервер для браузера, формат обмена мешами, цепочка инструментов Node и правила веб-разработки.

## Решения

- **Три части редактора, все уже есть в игре.**
  - Трёхмерный вид — сам рендер игры (`raylib_module`) с свободной камерой; граф рисуется поверх слоем оверлея (`OverlayLayers`, как F4 и F6).
  - Чат — вкладка Assistant консоли (`AssistantChat`, `console-plan.md`): ассистент читает её через `mcp_module` и правит параметры командами.
  - Палитра инструментов — окно ImGui в `raylib_module/gui/` рядом с `PaletteWindow`, построенное по схеме свойств.
- **Плагин `station_editor_module`** (клиентский, hot-loadable, как остальные) держит граф и команды редактора; окно и оверлей рисует `raylib_module` из компонентов в `z13/components/editor/` (плагин не включает чужих заголовков, `check_plugin_includes.py`). Имя несёт «station», потому что другие редакторы могут появиться.
- **Каждое действие редактора — команда** (`SubmitCommand`, тег `editor`). Мышь в окне и ассистент через MCP вызывают одни и те же команды, поэтому они равноправны, а журнал команд даёт отмену и повтор.
- **Источник правды — граф** (`assets/station/graph/<станция>.json`, схема свойств рядом), не чертёж. Блоки и стены `blueprints/*.json` — выход конвейера, руками не правятся. То, чего граф выразить не может, становится новым свойством, а не ручной правкой выхода.
- **Конвейер** — стадиями с явным форматом входа и выхода: `граф → объёмы → стены и проёмы → двери и лампы → трассы проводки и труб → обшивка`. Проверки (стыки стен, герметичность, пересечения объёмов) идут после каждой стадии. Прототип — на Python рядом с нынешними генераторами (`docs/station-layout/station_graph.py`, общие `station_blueprint.py`) и **игрой не запускается** (решение пользователя 2026-11-18: в проекте нет кода запуска процессов, и Python у игрока не гарантирован): игра правит и сохраняет граф, пересборку чертежа запускает разработчик или ассистент командой `python3 station_graph.py`, затем игра перезагружает сцену командой. Язык настоящего конвейера — открытый вопрос ниже.
- **Новый чертёж загружается в игру как сцена.** Конвейер пишет `blueprints/<станция>.json`; команда редактора перезагружает сцену: `remove<Gameplay>()` и `add<Gameplay>()`, как `StartGame` и `LeaveGame` (`game_transitions.cpp`), заново ставя `StationSceneChoice`; поза камеры запоминается и возвращается, потому что перезапуск сбрасывает счётчики id и игрока. Не проверено: читает ли `assets.source` файл заново или кэширует, и из исходников или из копии в сборке.
- **Стабильность при правке.** У узлов и рёбер постоянные id (не индексы), стадии зависят от соседей, а не от порядка обхода: сдвиг одного узла перестраивает его окружение, diff в git читается.
- **Проверка обратным ходом.** `BuildRooms` над сгенерированными блоками обязан вернуть граф, с которого всё началось; расхождение — ошибка конвейера.
- **Старые генераторы остаются, пока новый не совпадёт с ними** по `stats.txt` и тестам станции; потом переносятся по одному (`hub` первым).

## Правила разработки

Пользователь не сможет проверять код построчно, поэтому качество держат тесты и CI. К коду редактора применяются все правила `CLAUDE.md` (стиль C++, состояние, команды, ветки не больше 1000 строк); сверх них:

- **Логика не в окне.** Окно ImGui только показывает компоненты и отправляет команды; всё, что меняет граф, проверяется и тестируется без GUI (`Z13TestWorld`, как остальные модули).
- **Схема свойств — данные** (`properties.json`: тип, min/max, единицы, значение по умолчанию); окно, проверка и список допустимого для ассистента строятся по ней, ни одно свойство не прописано в коде окна.
- **Ошибки видны.** Результат конвейера (ошибки и предупреждения построчно) показывается в окне и возвращается команде; ни одна ошибка не глотается.
- **Всё управление с клавиатуры и мыши**, в окне видимый фокус; сенсорный экран — позже, редактор в первую очередь для разработчика на ПК.
- **Тесты.** Команда меняет свойство, граф проходит проверку, конвейер даёт чертёж, `BuildRooms` возвращает граф; плохие графы отвергаются с понятным сообщением. Новая функция без теста не принимается.
- **Документация.** Строка в карте кода `CLAUDE.md` и в `plans.md` скилла `plan-and-debt`, когда появится плагин.

## Граф

- **Узел** — комната с объёмом (бокс или контур с высотой) и типом: `Room`, `Corridor`, `Atrium`, `Shaft`, … Тип выбирает строитель.
- **Ребро** — соединение: коридор, проход, дверь, окно, лифт, пандус, трасса. Ширина коридора — свойство ребра, не узла.
- **Свойства** описаны данными (тип, min/max, единицы, значение по умолчанию), как `settings.fbs`: палитра редактора строится по схеме, ассистент видит список допустимого. Значения наследуются: район → вид помещения → узел. Решения о строительстве (ширина коридора, материал стен, освещённость, …) принимаются из свойств.
- **Палубы** — дискретные уровни внутри рамки (см. ниже), не абсолютная высота.
- **Строитель типа** объявляет занимаемый объём, **проломы** в чужих полах и потолках, порты и остановки. Стадия «объёмы» сначала резервирует объёмы всех узлов и рёбер, проверяет пересечения и лишь потом строит полы и потолки с вырезами.
  - **Атриум** — узел на несколько палуб; пролом выводится из высоты узла (не задаётся отдельно). Галереи — рёбра-проёмы от комнат на каждой палубе. Свет через пролом даёт `cell_light`.
  - **Лифтовая шахта** — узел-колонна; остановки — рёбра к комнатам на палубах (дверь шахты и кнопка). Заодно вертикальный стояк для проводки и труб. `BlueprintLift` сегодня знает только две остановки (`lower`/`upper`).
  - **Пандус** — ребро с перепадом высот. Длина выводится из перепада и допустимого уклона; слишком близкие узлы — ошибка валидатора, а не крутой пандус. Строится косыми панелями (`Panel`, `slant`, `oblique-walls-plan.md`), над ним оставляется высота прохода. Сначала прямой, винтовой позже.

## Рамки, гравитация и переходы

- **Рамка** (frame) — авторское понятие, соответствующее сетке игры (`multi-grid-plan.md`): форма на плоскости и высота (призма), **любая ориентация** (нужен ещё крен, в `BlueprintGrid` сегодня `yaw` и `pitch`), собственный **вектор гравитации** (направление и величина, не обязательно её «вниз») и ширина перехода у краёв. Каждый узел принадлежит рамке.
- **Поле рамок.** Вес рамки в точке — сглаженная глубина точки внутри призмы, делённая на ширину перехода, нормированная на сумму 1. Гравитация `g(p) = Σ wᵢ·gᵢ` (линейно; встречные векторы в центре перехода дают ноль — принято). Нормаль пола в точке — `−g(p)` нормированная.
- **Рамки пересекаются сами:** пересечение призм — переход, отдельного узла для него не задают. Отдельных стыков с ограничением по углу внутри перехода нет; атриум, шахта и пандус могут лежать в зоне перехода.
- **Геометрия запекается** генератором: поверхности в зоне перехода следуют полю, строятся стенами между узлами и косыми панелями. **Гравитацию считает игра** по тому же полю, в реальном времени, по позиции (не по помещению). Поле — только функция параметров рамок; если конвейер на Python, то Python и C++ считают его независимо, как `wall_panel_block` (порт, сверенный тестом на 4320 комбинациях): нужен такой же тест по сэмплам поля.
- **Владение узлами в игре — по узлу, не по клетке** (помещение нельзя разрезать сеткой, `multi-grid-plan.md`):
  1. Для узла считаются веса по всему объёму. Если во всём объёме вес одной рамки не меньше `1 − ε`, узел **чистый**, он принадлежит этой рамке.
  2. Иначе узел **смешанный**. Соседствующие смешанные узлы образуют связную **переходную область**; у неё **своя сетка** с позой, равной взвешенному среднему рамок в центре. Остаточное отклонение поля от позы запекается в `slant`. Область из двух, трёх или более рамок — всё равно одна сетка.
  3. Стыки сеток (стыковочный узел `multi-grid-plan.md`, этап 6) возникают только на границе чистой зоны с переходной областью. Границы зон привязываются к границам узлов.
  4. Если отклонение поля от позы области выходит за допустимый `slant` (`t·run ≥ run + slant`), валидатор отвергает область; разбиение на несколько сеток по полосам — второй уровень, отложен.
- Узлы, которые целиком пересекают зону перехода, редактор подсвечивает: граф в зонах перехода должен быть мельче ширины перехода.
- Отличие от SS13 (`ss13-reference.md`): в SS13 гравитация везде одна и направлена вниз; у нас по рамкам, с плавными переходами. Строка в `ss13-reference.md` добавляется веткой `f/frame-gravity`.

## Порядок работ (одна ветка на этап)

Решение пользователя: начинаем с редактора, чтобы на деле понять, как работает концепт (граф, свойства, чат, вид), и только потом закреплять поле, схему и конвейер. Этап 0 — прототип на минимальном графе; схема и конвейер этапов 3–4 затем подгоняются под то, что он показал, а не наоборот. Размеры ориентировочные.

0. **`f/station-editor-prototype`** (первый срез сделан: библиотека `station_graph`, схема свойств, Python-конвейер, чертёж `prototype`, обратная проверка `BuildRooms`; второй срез — `f/station-editor-module`: плагин и команды `editor_*`; `f/station-editor-reload`: команда `editor_reload_scene` (сцена пересобирается из файла, игрок возвращается на место; вертикаль выправляет гравитация); `f/station-editor-overlay`: слой `graph` оверлея — бокс на комнату, бокс на ребро по общей стене, цвет по виду ребра, подпись с числом проблем; на телефоне вместо F4 и F6 третья вкладка консоли «Overlays» (режим оверлея комнат и слои кнопками); общая геометрия комнат вынесена в `station_graph/graph_geometry.h`, `Diagnose` берёт схему; `f/station-editor-overlay`, дальше: окно «Station editor» (`editor_window`): список комнат и рёбер и поля свойств по схеме, правка уходит командой `editor_set_property`; компонент `EditorView` заполняет плагин, пока окно открыто) (~1200, двумя срезами): `station_editor_module` с графом-синглтоном (не `State`: источник — файл) и командами с тегом `editor` (загрузить и сохранить граф, добавить и удалить комнату и ребро, задать свойство, отмена, перезагрузить сцену из чертежа); слой оверлея графа поверх вида игры (боксы комнат и рёбер, одна подпись; подписей к отдельным боксам оверлей не умеет); окно свойств в `raylib_module` по схеме `properties.json`; чат — готовая вкладка Assistant. Конвейер — Python, вне игры (см. «Решения»). Цель — цикл «правка → пересборка → вид» и правки ассистентом; схема временная и не обещает совместимости с `f/graph-schema`. Тесты: команды меняют граф и отменяются, плохие правки отвергаются с сообщением, граф сохраняется и читается обратно, чертёж из конвейера принимается игрой.
1. **`f/frame-field`** (~700): `frames` — stateless-библиотека без flecs (веса, гравитация, ориентация по позиции, владение узлом) и, если конвейер остаётся на Python, его порт. Тесты: сумма весов 1, встречные векторы, три рамки в одной точке, сверка C++ и Python по сэмплам.
2. **`f/frame-gravity`** (~900): компонент «зона гравитации» (призма, вектор, ширина перехода) — настройка, уходит клиентам в `Welcome`; гравитация тела по позиции вместо `RoomGravity` по помещению; покрытие генераторами других сеток (`f/grid-gravity` из `station-systems-plan.md`, иначе наклонная палуба получит полную гравитацию без генератора); крен в позе сетки (`BlueprintGrid`). Тесты: игрок стоит на повёрнутой рамке, переход не дёргает камеру, предсказание и откат совпадают с сервером.
3. **`f/graph-schema`** (~800): схема графа и свойств (узлы, рёбра, рамки, свойства по данным), загрузка и проверка, формат выхода каждой стадии. Тесты на непротиворечивость схемы и значений по умолчанию.
4. **`f/graph-volumes`** (~1000): стадии «объёмы» и «стены и проёмы» для одной рамки; проверка стыков стен, герметичности, пересечений; **обратная проверка** `BuildRooms` → граф. Первая станция — маленькая тестовая из графа.
5. **`f/station-editor-tools`** (~900): инструменты мыши в виде игры — выбор узла и ребра лучом, перенос, изменение размера, подсветка ошибок конвейера на графе, срезы по палубам.
6. **`f/station-editor-chat`** (~500): команды редактора для ассистента (список допустимого строится по схеме свойств), события «граф изменён» в чат.
7. **`f/graph-special`** (~1000): атриум (пролом), шахта и пандус как строители; расширение `Lift` до N остановок или цепочка пар — решение ниже.
8. **`f/graph-frames`** (~1000): пересечения рамок сами, переходные области, владение по узлам, запекание поверхностей по полю, проверки допустимого `slant`.
9. **`f/graph-doors-lights`** (~700): двери и лампы из свойств рёбер и узлов.
10. **`f/graph-networks`** (~900): трассы проводки и труб по рёбрам, стояки в шахтах (`networks`, порты блоков).
11. **`f/graph-hull`** (~900): обшивка как оболочка вокруг объединения объёмов, клинья между наклонными палубами.
12. **`f/graph-port-hub`** (~1000+): перенос `hub` (потом `octant`, `spire`, `shard`) на граф; сверка со старым генератором.

Зависимости: 0 первым; 1 → 2 и 1 → 3 → 4 → 5; 5 и 6 независимы друг от друга; 7 после 4; 8 после 1 и 4; 9–11 после 4 (11 после 8); 12 в конце. Этапы 1–2 можно вести параллельно этапам 3–4.

## Открытые вопросы

- **Язык конвейера.** Прототип на Python и вне игры (пользователь выбрал это вместо сразу C++ конвейера: быстрее проверить концепт), но редактор живёт в офлайн-игре, и игрок без Python не сможет перестроить станцию. Варианты: оставить Python как инструмент разработчика (редактор показывает и правит граф, пересборку запускает разработчик); перенести конвейер на C++ (самодостаточный редактор, но переписывается всё, что порождают генераторы, по мере переноса); встроенный Python (тяжело и платформозависимо). Рекомендую C++ для настоящего конвейера, прототип оставить на Python. Решить до `f/graph-schema` (этап 3), чтобы не писать конвейер дважды.
- **Редактор в релизном пакете.** `mcp_module` сегодня только в сборках для разработки; `station_editor_module` — так же или включаемый настройкой? Вместе с вопросом о языке конвейера.
- **Где живут правки.** Граф в `assets/station/graph/` репозитория (правит разработчик) или в каталоге пользователя (правит игрок)?
- **Перезагрузка сцены на лету.** Как сегодня в игре станция пересоздаётся без выхода в меню; если нет — какая ветка добавит команду «перезагрузить сцену из чертежа».
- **Порог `ε`** «чистого» узла: от него зависят размеры переходных областей.
- **Второй уровень** (разбиение слишком неоднородной переходной области на несколько сеток) — в первой версии отвергаем область; нужен ли он сразу.
- **Вне призм рамок** вакуум: гравитация и геометрия не нужны? Предполагаем, что нет.
- **Лифт на N остановок:** расширять `Lift` в C++ или собирать цепочкой пар.
- **Кабели и трубы между сетками:** `networks` строит сеть по клеткам одной сетки; ребро «трасса через границу» запрещено или требует доработки `networks`.
- **Лифт через зону перехода:** кабина едет по формуле одной сетки; игрок при пересечении меняет «верх». В первой версии лифт только внутри чистой зоны одной рамки?
- **Откуда конвейер берёт палитру и размеры панелей:** общий источник с C++ (`primitives`) или копия в Python, сверяемая тестом, как у `wall_panel_block`.
